## Description

As a presenter signed in to the account that owns a deck, I want every screen that offers me a control over that deck — the presenter screen, the editor and the dry run — to give me the controls I am actually authorized to use, so that opening my own deck from a second browser does not hand me a read-only view of a presentation I own.

## Notes

Defect, **pre-existing** — not introduced by the branch that found it. Filed rather than fixed there because the review that surfaced it was scoped to three named cleanups, and the fix is a change to how authority is determined rather than to how it is displayed.

**What is wrong.** A client surface derives its whole notion of authority from one line of the shape:

```ts
const isOwner = !!getCreatorToken(id);
```

`getCreatorToken` reads the `omul-tokens` map out of this browser's `localStorage`. So `isOwner` answers "does this browser hold the deck's edit token?", not "may this caller edit this deck?" — and the server's answer to the second question is broader. `authorizeEdit` accepts **owner or edit token** (and, since REQ075, an `edit` collaborator grant): a cookie session or a personal API key resolving to `creatorId` authorizes just as an edit token does.

The two disagree whenever the account owner is not the browser that created the deck:

- The deck was created on another machine, or in another browser profile.
- `localStorage` was cleared, or the site data expired.
- The deck was created through the API with `x-api-key`, which deliberately mints **no** `creatorToken` at all (`mintToken: !viaApiKey`) because the key already authorizes edits. Such an owner can *never* have a local token for that deck.

In every one of those cases the owner opens the deck, reads `isOwner === false`, and gets the read-only view: on the presenter screen the lifecycle controls (start / end / reset) gone and the Q&A queue, preview, export and reset chips disabled; on the dry run the Edit button dead; in the editor the Preview control dead — each of them saying "you don't hold the edit token for this presentation", a message that is true and beside the point, because they do not need one. The server would authorize every one of those calls.

**Why it is P2.** It fails safe: the wrong answer is *less* access, never more, and the escape hatch already exists — the owner can claim the deck or re-accept a share link. Nothing is exposed and nothing is lost. But an owner told their own deck is not theirs is a support ticket, and it is exactly the case the API-key create path produces every time.

**What was still true when this was picked up (corrected 2026-08-14).** Two things in the paragraphs above were written on 2026-08-07 against a codebase that has since moved, and both are corrected here rather than left to mislead the next reader:

- **The presenter screen had already been half-fixed.** REQ075's collaborator work replaced its line with `heldEditToken || pres?.accessLevel === "edit"`, so `/present/:id` already recognized a tokenless owner. What remained was that two *other* surfaces still asked the token map alone — `PreviewPage` (the Edit button) and `CreatePage` (the Preview control) — and that the same decision was being spelled out three different ways, which is the shape ADR-0026 exists to prevent.
- **The prescribed server change was not made, because it was already there.** This entry proposed emitting a new `canEdit` bit on `GET /api/presentations/:id`. That response has since grown `accessLevel` (REQ075), resolved from the caller's own credentials by the same `resolveDeckAccess` every gated route uses and reporting `edit` for exactly the callers `authorizeEdit` accepts. It *is* the bit this entry asked for, under another name, so adding a second field would have put two answers to one question on the same payload. No server change was needed and none was made.

**Scope, as shipped.** One shared predicate — `callerCanEditDeck({ heldEditToken, accessLevel })` in `server/schemas.ts`, beside the `canMutateDeck` it is the client reading of, re-exported through `src/types.ts` — composed by all three surfaces. It takes both proofs a browser has, because the server honours both. The token map keeps exactly one caller: the **edit-link** control on the presenter screen, where the link *is* the token and a collaborator who was never given one has nothing to copy.

`api.ts`'s `listPresentations` was reviewed with this entry and deliberately left enumerating the token map. It is not an authority question: it answers "which decks does *this browser* know about", which is what a signed-out browser's local history is, and `HomePage` already merges it with the owner-scoped `GET /presentations/mine` — so a signed-in owner sees their decks on a machine whose token map is empty.

Out of scope: the display of the disabled state. The controls are already rendered-and-disabled with their reason per ADR-0025; what is wrong is the input to that decision, not the presentation of it. The disabled *reasons* were reworded all the same, from "you don't hold the edit token" to "you don't have edit access": once the gate is the wider question, a reason naming the token was false for the owner who never held one and useless to the viewer who cannot get one. Also out of scope: `authorizeEdit` itself, which is correct.

## Updates

- 2026-08-07 — Filed from the review of the Q&A / export / preview slice, which found the presenter screen's `isOwner` is `!!getCreatorToken(id)` — a question about this browser's `localStorage`, not about the caller's authority — while the server's `authorizeEdit` accepts owner *or* edit token. Left alone there as pre-existing and out of that task's scope.
- 2026-08-14 — Every client surface now derives "may this caller edit this deck" from one shared predicate — callerCanEditDeck({heldEditToken, accessLevel}) in server/schemas.ts, re-exported through src/types.ts — instead of from this browser's omul-tokens map. Composed by PresenterPage, PreviewPage (Edit) and CreatePage (the load guard and the Preview control); the token map keeps only the edit-link control, where the link is the token. No server change: GET /presentations/:id already reports accessLevel from resolveDeckAccess, which is the canEdit bit this entry asked for under the name REQ075 gave it — the entry's Notes are corrected to say so, and to record that REQ075 had already half-fixed the presenter screen. Disabled reasons reworded off the token onto edit access. Tests: callerCanEditDeck unit block in collaborators.schemas.test.ts, and a REQ149 block in ownership.integration.test.ts covering an API-key-created deck (no token in existence) read by its owner's API key and cookie session, the dry run opening for that owner, a claimed deck read from a browser without the token, the token holder still reading edit, and a stranger still reading null with the gate agreeing. api.ts listPresentations left token-scoped on purpose: it is local browser history, not authority, and HomePage already merges /presentations/mine over it. Verified in the running app with a tokenless owner: presenter, editor and preview all render live controls; with the session cookie cleared the editor redirects out and the presenter screen falls back to View only.
