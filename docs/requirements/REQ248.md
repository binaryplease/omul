## Description

As an organizer who works in German, I want to switch omul's interface (home, editor, presenter screen, menus, dialogs) to German, and to have it start in German when my browser is set to German, so that I can prepare and run a session without reading an English interface. The deck's participant language (REQ084) stays a separate choice made for the audience, and the surfaces the audience reads keep following it (REQ225).

## Notes

**Why this record exists.** An organizer who works in German cannot switch the interface to German. Only participant- and room-facing strings follow a language: the deck's language (REQ084), held in `src/i18n.ts` as one `Dict` per language for en/de/fr/es/it/pt/nl and read with `getDict(pres.language)`. REQ225 extended that to the quiz and leaderboard text on the participant's phone and the shared screen, and to the app menu on the participant's screens. Everything else an organizer reads is an English literal in the components, and the document is `<html lang="en">` (`src/index.html`).

**Provenance.** This record is the replay onto `main` of an earlier unmerged branch's REQ215, renumbered because REQ215 names a quiz requirement on `main`. That branch's German interface is about 13,000 changed lines. Slice 1 landed on its own; slices 2 to 11 landed together as one build, by the operator's decision (see the update log), each adapted to `main`.

**Options weighed (UI/UX concept stage, 2026-10-27).**
- *Follow the browser's language only, with no switch.* Rejected as the whole answer. An organizer whose browser is English, on a shared or managed machine, could never get German. It survives as the default.
- *Follow the deck's language.* Rejected. The deck's language is the audience's. A German organizer running an English deck for an English room would get an English interface, and home, workspaces and templates have no deck at all.
- *A setting on the account.* Rejected for now: decks can be created and presented without an account (creator tokens), so those organizers would have no switch, and it needs a schema field and a route for a display preference. Syncing the choice to an account is a possible follow-up, not part of this record.
- *A per-browser choice in the app menu, beside the theme* (chosen). The app menu is drawn on every screen (`src/components/ui/AppMenu.tsx`), it already holds the one other per-browser display preference (the theme, under `THEME_KEY` in `src/storage.ts`), and it works without an account.

**The language rule.** Who reads a string decides its language:
- **Participant- and room-facing surfaces speak the deck's language** (`getDict(pres.language)`, with REQ084's English fallback). That covers the participant screen, including its app menu (REQ225), the leaderboard, and on the presenter screen, which is also the projector (REQ191), the deck's words addressed to the room: "Waiting for responses…", "Results are private", the countdown, REQ247's join line, the room-sized QR dialog.
- **Organizer surfaces speak the interface language.** That covers the app's chrome, menus, dialogs, panels, toasts, empty states, every control's label, `aria-label` and `title`, every disabled reason, and the formatting of numbers and dates (`Intl` with the interface locale).
- **A string that tells the organizer what to do** is organizer text, even when it is drawn on the slide (the reveal, participation and countdown buttons).
- **An element whose language differs from the page's** carries a `lang` attribute.
- The two languages are independent. Neither sets the other, and REQ084 is unchanged.

**How the mechanism meets REQ225.** REQ225 already made the app menu speak a language: `appMenuLabelsFor(dict)` maps a deck dictionary's words into the menu's descriptor, and the participant screen passes `language={pres.language}`. Slice 1 keeps that path and adds the interface language beside it:
- The participant screen and the preview pass `speaksDeckLanguage`. There the menu has no Language section and speaks the `language` prop's dictionary, or English where none is given, exactly as before. The preview's header is organizer chrome, but it and its menu stay English; the preview is no slice's surface beyond the menu.
- Every other screen's menu speaks the interface language. Its Appearance, theme, feedback and legal words come from `getDict(interfaceLanguage)`, which holds all of them in German already, so there is one German copy of each. The interface text (`src/interface-text/app-menu.ts`) holds only what no dictionary has: the Language section's words and the trigger's and backdrop's names while the section is drawn.
- The panel and the feedback dialog are portaled, so they carry `lang` set to the dictionary's `locale`.
- Counted phrases in the interface use the deck's `PluralForms` shape and `fillTemplate`. `countPhrase` (REQ225) is not reused for them because it writes the count unformatted, which REQ225's surfaces print today; `pluralText` formats it with `formatNumber`.

**Design — build exactly this.**
- **Where it is picked.** A Language section in the app menu, directly below Appearance, with the theme choice's radio-group keyboard handling. Its heading carries the lucide `Languages` icon and reads the word for "Language" in the interface language, followed by the English word outside English ("Sprache · Language"), so an organizer stuck in a language they cannot read finds the way back. Rows, each language named in itself: "Automatic (English)" or "Automatisch (Deutsch)", naming what it resolves to, then "English", "Deutsch". Choosing a row switches at once without a reload and keeps the menu open. Below 640px the presenter screen's app menu is merged into the More menu (REQ199), and the section sits there in the same place. The trigger's name gains the section ("Appearance, language and legal").
- **What is stored.** `INTERFACE_LANGUAGE_KEY = "omul-interface-language"` in `src/storage.ts`, holding `"auto"` or a language code. A missing or unknown value reads as `"auto"`. Another open tab picks the choice up on its next load.
- **The default.** `"auto"` resolves to the first entry of `navigator.languages` whose primary subtag is an offered interface language, and to English when none is: `de-AT, en` is Deutsch, `fr-FR, en-GB` is English.
- **Which languages are offered.** English and German, as `InterfaceLanguage`, separate from the deck's `Lang`. A language joins only once its interface dictionary exists.
- **The mechanism.** `src/interface-text/index.ts` holds one section per surface, each a file with an English `en` holding every key and a German `de`. A key without a German entry reads English, never a blank and never a key name. Components read the text through `useInterfaceText()` from `src/interface-language.tsx`, whose provider sits at the app root. `interface-text.test.ts` fails when a key of a done slice's sections has no German entry, and grows with each slice. Tests that pin English labels keep passing, because they run with the interface in English.
- **`<html lang>`.** The provider holds it at `en` unless the mounted screen declares its own with `useDocumentLanguage()`. Every organizer screen (presenter, editor, home, workspaces, templates, generate, join, shared results) declares the interface language; the participant screen and the preview declare the deck's.
- **Translation.** The German wording uses the informal "du" that the participant `Dict`'s German already uses.
- **German is longer than English.** The bar constraints of REQ190, REQ192 and REQ199 must hold in German too, at 360, 768, 1280 and 1536px.
