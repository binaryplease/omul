## Description

As an operator who does not run Docker, I want one documented path to build omul from this repository and run it on a plain Linux host. The instance must keep its data across restarts and come back after a reboot, so that I can self-host it without a container runtime.

## Notes

**Why this record exists.** `docs/deployment.md` and the README's self-hosting section documented only the Docker image (REQ172). The server did not need Docker. The `Dockerfile` runs `bunx vite build`, then `bun build server/index.ts`, both with `NODE_ENV=production`, then `bun dist/server/index.js`. A checkout can run the same steps. `mise run build` does not quite: `.mise.toml` sets `NODE_ENV=development` for every task, and the task overrides it for the server half only, so its client is React's development build. What was missing was the documentation, not the code.

**What was built.** Documentation only: `docs/self-hosting-without-docker.md`, linked from `README.md` (Self-hosting) and from `docs/deployment.md` (a "Running without Docker" subsection under Running the image). It covers:
- the build: the Dockerfile's two commands under `mise exec -- env NODE_ENV=production`, because mise's `[env]` overrides an exported `NODE_ENV`. Without that setting, `bun build` folds development mode into the server bundle, and that server binds `127.0.0.1` and does not serve the client;
- a foreground smoke test against `/api/health`;
- a root-only environment file (`/etc/omul/omul.env`);
- a systemd unit (`DynamicUser`, `StateDirectory=omul` as the `DATABASE_PATH` directory, `Restart=on-failure`, `WantedBy=multi-user.target`);
- the reverse proxy's obligations, backups with the service stopped, and the upgrade sequence.

Variable meanings are linked to `docs/deployment.md`, never restated.

**No new packaging.** No Nix module, install script, `Dockerfile`, `compose.yaml` or `flake.nix` change, and no application code.

**A posture the guide has to cover, because the code does not.** In production the server listens on `0.0.0.0` (`server/index.ts`, `HOSTNAME`), and no variable changes that. The container covers this by publishing on the host's loopback. A plain host has no such layer, so port 3000 would be reachable from the network, without TLS and past the proxy. The documented unit therefore ships `IPAddressDeny=any` / `IPAddressAllow=localhost` as its default, and the guide makes removing them an explicit step. Removing them is needed when mail or deck generation (REQ007) needs outbound traffic, and the host firewall then has to close the port instead. The guide also asks the operator to check from another machine that the port is closed. A unit-file confinement is weaker than a server that binds loopback when asked. A configurable listen address is application code and out of scope here; it would be a requirement of its own.

**What was verified, and what was not.** On the development machine (macOS, Bun 1.4.2, no root):
- `mise run build` exited 0.
- `bun dist/server/index.js` ran under `env -i` with only the guide's variables, on a free port with a scratch `DATABASE_PATH`. `/api/health` answered `{"ok":true}` (200), `/api` answered its discovery index (200), `/` redirected to `/app/` (302) and `/app/` served HTML (200). The three SQLite files were created in the configured directory.
- Without `BETTER_AUTH_SECRET` the same command exited 1 with `BETTER_AUTH_SECRET is not set — refusing to start.`

The systemd unit, the environment-file permissions and the `IPAddress…` confinement were reviewed on paper only. Nothing here ran them on a systemd host.

**Renumbered and ported.** This record was written as REQ216 on a branch that was not merged as it stood. That number names a different requirement in this catalog, so the record carries REQ249 here, and its content was replayed onto the current `main`. The port changed the guide where `main` differed from the branch's base:
- the backup section, and the state-and-backups text in `docs/deployment.md` and the README, name a fourth database: `feedback.sqlite` (`server/feedback-store.ts`, `FEEDBACK_DB_FILENAME`), created beside the docstore once `OMUL_FEEDBACK_ENABLED` is `"true"` or `OMUL_FEEDBACK_PROMPT_PERCENT` is set, and moved by `OMUL_FEEDBACK_DB`;
- the environment-file step says a path that `OMUL_AUTH_DB`, `OMUL_ADMIN_DB` or `OMUL_FEEDBACK_DB` sets has to stay inside `/var/lib/omul`, the unit's only writable directory;
- the example release is `v1.2.0`, the newest tag;
- the boot log is described as lines tagged per posture, because `[rate-limit]` and `[discovery]` print three lines each.

The unit keeps `IPAddressDeny=any` / `IPAddressAllow=localhost` as its default, because `server/index.ts` still binds `0.0.0.0` in production. The guide states that the two lines also block mail and deck generation (REQ007). A configurable bind host stays out of scope here and is a requirement of its own.
