## Description

As the owner of a repository headed for publication, I want the drawn brand marks that now ship in the tree to carry an explicit use position of their own — separate from whichever license covers the code — and I want the repository's public name and the package's name settled against the product's name, so that publishing the code does not silently hand every recipient the right to ship a build wearing this product's identity.

## Notes

Raised by a publication readiness check, **internal**. Nothing here is a disclosure and nothing needs rotating; it is a gap in the license claim REQ161 is preparing, opened by work that landed after REQ161 was written.

**What landed, and when.** REQ167 and REQ169 carried a drawn wordmark and ring signet into the tree on 2026-08-27, two days after REQ161 enumerated the tree's third-party license position. Eight files under `public/brand/` — the wordmark, its inverse form, a closed-ring signet, an open-ring signet, and a 512px raster export of each — plus `src/components/BrandMark.tsx`, which draws them, and `src/index.html`, whose document title is now the product name alone. REQ161's enumeration predates all of it and therefore does not cover it.

**Why a permissive identifier is not the whole answer.** An SPDX identifier at the repository root is a copyright grant over the files in the tree, and it does not stop at the ones that are code. Applied unqualified, it grants every recipient the right to copy, modify and redistribute the mark files too — which is how a fork ends up shipping a build that presents itself as this product. The remedy is not to weaken the code license: it is to say, in the tree, that the marks are excluded from it and on what terms they may be used. A trademark position is a different instrument from a copyright license and the two are commonly shipped side by side; which instrument, and what it says, is the owner's decision with the legal advisor, and this requirement does not choose it.

**The naming divergence is now a mandate question, not a detail.** The repository, its `package.json` `name` and its remote all carried the working name — while REQ167's done-when is that *no user-facing surface still shows it*. So the public URL, the package name and the product name did not agree, and publication fixes all three at once and irreversibly: a repository name becomes a canonical URL and a package name, once spent on a registry, is never reused. The finish line has to name which one the public artifact carries before anything is created, not after.

**Ordering.** This sits with REQ161, before REQ165's extraction: the tree that crosses into the new repository is the tree whose license claim has to be true, and the new repository is created under whichever name the answer above settles on.

**Done when.** The mark files carry an explicit use position stated in the tree and excluded from the code license by name or by path; the public repository name, the `package.json` name and the product name are reconciled by a decision on record; and REQ161's third-party enumeration is extended to cover `public/brand/` and `src/components/BrandMark.tsx`.
