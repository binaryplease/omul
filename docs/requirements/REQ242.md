## Description

As a participant, I want to get into a live poll from whatever browser my phone or laptop opens the link in, so that the browser I happen to use never decides whether I can take part.

The participant entry path — the join page, entering a code or opening a deck link, stating a name where the deck asks for one (REQ076), and the first live slide arriving over the WebSocket — works in each browser on a written support list. Where a browser on that list cannot run omul, the participant sees a message that says so instead of a blank or stalled page.

**Done when.** The support list is written down in `docs/` (engines and minimum versions, with iOS Safari and an in-app browser among them). The entry path is walked in each listed browser against a live deck, and the result per browser is recorded in this requirement. Every failure found has been fixed or has its own requirement. A browser below the list's minimum gets the unsupported-browser message. `mise run check` and `mise run test`, as `AGENTS.md` declares them, apply unchanged.

## Notes

Defect, **internal**: raised from presenter feedback received on 2026-10-28 after a session with a large audience. The presenter reported the UI and the poll under load as fine; the one problem was that some participants, depending on the browser they used, had trouble getting into the poll. Which browsers or devices, and whether the page stayed blank or showed an error, is not known yet; the presenter has been asked.

Candidate causes found by reading the code, none of them confirmed:

- `getParticipantId()` (`src/api.ts:1544-1551`) calls `localStorage` with no guard. Where storage is blocked (some private modes, some in-app browsers, cookies-and-site-data disabled) `getItem` or `setItem` throws, and the entry path has no fallback.
- The same function calls `crypto.randomUUID()`, which exists only in a secure context and only from Safari 15.4, Chrome 92 and Firefox 95 on.
- `vite.config.ts` sets no `build.target`, so the bundle uses Vite 8's default browser baseline. Browsers older than that baseline can fail to parse the bundle and show an empty page with no message.
- The live slide arrives over `new WebSocket` (`src/api.ts:1496`). A network or proxy that blocks WebSocket upgrades leaves the participant waiting with no explanation.

Previous checks of individual features ran in Chromium and WebKit only (REQ216, REQ223). No requirement so far covers the entry path across browsers.
