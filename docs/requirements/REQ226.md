## Description

As a participant joining a presentation whose first slide is a quiz question, I want the question's countdown to start when the presenter brings the question up, not when the presentation goes live, so that I am not left with two thirds of the time because I was still typing the code. This repairs REQ057 (the quiz question window), which opened the first slide's question as a side effect of going live.

- **Going live does not open a timed quiz question.** When the slide on screen at go-live (the first slide) is a quiz question with a time limit, `startPresentation` does not stamp `slideStartedAt` for it. Every other first slide, an untimed quiz question included, is still opened by going live as before.
- **The waiting question takes no answers.** On a live, presenter-paced deck, a timed quiz question with no opening instant refuses an answer with the stated refusal `quiz-not-started` (`quizWindowNotYetOpened` in `server/schemas.ts`). Before this, "no opening instant" read as "no deadline": the answer was accepted and, timed against no instant, scored the full 1000 points.
- **The presenter starts it with the existing timer control.** On the shared screen, the control under the question reads **Start timer** while the question waits (`quizAwaitingStart`) and **Restart timer** once it has run. Both call `POST /presentations/:id/timer`. The waiting state wears the primary button, because starting is the one thing left to do. The confirmation toast reads "Question timer started" or "Question timer restarted" (`quizTimerControlFor`).
- **The room sees the question, not the countdown.** The phone shows the question and its options (or the answer field), locked, with "Waiting for the presenter to start this question" in the deck's language, in the polite status region. The shared screen shows the same line where the countdown will be.
- **The result stays withheld while it waits.** `quizQuestionIsRunning` counts a waiting question as running. So the shared screen draws "Results appear when the time is up." and no key, and the phone draws no verdict. This is consistent with REQ214/REQ216 (reveal at window end) and REQ217 (each answer timed against its own window).
- **Navigating to a quiz question later still opens it on arrival**, as before. Only the slide on screen at go-live waits.

## Notes

Defect, **internal**: found by a UI test pass of the quiz feature on `f3bd62e` (minor m3). On a deck whose first slide was a quiz, "Start Presentation" started the countdown. A participant who joined at once and passed the name gate had 20 s of 30 s left.

Reproduced on the current tree before the fix. `POST /start` on a deck whose first slide is a 30 s quiz wrote `slideStartedAt.qz`, and the integration test "going live leaves a timed first question waiting" fails on the pre-fix tree.

The refusal is wider than the waiting slide. Any timed quiz question on a live, presenter-paced deck that has not been opened refuses answers, including one further ahead that a hand-built request names. Those were previously accepted at full points for the same reason. The phone only ever offers the slide on screen, so no participant flow changes. Survey decks (REQ003) are not affected: nothing is ever opened there, and a quiz question there stays untimed by construction.

Open product question, not decided here: should a quiz slide carry a per-slide "start manually" setting? That would make *any* quiz question, not only the one on screen at go-live, wait for the presenter. The minimal behaviour above covers the defect. A later question still opens on arrival, so a presenter who reaches it before the room is ready uses Restart timer, as before. Paging back to a waiting question from a later slide opens it on arrival, as any navigation does.
