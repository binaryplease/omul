## Description

As a participant in a scored quiz, I want my phone to show the room's results and the solution once the question is over, without reloading the page, so that I see what the rest of the room sees at the same moment. This repairs REQ056 (the answer key is withheld until the question is over and then becomes the audience's) and REQ057 (the question's window), and keeps the phone in step with the shared screen's own change-over (REQ214).

A quiz question is over when its window has run out with the submission grace, or when the presenter has closed it to submissions after it opened (REQ111). At that moment every connected participant sees the revealed results: on a select question the correct option is marked for everybody, also for whoever answered wrongly or not at all; on a typed question the grouped answers and "Accepted: …" appear. The reveal setting still decides: under `on-click` the verdict and the results wait for the presenter's reveal, and under `private` nothing about the tally changes. Reopening a closed question inside its window withholds the key again.

Before the presenter has reached a quiz question, or while a live-paced deck is not live, the question is not "being answered": the shared screen says to start the presentation rather than waiting for the question to close.

## Notes

Defect, **internal**: found by a UI test pass of the quiz feature on `f3bd62e` (major M3). Reproduced on the branch after REQ214, before this fix, in Chromium. A select question showed "Not quite" to a wrong answerer with no option marked correct. A typed question kept "1 answer in — they appear once the question is over." under "Time's up". Only a reload showed the result.

**What was wrong.** While a question runs, every `results.updated` frame the room is sent withholds the key (`isCorrect: null`) and a typed question's answers (`typedAnswers.entries: null`) (REQ056), and so does the phone's copy of the deck. The end of the window changes what the audience may see without changing a single stored row, so nothing re-sent the tally. The phone showed results from the countdown's deadline onward, but with the last withheld frame in hand. The deadline is also too early: answers in flight are accepted for the grace after it.

**Why the server says so, not a client refetch.** The window is the server's: the same `slideStartedAt`, limit and grace the vote boundary refuses a late answer on. When the server broadcasts at that instant, one frame goes to each room, and it is never early. A refetch on each phone at deadline + grace would send every phone in the room to the results endpoint in the same millisecond, the load REQ150 removed from the answer path. Each phone would also read the instant through its own clock offset, and a refetch that landed a hair early would get the withheld shape again and need a retry. The cost is a timer held in memory, which the server re-arms from the store at boot.

**What closes it.**

- `server/keyed-timers.ts`: one pending one-shot timer per key. A new schedule replaces the old one, so a restarted timer's old close never fires into the new window. Unref'd, and failures are reported, never thrown.
- `server/services/presentations.ts`: `armQuizWindowCloses` schedules a close at deadline + grace + 1 ms for each open quiz window on a live deck. It runs when a question opens (`setActiveSlide`, `startPresentation`), when its timer restarts, and when the deck is saved (a changed time limit). `sendQuizWindowClosed` re-reads the deck when the timer fires. It sends nothing if the deck is no longer live or the slide is no longer a quiz, and waits again if the window has moved later. Otherwise it sends the ordinary coalesced room tally, which carries the key on `instant` and the withheld marker (ignored by clients) on `on-click`/`private`. `rearmQuizWindowCloses` re-arms every live deck at boot (`server/index.ts`). `setSlideParticipation` re-sends a quiz slide's tally on close and on reopen.
- `server/schemas.ts`: `solutionVisibleToAudience` treats a quiz question closed to submissions **after it opened** as over. A question closed before it was ever opened stays withheld, because closing ahead of time is no reveal. `quizQuestionIsRunning` (REQ214) is false on a live-paced deck that is not live and for a question with no opening stamp. An audience-paced deck stamps nothing and runs its questions until they are closed or the deck ends. This is the step-1 review's MUST-FIX: a draft deck said "Results appear once the question is closed to answers." on the shared screen, and the shared results page said a question nobody had been asked was "still being answered".
- `src/components/ParticipantSlideView.tsx`: "the question is over" is now `useQuizQuestionRunning` (REQ214), the same reading and the same instant the shared screen changes over on, not the countdown's `expired`. The verdict, the scorecard re-read and the room's tally follow it. The answer lock still engages at the deadline.
- `src/pages/SharedResultsPage.tsx` reads the window on the server's clock (`serverNow`) rather than the visitor's.

**How it is held.** `server/ws.integration.test.ts` covers four cases, all with no answer cast after the window: a select question's window running out sends a frame with the key; a typed question's sends the grouped answers and the accepted list; closing with time left sends the key and reopening withholds it; `on-click` sends only withheld markers. All four fail without the server change. `server/keyed-timers.test.ts` covers replacement, independence of keys, cancel/reset, clamping and error routing. `src/components/ParticipantSlideView.test.ts` covers the phone: nothing is drawn inside the grace, results and the key appear once it is over, closing ends the question with time left, `on-click` waits for the reveal. The grace and closed cases fail against the old view. `server/quiz.schemas.test.ts` covers the new `quizQuestionIsRunning` and `solutionVisibleToAudience` cases. `src/components/PresenterSlideView.test.ts` renders a draft deck and checks it says to start the presentation.

**Left as it was.** Under `private` the phone shows neither results nor a verdict, as before this change; `tallyVisibleToAudience` gates both and is untouched. After a close with time left, the countdown keeps running on the phone (REQ111/REQ057 behaviour), and a participant who had not answered sees "No answer in time".
