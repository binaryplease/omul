## Description

The PDF a deck is rendered to draws every character the deck and its responses actually contain — a Polish `ł`, a Greek or Cyrillic word, a CJK title, an emoji a participant typed into a word cloud — rather than folding them to a nearest Latin letter or to a substitution mark.

Built by NST11820-req158-extended-pdf-fonts.

### The embedded face (slice 1)

- **Where:** `server/fonts/NotoSans-{Regular,Bold}.ttf` (release NotoSans-v2.015 from `notofonts/latin-greek-cyrillic`, the **hinted** TTFs, ~620 KB each), imported `with { type: "file" }` so `bun build` copies them into `dist/server/` and resolved against `import.meta.dir` (the bundle names them relative to itself, not to the working directory). Read when `server/deck-pdf.ts` loads, so missing fonts fail the server at boot. Notice and license: `NOTICE.md` §3, `public/licenses/OFL-1.1-fonts.txt`. Embedding goes through `@pdf-lib/fontkit` (a dependency now) with `subset: true`.
- **Why hinted:** pdf-lib's subsetter writes the *unhinted* build's glyphs out unreadable — poppler and macOS Quartz both drew blank boxes, while the text still extracted fine, so only a rendered page shows it. The hinted build subsets cleanly. Any face a later slice adds needs the same check on a **rendered** page, not on extracted text.
- **The fold:** `winAnsiText()` became `faceText()`, the same three steps against the face's own coverage (the code points both weights have) instead of WinAnsi, after an NFC pass so base-plus-accent input draws the precomposed glyph. CJK, emoji and every script beyond the four above (Arabic, Hebrew, Devanagari, Thai, …) still fold to `?` — slices 2 and 3 cover only CJK and emoji, so closing REQ158 as written leaves those other scripts folded; that is a gap to state when slice 3 lands, not one either slice closes.
- **Measuring:** `widthOfTextAtSize` on an embedded face runs fontkit's shaping over the whole string, and the wrapper measures the same text many times (REQ159): a 160,000-character run took 6.8 s. `textWidth()` sums per-character widths cached per font, and the same render takes 0.9 s. Slice 2 has to keep that: a run drawn from two faces is measured per segment, in the face that segment is drawn in.
- **Open for slice 2:** pdf-lib draws one `drawText` per font, so a fallback face means splitting a wrapped line into segments by coverage and drawing them at advancing x — the wrapper and every `drawText` site in `createFlow` take one font today. Tests read text back through each font's `ToUnicode` table (`server/deck-pdf.test-support.ts`), which already handles any number of fonts on a page.

### The CJK face (slice 2)

- **Where and which:** `server/fonts/SarasaGothicSC-Regular.ttf` (release v1.0.42 from `be5invis/Sarasa-Gothic`, the **hinted** TTF, unmodified, ~24 MB; SIL OFL 1.1, notice beside Noto Sans's in `NOTICE.md` §3 and `public/licenses/OFL-1.1-fonts.txt`). Its CJK glyphs are Source Han Sans', the design Noto Sans CJK shares. Imported and resolved exactly as slice 1's faces are, and `bun build` ships it into `dist/server/`.
- **One weight, one orthography:** regular only, so bold runs (titles, headings, labels, table headers) draw their CJK characters in the regular face. It is the SC build, so a Japanese or Korean Han character whose regional form differs is drawn in the Simplified Chinese form.
- **What it draws:** only CJK — code points in Han, Hiragana, Katakana, Hangul and Bopomofo by `Script_Extensions`, the CJK Symbols and Punctuation block, and full-width punctuation (`，`, `？`, `（）`). Full-width letters and digits still fold to ASCII, and the face's own Latin, arrows and symbols are never used. `faceText()` keeps what either face draws and folds the rest; `fontFor()` sends a kept character to Noto Sans if Noto has it, otherwise to the CJK face.
- **Why this face — the subsetter's real precondition.** `@pdf-lib/fontkit`'s TTF subsetter writes the subset's `loca` in the short format whenever the subset's glyph data is under 64 KB, which halves every offset, and it does not pad glyph records to make that exact. A face with odd-length glyph records therefore subsets into glyphs starting a byte off: readers draw them blank or not at all while the text still extracts. That — not hinting as such — is what slice 1 hit with unhinted Noto Sans; ttfautohint output pads every record. Tried and rejected on a rasterized page: Noto Sans CJK SC (CFF outlines; poppler rejects the subset as an invalid font), Google's static Noto Sans SC TTF (odd records, and no Hangul), Droid Sans Fallback (odd records, no Hangul), and the Noto Sans CJK variable TTF (36 MB, variable). Sarasa's hinted build has no odd record and draws cleanly in poppler and macOS Quartz. `server/deck-pdf.schemas.test.ts` now asserts every `.ttf` under `server/fonts/` has only even glyph offsets, so a face that would draw blank fails `bun test` rather than a rendered page.
- **Drawing:** a line is split into runs by face (`faceRuns`) and drawn one `drawText` per run at advancing x (`drawFaceText`); every `drawText` site in `createFlow` and the footer goes through it. Measuring is unchanged in shape: `textWidth` still sums cached per-character widths, each taken from the face that character is drawn in, so a mixed line is measured per segment.
- **Size:** the CJK face is embedded only when the document contains a character it draws (`drawsCjk`, which runs the model through the same fold before drawing — embedding is async and the flow is not). An export without CJK does not grow at all; an unused subset would still have cost ~9 KB of hinting tables. With CJK it grows by those ~9 KB plus the glyphs used: a one-slide deck with four CJK answers and a CJK title exported at 39 KB from the built server, against 18 KB for a comparable Latin one.
- **Performance:** a 160,000-character CJK run (question + body, 320,000 characters) renders in 3.1 s against 0.9 s for Latin — still linear (40k → 160k is ×4.0). CJK characters are about twice as wide, so twice the lines, and pdf-lib's per-line shaping pass costs about three times as much per character in this face. A run alternating script on *every* character is the worst case, one `drawText` per character: 6.9 s at the same size, still linear. The CJK long-run test carries a 15 s backstop; the ratio is the assertion.
- **For slice 3:** an emoji face is a third entry in `fontFor()` and a third coverage set beside `CJK_COVERAGE`, which keeps emoji out today because it is restricted to CJK scripts. The face has to pass the even-offset test, and the conditional embedding should extend to it (`drawsCjk` generalises to "which fallback faces does this document need"). After slice 3, Arabic, Hebrew, Devanagari, Thai and the other scripts outside all three faces still fold — the gap slice 1's notes ask to be stated when REQ158 closes.

### The emoji face (slice 3)

- **Where and which:** `server/fonts/unifont-15.0.06.ttf` (Basic Multilingual Plane, ~12 MB) and `server/fonts/unifont_upper-15.0.06.ttf` (the planes above it, ~13 MB) — GNU Unifont release 15.0.06 from unifoundry.com, the TrueType builds, unmodified and under their upstream file names. Dual-licensed SIL OFL 1.1 and GPLv2+ with the font embedding exception since 13.0.04; this tree takes the OFL, notice in `NOTICE.md` §3 and `public/licenses/OFL-1.1-fonts.txt`, no reserved font name. One face in two files, split where Unifont splits it: `❤ ✅ ⭐ ☕ ✨ ❌ ⚡` live in the first, nearly every other emoji in the second. Imported and resolved exactly as slices 1 and 2's faces are, and `bun build` ships both into `dist/server/`. SHA-256, identical to the files at `unifoundry.com/pub/unifont/unifont-15.0.06/font-builds/`: `unifont-15.0.06.ttf` `9282b6eff54eeca2e7f58c9a40a91049bd219f3e6a45fbee8eba013379b9af3a`, `unifont_upper-15.0.06.ttf` `2c7035286fe16270c0c75b9de708c680fac3732dba5f85f9cce5c33f095c871c`.
- **Why this face — the even-offset test again.** Every monochrome emoji face with an outline design failed it: Noto Emoji (the current variable build from `google/fonts`, its static Regular from Google Fonts, and the 2019 and 2020 monochrome builds from `googlefonts/noto-emoji`, 431–824 odd records each) and OpenMoji 17.0.0's `OpenMoji-black-glyf` (7,721 odd records; also CC BY-SA, not a font licence). Rendered through `@pdf-lib/fontkit`'s subsetter and rasterized with poppler, Noto Emoji drew one or two glyphs in five and OpenMoji nothing, exactly as the slice-2 notes predict. Noto Sans Symbols 2 (full build) passes but covers 202 of 1,219 emoji-presentation code points; DejaVu Sans passes and covers 98. Unifont 15.0.06 has no odd record in either file. It is the last Unifont release with TrueType outlines: 15.1 onwards ships CFF only, whose subsets poppler refuses (slice 2), and an `.otf` would also sit outside the even-offset test, which reads `.ttf` files. So the face draws the emoji of Unicode 15.0 and earlier — not every emoji Bun's tables know, as this note first claimed from a cmap lookup.
- **What it looks like:** monochrome pictographs on Unifont's 16-pixel grid, a full em wide, black like the text around them — legible, not the colour picture a phone shows. One weight: bold runs (titles, headings, labels, table headers) draw their emoji in it as they draw CJK in the regular face.
- **What it draws:** only emoji — code points that are `\p{Extended_Pictographic}` or `\p{Emoji_Presentation}` (the latter adds the regional indicators). Unifont has glyphs for nearly every script, Arabic, Hebrew and Thai included, and none of them is drawn from it; `→` still folds to `?`. **Placeholders are not coverage:** Unifont maps every code point of its planes, and one Unicode had not assigned by 15.0 — the 1,453 still reserved in the emoji blocks (U+1FC45), and the 14 emoji Unicode 16.0 and 17.0 added (`🫩`, `🫪`, 1F6D8, 1FA89, …, 1FAEF) — is mapped to a placeholder: its hex digits knocked out of a solid full-cell square, which poppler drew as a box reading `01F AE9`. `isUnifontPlaceholder()` leaves any glyph whose outline traces that whole-cell square out of the coverage set at module load; no real emoji glyph in either file does (checked: it flags exactly those 1,467 and nothing else), so they fold to `?`. Tests hold every reserved emoji-block code point and the 14 to `?`. `fontFor()` asks the text face first, then the CJK face, then the emoji face, so the few characters both fallbacks claim (`〰`, `㊗`) draw from the CJK face as they did before this slice. `Typeface` carries a map of the fallback faces the document embeds instead of a `cjk` field, and `drawsCjk` became `fallbackFacesDrawn`, which answers "which fallback faces does this document need" through the same fold.
- **Sequences — verified on rasterized pages in poppler and Quartz, and by tests reading the text back:** a ZWJ sequence (`👨‍👩‍👧`) draws as its members side by side. The joiner is dropped first, because fontkit's shaping swaps a default-ignorable character for the space glyph — kept, it drew a gap and copied out as a space. A skin tone is dropped (`👋🏽` → `👋`): Unifont draws a standing modifier as a swatch square. A keycap draws as its digit (`1️⃣` → `1`): Unifont's U+20E3 is a zero-advance mark drawn a full 16-pixel cell back, so after a narrower Noto Sans digit it boxed the space before it too. A flag draws as its two regional indicators, which Unifont draws as boxed letters (`🇩🇪` → (D)(E)). A subdivision flag's tag characters are dropped, leaving `🏴`. `FE0F` was already dropped with the other variation selectors. None of these throws, draws a blank box, or leaves a `?` between drawable parts.
- **Size:** an export with no emoji embeds neither file and is the size it was: a Latin, Greek and Cyrillic deck rendered at 20,559 bytes before this slice and after it (pdf-lib names each subset with a random numeric suffix, so a size can move by a byte between any two runs). A three-page retro deck with about 25 distinct emoji across title, options, bars, a response table and the footer exported at 37,306 bytes against 32,308 for the same deck without them — about 5 KB for both subsets, with no hinting tables to carry. Reading the two files and their coverage at module load adds about 25 ms to the import (189 ms against 165 ms), and the placeholder scan, which parses each emoji glyph's outline once, about 30 ms more (≈215 ms).
- **Performance:** the measurement path is unchanged — per-character widths cached per typeface, each from the face that draws it, so a mixed line is measured per segment. A 160,000-character unbroken emoji run (question + body) renders in 0.38 s against 0.13 s at 40,000, a ratio of 3.0, and against 0.92 s for the Latin run of the same length. Unifont has no `GSUB`/`GPOS`, so the shaping pass `drawText` makes per line costs next to nothing even though an emoji is twice as wide. A run alternating `😀` with Latin breaks without losing a character (every emoji is a surrogate pair, which the break search already steps off). `deck-pdf.schemas.test.ts` holds the emoji run to the same ratio shape as the Latin and CJK long-run tests.
- **Renderers checked:** a full `renderDeckDocument` export, rasterized page by page with poppler's `pdftoppm` (`pdffonts` lists `UnifontMedium` and `UnifontUpperMedium` as embedded CID TrueType subsets) and with macOS Quartz (`CGContext.drawPDFPage` from a Swift script). Both draw every emoji above legibly at body, bold title and footer sizes, alongside Noto Sans and Sarasa runs on the same line.
- **What still folds after REQ158:** Arabic, Hebrew, Devanagari, Thai and every other script outside Noto Sans' Latin/Greek/Cyrillic, the CJK face's Han/kana/Hangul/Bopomofo and the emoji face's emoji — to the nearest drawable form or a single `?`, never failing the export. Also every emoji added after Unicode 15.0 (`🫩`, `🫪`, …). Colour and bold emoji, RTL shaping and the download filename's ASCII fold were out of scope.

### Before slice 1

Raised by the REQ096 implementation, which ships the fold rather than the coverage. The paragraphs below describe the export as REQ096 shipped it.

`server/deck-pdf.ts` sets its text in the PDF **standard fonts** (Helvetica / Helvetica-Bold). Nothing is embedded, so the file is small and every reader draws it identically — but their encoding is **WinAnsi**, which covers Latin-1 plus a handful of typographic characters and no more. `winAnsiText()` is what keeps that from being a crash: a character WinAnsi has is kept, one it does not is decomposed and stripped of its combining marks (so `č` prints as `c`, `ą` as `a`), and a run of what survives neither collapses to a single `?`. Without it `drawText` throws on the first unencodable character and the whole export fails over one word somebody typed, which is why the fold is there and not merely tolerable.

What it costs: a deck authored in a script these fonts cannot express exports as a page of `?`, and a Latin-Extended deck exports with its diacritics quietly removed. Neither is silent in the code — both are documented at the endpoint and in `docs/api.md` — but both are a real loss of what the organizer wrote.

The fix is an **embedded font**, which is a decision with a size to it rather than a bug to patch:

- A vendored Latin + Latin-Extended + Greek + Cyrillic face (vendored and bundled, never fetched at runtime) is a few hundred KB and closes everything except CJK. `pdf-lib` embeds TrueType/OpenType through `@pdf-lib/fontkit`; the faces this repo already ships (`@fontsource-variable/figtree`, `@fontsource/dm-mono`) are WOFF2 and would need a TTF/OTF beside them.
- CJK needs a font an order of magnitude larger again, and is the part that decides whether this is one font or a subsetting step.

Subsetting on export would keep the file small and is the shape that scales to both, at the cost of a real font pipeline in a module whose whole point today is that it has none.

Whichever way it lands, `winAnsiText()` stays as the floor for whatever the embedded face still cannot draw — the export must never fail over a character.
