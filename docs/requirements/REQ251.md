## Description

As the operator of an instance that is reachable from the internet so that participants can join, I want to switch off account sign-up with one environment variable, so that a visitor cannot open an account on my instance. Accounts that already exist keep signing in, resetting their password, verifying and changing their email, and doing everything they do today. Joining a presentation by code stays open to everyone without an account. With the variable unset the instance behaves exactly as it does today.

## Notes

**What happens today**, read at `0249270`. Email-and-password sign-up is enabled unconditionally (`server/accounts.ts:148`, `emailAndPassword.enabled: true`), and no environment variable turns it off. It is the only way an account is created: `betterAuth()` in `server/accounts.ts` configures no social provider and no magic-link plugin, and its one plugin, `apiKey` (`:289`), creates no users. Blocking the sign-up endpoint at a reverse proxy leaves the "Create account" tab of the sign-in dialog visible (`src/auth.tsx:417–425`) and offering an action that fails.

**The dependency already has the switch.** Better Auth `1.6.23` (the version `bun.lock` resolves) reads `emailAndPassword.disableSignUp`; with it set, `POST /api/auth/sign-up/email` answers `400` with code `EMAIL_PASSWORD_SIGN_UP_DISABLED` (`better-auth/dist/api/routes/sign-up.mjs:143`), and the sign-in route does not read the option.

**The variable.** `OMUL_SIGNUP_DISABLED`. Unset or `"false"` keeps sign-up open; `"true"` closes it; any other value stops the server at boot with an error that names the variable, the way `server/auth-secret.ts` refuses to boot without a usable secret. The repository's other boolean switches read `=== "true"` and treat every other value as off (`server/auth-secret.ts:97`); for a switch that closes something, that rule would leave an instance open on a typo such as `"1"`, so it does not apply here. The value is read once at boot. `.mise.toml` sets the default `"false"`.

**What the client is told.** A public, read-only `GET /api/instance-access` answers `{ signUpOpen, guestCreationOpen }`, both always present (`guestCreationOpen` is REQ252's). Its response schema is a Zod schema in `server/schemas.ts`, and the route carries a `detail` for `/api/docs` like `GET /api/legal` (`server/routes/legal.ts:15`) does.

**Client.** While sign-up is closed, the "Create account" tab stays visible and is disabled, with the reason stated on it: sign-ups are closed on this instance; ask its operator for an account. The reason reaches keyboard, touch and screen-reader users the way `docs/frontend.md` describes for an unavailable control (REQ127, `src/components/ui/ReasonTip.tsx`); a `disabled` attribute with the reason in a `title` alone does not. The same dialog is the gate of a deck that requires participants to sign in (REQ134), so that surface follows without a change of its own. The home page's offer to keep this browser's decks with an account (REQ194) chooses between `"signin"` and `"signup"` (`src/email-recovery-prompt.ts:67`); while sign-up is closed it offers signing in only.

**What `docs/deployment.md` tells the operator.** The operator creates their own account before setting the variable, or sets it to `"false"`, signs up and restarts with `"true"`. While sign-up is closed, a deck that requires participants to sign in (REQ134) can be joined only by people who already have an account on the instance.

**Done when** with `OMUL_SIGNUP_DISABLED=true` a sign-up request answers `400` with `EMAIL_PASSWORD_SIGN_UP_DISABLED`, an existing account signs in, `GET /api/instance-access` reports `signUpOpen: false`, the "Create account" tab is disabled with its reason, and a value other than unset, `"true"` or `"false"` stops the server at boot naming the variable; with the variable unset each of those behaves as before. Tests cover the parsing, the refused sign-up and the unaffected sign-in, and `docs/deployment.md` and `docs/api.md` document the variable and the endpoint. The gate and the test suite `AGENTS.md` declares stay green.

**Out of scope.** Deciding which accounts may create presentations: REQ252 closes creation without an account, and every existing account may still create. An invitation flow or an allowlist that lets named addresses sign up while sign-up is closed. Any change to the landing page.

## Updates

- 2026-11-18 — Filed from https://github.com/binaryplease/omul/issues/29, together with REQ252 (closing presentation creation without an account). Every code reference checked at `0249270`; Better Auth's `disableSignUp` behaviour checked in the `1.6.23` package `bun.lock` resolves.
- 2026-11-18 — Shipped. `OMUL_SIGNUP_DISABLED=true` sets Better Auth 1.6.23 `emailAndPassword.disableSignUp` in `server/accounts.ts`: `POST /api/auth/sign-up/email` answers `400 EMAIL_PASSWORD_SIGN_UP_DISABLED`, and sign-in, password reset and the other account routes are unaffected. The parsing rule lives in `server/closing-switch.ts` as `readClosingSwitch(variable, environment)`: unset, empty or `"false"` is open, `"true"` is closed, and any other value throws an Error naming the variable. Read at boot, that throw stops the server. `server/instance-access.ts` holds `SIGNUP_DISABLED_ENV`, `signUpDisabled()`, `resolveInstanceAccess()` and the `[accounts]` boot report line. New public route `GET /api/instance-access` (`server/routes/instance-access.ts`, factory `createInstanceAccessRoutes(access)`, mounted in `server/index.ts` with the access resolved at boot) answers `InstanceAccessSchema` from `server/schemas.ts`: `{ signUpOpen, guestCreationOpen }`, both always present. `guestCreationOpen` is hard-wired to `true` in `resolveInstanceAccess()`. Client: `useInstanceAccess()` in `src/instance-access.ts` loads the route once per page load, parses it with the shared schema via `api.getInstanceAccess()`, and draws the instance open until the answer arrives. The sign-in dialog renders the "Create account" tab as a `ReasonButton` with the reason `account.signUpClosed` (en, de) and leaves the sign-up tab once sign-up is reported closed. `emailRecoveryOfferFor()` takes `signUpOpen` and offers "signin" while it is false. `.mise.toml` sets the default `"false"`; `docs/api.md` and `docs/deployment.md` document the variable, the endpoint and the operator steps. Tests: `server/instance-access.test.ts` (parsing, the route, and Better Auth in subprocesses: refused sign-up, unaffected sign-in and password reset, boot failure on `"yes"`), `src/instance-access.test.ts`, `src/email-recovery-prompt.test.ts`. Checked in a browser against a production build with the switch on. For REQ252: call `readClosingSwitch("OMUL_GUEST_CREATION_DISABLED")` in `server/instance-access.ts`, replace the hard-wired `guestCreationOpen: true` in `resolveInstanceAccess()`, extend `instanceAccessStartupReport()`, and read `guestCreationOpen` from `useInstanceAccess()` on the client. The route, schema and loader need no change. The client default before the answer arrives is open, so REQ252 relies on the server refusal while the read is pending. `.env.example` and `docs/frontend.md` (its list of `ReasonButton` users) were outside this slice's footprint and were not changed.
