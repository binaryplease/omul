## Description

As a presenter who capped how many responses one device may give to a word cloud or an open question (REQ022, REQ026), I want that cap to hold however many submissions arrive from that device at the same moment, so that the number I set is the number the room is held to rather than a limit a double-tap can step over.

## Notes

Defect, confirmed by reproduction, **pre-existing** — not introduced by the branch that found it. Filed rather than fixed there because the review that surfaced it was scoped to the quiz slice (REQ147), and because this instance is materially less severe.

**What is wrong.** The cap in `submitVote`'s word-cloud / open-text branch is a read-modify-write, the same shape REQ147 fixed on the quiz branch: it counts the participant's existing rows, then either replaces (cap of 1), refuses (cap reached) or inserts. `votes.find` is `await`ed, so a second submission's handler runs in that gap, reads the same count, and writes too.

Reproduced against a fresh in-memory deck with `maxResponses: 1` and three concurrent submissions from one participant — all three stored:

```
words:      [{alpha, 1}, {beta, 1}, {gamma, 1}]
totalVotes: 3
```

**Why it is P2 and the quiz was P1.** This branch *replaces* on the participant's next submission, so the extras collapse the moment that device answers again — and on a cap-of-1 slide the participant's own client will do exactly that on their next edit. A quiz permanently refuses that next submission, so its duplicates were unreachable and permanent. Here the room's word cloud is wrong until somebody answers again, which is a real defect and a recoverable one.

The `allowResponseVotes` duplicate fold (REQ025) sits in the same branch and has the same gap: two participants typing the same text at once can both be stored as fresh responses rather than one becoming an upvote on the other.

**Scope.** Close the gap the way REQ147 did — run the cap's check-and-write through `server/keyed-lock.ts`, keyed `presentationId:slideId:participantId`. The primitive and the precedent already exist; this is applying them. Worth deciding at the same time whether the remaining single-row branches (ranking, 100 Points, Guess the Number, Pin on Image, single-select multiple choice, and the per-statement scale and grid branches) should be queued on the same key, since every one of them reaches the same gap and relies on the next submission to tidy up after it.

Out of scope: a store-level unique index. `votes` is one collection shared by every slide type, and the rows a word cloud legitimately writes several of are the rows a quiz may write only one of, so no single uniqueness constraint fits the table.

## Updates

- 2026-08-07 — Filed from the review of the quiz slice, which confirmed the same race here (cap of 1, three concurrent submissions, three rows stored) and left it alone: pre-existing, and self-correcting on the participant's next submission in a way the quiz instance was not. REQ147 fixed the quiz branch and left `server/keyed-lock.ts` in place for this one to use.
- 2026-08-14 — Fixed by running every check-and-write in the vote path through server/keyed-lock.ts. The word-cloud / open-text cap (REQ022/REQ026) queues on presentationId:slideId:participantId; the allowResponseVotes duplicate fold (REQ025) queues on presentationId:slideId, because "has anybody already said this?" reads the whole slide and a per-participant key would leave it as raced as it was found — so a slide whose fold is on takes the wider key (which covers its cap too) and every other one, the word cloud above all, keeps the narrow one. Decision on the remaining single-row branches: queued, not left. Ranking, 100 Points, Guess the Number, Pin on Image, single-select and capped multi-select choice, a form, the per-statement scale and grid rows and the default single-statement scale all now go through one storeSingleRowVote helper on the same per-participant key (plus statementId where the row is per statement, so one device placing two grid items at once is not queued behind itself). The "replaces on the next submission" argument that made this P2 rather than P1 only holds if that next submission comes, and on a guess, a pin or a ranking somebody has already answered it does not — the room's distribution counts one person twice until the deck ends. The queue costs a turn per participant per slide and the copies of the read-modify-write it replaced were nine statements of one rule. voteOnResponse's upvote toggle was queued too (per participant per response): the same shape, and unlike the rest nothing later collapses the two rows a double-tap left. Broadcasts stay outside every critical section, per REQ147. Regression tests in server/vote-races.integration.test.ts (18 tests), 14 of which reproduce a race and were each confirmed failing against the unfixed service; the other 4 guard the fix against over-serializing (a room of 12 all get their capped response) and over-folding (distinct answers stay distinct). Full suite 1958 pass / 0 fail, mise run check green. Also verified over HTTP: cap of 1 with three concurrent submissions reads totalVotes 1, and three participants typing the same words at once read one response with 2 upvotes. Not done: a store-level unique index (ruled out by the requirement), REQ150's broadcast coalescing, and the window where a presenter toggles allowResponseVotes mid-session and submissions move between the two keys — covering that would mean serializing every word cloud in the product.
- 2026-08-14 — Review fix pass (NST9150). Two findings fixed. (1) Major: storeSingleRowVote omitted statementId from its lookup when there was none, so on a multi-statement scale — where the request schema allows a statement-less vote and the default single-row branch then handles it — the find matched every row the participant held on the slide, and the new collapse loop deleted all but the first. A participant who had rated three statements was left holding one, and the per-statement distribution lost two data points with no way back; the pre-refactor code overwrote one value but never removed anything, so the refactor had turned a malformed-request bug into data loss. statementId is now matched explicitly and always, including as null: stored rows default it to null (ADR-0029) and binp-docstore compiles a null operand to IS NULL, so the lookup matches exactly the rows the key covers. (2) Minor: the duplicate fold's upvote insert and voteOnResponse's toggle wrote the same responseVotes row under different keys, so one participant folding a duplicate and tapping upvote in the same tick could still leave two rows. The fold now takes the upvote key for that insert, nested inside its own slide-wide turn — safe because the order is only ever fold key then upvote key, and nothing holding the upvote key reaches for the fold's. Also typed the helper's payload as a two-member union so the scale and grid call sites cannot pass statementId without skip. Both fixes have regression tests in server/vote-races.integration.test.ts, each confirmed failing against the parent commit (e21c473): the statement-less vote overwrote st1 from 5 to 1, and the fold-plus-tap left 2 upvote rows. Suite now 1960 pass / 0 fail, mise run check exit 0. Disclosed and not fixed: an open-text slide with allowResponseVotes on queues the whole room on one key and each turn rescans every row on the slide, so the cost of the fold is quadratic in the number of responses. The key is right — the invariant is genuinely slide-wide — but the cost compounds with the per-answer broadcast, and it belongs with REQ150 rather than here.
