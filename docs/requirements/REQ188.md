## Description

As the operator of a production omul, I want to be able to require a verified email address before an account is signed in, so that an account on my instance proves it controls the address it was created with before it can present, own decks or mint API keys.

## Notes

Raised for production hardening, **internal**. This touches authentication: today an address is never proven before it is used.

**Current behaviour.** Email verification is soft and hard-wired that way: `server/accounts.ts:174` sets `emailAndPassword.requireEmailVerification: false`, with the reasoning in the comment at `server/accounts.ts:166-173` (local dev only logs the link; a mistyped address would strand the user). Better Auth's default `autoSignIn` (`server/accounts.ts:145`) issues a session on sign-up, so a fresh account can use every feature at once; the only consequence of not verifying is the banner in `src/auth.tsx:700`. No environment variable changes this, so a deployment cannot enforce verification without a source edit and a rebuild.

**Desired outcome.** A deployment can be configured so that an account whose email address is unverified cannot obtain a session by signing up or signing in, while a deployment that does not opt in behaves exactly as today.

**Done when.** With enforcement on, signing up and signing in with an unverified address yield no session and the account can sign in once its verification link is followed; with enforcement off, the current soft flow is unchanged — both pinned by tests, with the gates in `AGENTS.md` (`mise run test`, `mise run check`) green and the setting documented in `docs/deployment.md`.

**Out of scope.**
- Turning enforcement on for any particular deployment — that is the operator's rollout, tracked with the deploy configuration in the separate private infrastructure repository.
- Gating the admin surface on a verified address, which holds whether or not enforcement is on: REQ189.

**Note.** Sessions and personal API keys issued to an account before enforcement was switched on are not touched by this record and stay valid until they expire or are revoked. A later record would have to decide whether enforcement also retires those. Enforcement is only usable where mail actually leaves the server (`SEND_EMAILS` and the Brevo settings in `docs/deployment.md`); a deployment in log mode would lock every new account out.
