## Description

As a presenter on the presenter screen (`/present/<id>`), I want to switch to a presenting view that shows the room only the slide — no top bar, no slide rail, no panels — and to switch back just as easily, so that I can put the deck on a projector or a second screen cleanly while still paging, revealing, blanking and showing the QR code without leaving that view.

## Notes

**Why this record exists.** A presenter has no way to show a room only the slide. The presenter screen is both the presenter's console and the view the room is shown (REQ191: there is no separate projector route), and it always draws the top bar (`src/pages/PresenterPage.tsx:1341`), the slide-navigation rail on the left (`:1682-1697`), any open panel (`:1758` onward) and, below 640px, the bottom dock (REQ199). Nothing turns any of them off. Browser full screen (F11) only removes the browser's own chrome, so the bar and the rail still fill the projector.

**What exists to build on.**
- Paging keys are handled in one window `keydown` listener (`handleKeyDown`, `:767-841`): ArrowRight/ArrowDown/Space and ArrowLeft/ArrowUp, for an editor of a live deck only. Skipped slides are stepped over (REQ110).
- Paging is one `slidePaging` descriptor (REQ199, ADR-0027) read by the in-slide row `slideNavigation` (`:1007-1040`) and the phone dock.
- A second browser that opens the same `/present/<id>` already follows the deck: slide changes, reveal and blank are broadcast (REQ109's log: "a second browser on the projector blanks too"). REQ199 also uses this: a phone acts as the remote while a laptop drives the projector.
- Blank (REQ109) is an early return (`:1065-1100`) that draws only controls on a curtain.
- The room-sized QR dialog (REQ191) closes on Esc and on every paging key, without paging.
- The slide's own live controls are drawn inside `PresenterSlideView` when `controls.canControl` is set. These are reveal, participation open or closed (REQ111), timer restart, countdown run (REQ107), the quiz audio cue (REQ058) and answer moderation (REQ027).

**Options weighed (UI/UX concept stage, 2026-10-27).**
- *Browser full screen alone, documented.* Rejected: the bar, the rail and the panels stay on the projector, so the reported problem stays.
- *A separate projector route* (for example `/screen/<id>`), opened in its own window. Rejected for now:
  - it is a second surface to keep in step with the presenter screen, the argument REQ199 already made against a separate remote route;
  - it needs its own decision on who may open it;
  - it does nothing for a presenter with one screen.
- *A presenting view on the same route* (chosen):
  - one state of the page that it already draws, with the same data, the same keyboard listener and the same disabled reasons;
  - it serves one screen, a mirrored projector, an extended second screen (a second window opened straight into the view) and a phone used as a remote (REQ199).

**Design — build exactly this.**

*Entering.* There are three ways in, and all three enter the same view:
1. **The Present control.** It is the second item of the room console's Screen group, after Blank, built as a `BAR_GROUP_ITEM`. It shows the lucide `Presentation` icon at 16, with the visible label "Present" from `sm`. Its `aria-label` and `title` are "Present — show only the slide, full screen (F)". It is not a toggle and has no `aria-pressed`, because the control is not drawn while the view is on. Below 640px the dock stays exactly as REQ199 left it. "Present" is instead the first row of the More menu, a row in REQ199's leading section, with the same icon and label.
2. **The `F` key.** It enters when pressed with no modifier, while focus is not in an `input`, `textarea`, `select` or `contenteditable`, and while no dialog or menu is open. Pressed in the view, `F` leaves it.
3. **The address.** `/present/<id>#presenting` opens the page in the presenting view. Entering by any route writes `#presenting` with `history.replaceState`, so no history entry is pushed and Back does not toggle the view. Leaving removes it. A reload therefore stays in the view. Check that `routeForLocation` (`src/router.ts:72`) still resolves the present route with this hash.

The view is open to every viewer of `/present/<id>`, an editor or a view-only viewer alike. A view-only viewer's machine on the projector can then simply follow the deck.

*Full screen.* Entering by the control or by `F` is a user gesture. It also calls `document.documentElement.requestFullscreen()` when `document.fullscreenEnabled` is true. Use the document element, so that the portaled menus, the QR dialog and the toasts stay visible.
- If full screen is unavailable (an iPhone) or refused, the presenting view still applies.
- Entering by the address cannot request full screen, because there is no gesture. The control layer then offers a **Full screen** button (lucide `Maximize`), drawn only while `document.fullscreenEnabled` is true and `document.fullscreenElement` is null.

*Leaving.* There are four ways out:
- Esc;
- `F`;
- the control layer's Leave button;
- leaving browser full screen by any route. A `fullscreenchange` event that ends a full screen this view requested also leaves the view, so a browser that consumes Esc to exit full screen still leaves in one press.

An open dialog or menu takes Esc first; the QR dialog closes, as REQ191 says. Leaving calls `document.exitFullscreen()` only when this view requested the full screen. A full screen the user started themselves (F11) is left alone. Leaving restores the presenter screen exactly as it was, including which panels were open and where focus was: back on the control that entered, or on the More trigger below 640px.

*What the room sees in the view.*
- **The slide**, centred in the full viewport (`100dvh`). This includes its appearance and background (REQ087), the reaction stream (REQ077) and its results, all drawn by the same components and with the same width rule as today (`presenterSlideWidthClass`). Nothing is enlarged beyond today's rule; scaling for large rooms is not part of this record.
- **A join line** at the top edge. The join code is the room's standing invitation whenever the deck is on screen (REQ191), so the view keeps it, made quiet:
  - one line, `text-sm`, `text-text-muted`, centred, with no border and no button chrome;
  - it reads "Join at <host>", as the Door's label does from `2xl` (REQ191), followed by the code in `font-mono font-bold text-accent-text tracking-widest`;
  - it is not interactive;
  - it is the deck's text addressed to the room, so its words follow the deck's language once REQ248's slice 3 (presenter-room) is built.
- **Nothing else** while the control layer is down. There is no top bar, no rail, no panels, no dock, no in-slide paging row and no cursor (`cursor: none` on the view while the layer is down).

*The control layer.* The presenter's controls come back only while the layer is up.

- **Comes up on:**
  - a pointer move anywhere in the view;
  - a tap on the slide (a tap while the layer is up takes it down);
  - a `Tab` keypress. The layer comes up before focus moves, so focus lands in it.
- **Paging keys do not raise it.** A clicker or arrow key changes the slide and leaves the screen clean.
- **Goes down** 3 seconds after the last pointer activity. It stays up while the pointer is over it, while focus is inside it, and while a menu or dialog opened from it is open. With `prefers-reduced-motion: reduce` it appears and disappears without the fade; otherwise the fade lasts 150ms.
- **The strip.** One floating pill centred at the bottom edge, `bottom-4` with `env(safe-area-inset-bottom)` added. It uses the console's `BAR_GROUP` look with `BAR_GROUP_ITEM`s at REQ192's height for the width (44px below 640px, 40px from 640 to 1279px, 38px from 1280px). In this order:
  1. **Previous** · the position "4 / 12" (`font-mono tabular-nums`) · **Next**. They read the existing `slidePaging` descriptor. Their names, their disabled-with-reason state (a view-only viewer, a deck that is not live, the first or last slide) and the stepping over of skipped slides are all as in the dock.
  2. A divider, then **Blank**. Same handler, `aria-pressed`, `Monitor`/`MonitorOff` icons and disabled reason as the console's Blank.
  3. **QR**. Opens the room-sized QR dialog (REQ191), which closes as it does today.
  4. **Full screen**, only under the conditions above.
  5. A divider, then **Leave**. lucide `Minimize2` with the visible label "Exit" from `sm`, and `aria-label`/`title` "Leave presenting view (Esc)".
- **The slide's own controls** (reveal, participation, timer restart, countdown run, audio cue, answer moderation):
  - they stay where `PresenterSlideView` draws them, and work as today;
  - they are shown only while the layer is up, using `visibility` and opacity, never by removing them, so the slide does not reflow when the layer goes;
  - this keeps them reachable without moving them into the strip;
  - with the layer down, the room sees the slide without them.
- **The strip's role.** It is a `role="toolbar"` with `aria-label="Presenting controls"`, and keeps its controls in a normal Tab order.

*Blanked while presenting.*
- With Blank on (REQ109), the view draws the deck theme's background and nothing else: no curtain text, no join line.
- When the layer comes up, the strip shows Blank pressed. The curtain's controls (participation, audio cue) appear centred, under the same layer rule.
- Paging still works behind the blank, as REQ109 intends.

*Keys while presenting.* Every existing paging key and its guard (an editor of a live deck) keep working. Beyond them:
- **`PageDown` and `PageUp`** page forward and back, as ArrowRight and ArrowLeft do. Presentation clickers send these keys. Add them to the presenter screen in both views and to the QR dialog's list of keys that close it (REQ191).
- **`B`** toggles Blank, under the same no-modifier and not-in-a-field guard as `F`. It is subject to Blank's own disabled conditions.
- **`F`** and **Esc**, as above.

*A second screen or a projector.*
- **One screen or a mirrored projector.** Press Present or `F`. The laptop shows the room the slide. Page with the arrow keys or a clicker, and move the pointer to bring the controls up.
- **An extended second screen.** The Deck menu (the More menu below 640px, REQ199) gains the row **"Open presenting window"** (lucide `MonitorUp`), enabled for every viewer.
  - It calls `window.open("/present/<id>#presenting", "omul-presenting-<id>")`. The named target means a second use brings back the window already open rather than opening another.
  - The new window opens in the presenting view and shows a **start card** centred over the slide. It reads "Drag this window to the projector, then press F or choose Full screen", with a **Full screen** button (the gesture) and a **Dismiss** button.
  - The card goes away on entering full screen, on Dismiss, or on the first paging key. It is shown whenever the view starts from the address without full screen, which includes a reload.
  - The original window stays the full presenter screen: panels, notes, Q&A. Both windows follow each other through the existing broadcast. A paging key pressed in either window pages the deck.
- **A phone as the remote** (REQ199). The projector machine is in the presenting view, and the phone holds the presenter screen with its dock. This already works through the broadcast and needs nothing new.
- **Not used.** The Window Management API (placing a window on a chosen screen) is Chromium-only and needs a permission prompt. It is left out.

*The top bar's constraints hold* (REQ190, REQ192, REQ199):
- Present is one more `BAR_GROUP_ITEM` in the Screen group from 640px. Below 640px it is a More-menu row, and the dock does not change.
- At 360, 768, 1280 and 1536px wide, in draft, live and ended, as editor and as view-only, the bar still has no horizontal overflow. Back, the title and the lifecycle button (or View only) stay visible and uncovered. Every bordered or filled control keeps one rendered height per width.
- The title stays the only element that gives way, and at 1280px it truncates sooner by the width of the labelled Present item.
- Every control the bar offers today stays where it is.

*Discoverability.* The hint under the slide that reads "(arrow keys)" (`:1024-1026`) becomes "(arrow keys · F to present)".

**Done when.** In Chromium and in WebKit, at 360, 768, 1280 and 1536px wide:
1. On a live deck as its editor, Present and `F` each enter the view. The top bar, rail, panels, dock and in-slide paging row are gone, and the slide and the join line are on screen. In Chromium on a desktop, `document.fullscreenElement` is set after entering by the control or `F`.
2. In the view with the layer down, a screenshot shows only the slide, its background and reactions, and the join line. There is no control and no cursor.
3. A pointer move brings up the strip with Previous, position, Next, Blank, QR and Exit. Three seconds without pointer activity, with the pointer off the strip, take it down. `Tab` brings it up and focuses its first enabled control.
4. With the layer down, ArrowRight, Space and PageDown move to the next non-skipped slide, and ArrowLeft and PageUp move back. The strip stays down.
5. `B` blanks and unblanks. While blanked, the view shows only the theme background.
6. Esc, `F`, Exit, and leaving browser full screen each return to the presenter screen. Panels that were open before are open again, and the view does not stay full screen when it requested it.
7. As a view-only viewer, the view opens. The strip's paging and Blank are disabled with their reasons, and QR and Exit work.
8. "Open presenting window" opens a second window at `/present/<id>#presenting` showing the start card. Its Full screen button enters full screen. Paging in the first window moves the slide in the second, and paging in the second moves the first.
9. Reloading `/present/<id>#presenting` reopens the view, with the start card and a Full screen button.
10. The REQ190/REQ192/REQ199 bar checks above still pass, with Present in the Screen group from 640px and in the More menu below it.
11. `mise run check` and `mise run test` pass.

**Out of scope.**
- A separate projector route.
- Scaling slides up for large rooms.
- Presenter notes on the second screen. They stay in the console window's Notes panel.
- The Window Management API.
- Translating the view's strings, which is REQ248 slice 2 (presenter-chrome).
