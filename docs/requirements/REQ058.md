## Description

A quiz slide can play an audio track for the duration of its answer window, on the presenter surface only.

An author can hear a bundled track while choosing it in the editor. A track that loops plays through its loop point without an audible transition.

## Notes

**Open since the 2026-11-03 acceptance run.** Both points below are built and neither is closed, because each needs a listening check by ear and the automated tests hold no audio.

- **Hearing a track in the editor.** Each bundled track has a play control beside its tile, as "Three bundled tracks and Custom" below describes. Whether this meets the need has not been checked by ear. Playing from a separate control is the default chosen, because a selection then never makes unexpected sound.
- **The loop point.** The cause was the media element's restart, measured on 2026-11-03 in a headless Chromium-based browser (Brave 1.93, user agent Chrome 151) on a local production build, with no audio device. The numbers are below "Measured", and whether the result is inaudible is the open listening check.

**Measured.** The files were not the cause: decoded with ffmpeg, each is 8.000 s and its first and last samples are below 0.0002 in amplitude, so the file holds no click. Plucked notes sounds up to 0.2 ms before its end; Ticking clock and Heartbeat end in about 425 ms and 403 ms of quiet.

| What was measured, for each of the three tracks | `HTMLMediaElement.loop` | Looping buffer source |
|---|---|---|
| Extra time per loop, from comparing the signal tapped into an `AudioWorklet` with itself one track length later (27 comparisons per track over 36 s) | 10.875 ms, with a few readings of 5 to 10.6 ms early in the recording of Heartbeat and Plucked notes | 0 ms, every comparison |
| Longest silence in Plucked notes, below 0.0002 in amplitude | 11 ms, at each restart | 0.15 ms |
| Time between the element's `seeking` events with no tap attached, on a track of 8000 ms | 8063 ms once settled | no restart happens |

The tapped and untapped readings of the element differ by about 52 ms, and the reason was not investigated. The tap replaces the element's output path with a Web Audio graph, so the untapped 63 ms is the reading of the path a presenter's screen uses. Neither reading was taken on a real audio device.

Defaults this requirement left open, as built:

- **The track is an authored address, never an upload.** A quiz slide carries `quizAudioUrl`, `""` by default. It is held to the authored-URL rule every slide media URL meets: stored as typed, capped at `SLIDE_MEDIA_URL_MAX_LENGTH` (2048) on create and PATCH, and resolved at one read site, `quizAudioCueFor()` in `server/schemas.ts` — `browserSafeAssetUrl`, so `http(s)` or a root-relative path, refused rather than repaired, and inert on a slide that is no longer a quiz. Nothing is uploaded.
- **Three bundled tracks and Custom.** The editor's Audio cue row offers `QUIZ_AUDIO_PRESETS` in `src/components/QuizAudioCue.tsx` ("Ticking clock", "Heartbeat", "Plucked notes") and "Custom". Choosing a track stores its root-relative path, such as `/app/audio/quiz-cue-1.mp3`, as an ordinary `quizAudioUrl` value, so the schema, the resolver and `withAudienceSlides()` did not change. A stored value equal to a preset's path reads as that preset; any other non-empty value reads as Custom with its address in the field, so a deck authored with a URL keeps working. The URL field is drawn only under Custom. "Remove audio cue" empties the value.
- **Hearing a track in the editor.** Each bundled track has its own play control beside its tile, a separate button drawn by `QuizAudioPreviewButton`: selecting a track stays silent and pressing play does not select it. `useQuizAudioPreview()` in `src/components/QuizAudioCue.tsx` plays one track at a time through one media element, once, and then returns to idle. It stops on a second press, on playing another track, on "Done", on leaving the slide and on unmount, because the last three all unmount the row. Selecting a tile while a preview plays leaves the preview playing. A track that cannot be loaded draws its reason in words at the control and offers play again. The preview takes no slide, so it writes nothing to the deck. A "Custom" address has no preview. It adds no sound to the presenter page, the dry-run preview or any participant surface.
- **The track files can be replaced without a code change.** The files are `public/audio/quiz-cue-{1,2,3}.mp3`, each at most 1 MiB, and a path names a slot and no track content, so swapping the file at that path is enough. Each current track is original synthesis made with ffmpeg, which starts and ends at silence so the loop point makes no click. The whole decoded file goes round, so a replacement has to be cut to loop on its own length. `public/licenses/quiz-audio-tracks.txt` names each track with its source and license and records the commands that rebuild it, and `NOTICE.md` section 4 states their position. A replacement updates that license file, and a third-party replacement also needs its own entry in `NOTICE.md`.
- **A media element's seek relies on Bun's range answer.** That covers a Custom address on this server; a bundled cue is read whole by `fetch` and does not seek. The server answers a `GET` for a track with `206` through Bun's handling of a `Response` holding a `Bun.file`; `server/routes/static.ts` adds the `audio/mpeg` type, and states the range on a `HEAD` itself because Bun and Elysia ignore it there.
- **Two players, chosen by the address.** `quizAudioCueLoopPath()` sends a bundled track to `createBufferCuePlayer()`, which fetches and decodes the file once and plays it as an `AudioBufferSourceNode` with `loop` set, through one `AudioContext` for the life of the screen. Any other address goes to `createElementCuePlayer()`, one media element with `loop` set, because it may be on another host that sends no CORS headers and `fetch` cannot read such a file for decoding. A Custom address therefore keeps the restart gap measured above. Output level did not change with the player: Plucked notes peaks at 0.3311 on both. Chromium's `decodeAudioData` returned exactly 384000 frames at 48 kHz for each track, so MP3 encoder delay and padding are not in the loop. Firefox and Safari were not measured; a decoder that kept the padding would put it in the loop as silence.
- **The application sends no Content-Security-Policy**, so the app's own answers restrict neither player. An operator's proxy that adds one has to allow the same origin in `connect-src` for the bundled tracks' `fetch`, and in `media-src` for the preview and any Custom address. A policy that refuses the `fetch` reads "Audio cue unavailable"; this was checked by adding a policy to a local production build's page. `default-src 'self'` with `connect-src 'self'` plays the track.
- **Off by default.** No track is selected by default, and a quiz with no track behaves exactly as before; a deck stored before the field existed reads back with it empty.
- **Presenter-only on the wire.** `withAudienceSlides()` empties the field for every caller the deck is not authored for — anyone but its owner, the holder of its edit token and the accounts it is shared with (a `view` or `comment` collaborator reads it, as they read the notes) — so the join payload whoever asks, the public list, the `slide.changed` broadcast and a deck fetch without standing never carry it, and a participant's device is never handed the address. Writing it is the deck PATCH's ordinary gate (owner, edit token or `edit` collaborator).
- **When it plays** (`src/components/QuizAudioCue.tsx`): from the moment the presenter's screen opens the question until its window closes — the countdown reaching zero (the deadline the countdown shows, not the boundary's submission grace), the presenter closing the slide to submissions (REQ111), navigating away, or ending the deck. It loops for a window longer than the track and keeps the window's time: whenever it starts — the question opening, reopened to submissions, paged back to, or the page reloaded mid-question — it starts where the window has got to, so a question reopened with Restart timer starts it from the top. A results reveal does not stop it, because a reveal does not close the question; neither does blanking the screen (REQ109), which stops nothing. An audience-paced deck has no shared window, so its cues never play.
- **Where it plays.** Only the presenter page, and only on a screen that can run the deck: a view-only spectator is told the cue plays on the presenter's screen, the dry-run preview plays nothing, and no participant surface imports the module. Every presenter screen that can run the deck plays it, so a second one is muted from its own switch. `mise run check` guards both halves: nothing but that module and the editor reads the field or resolves the cue, and nothing outside that module and the presenter page makes an audio element or an audio context. (A video slide's own player is the slide's content, not a cue, and is outside both.)
- **Mute** sits beside the question's countdown (and on the blanked screen), per question and per screen, for as long as the page is open. A muted cue keeps running silently, so unmuting picks it up where the window has got to: a bundled track's source runs on with its gain at 0, and a Custom address's element runs on muted.
- **Browser autoplay rules** are surfaced, not fought: before anyone has clicked on the presenter's page a browser refuses sound, and the switch then reads "Play audio cue" and starts it on the click, where the window has got to by then. A browser leaves a held-back `AudioContext`'s `resume()` pending, so the buffer player counts a context still not running 300 ms after its track is decoded as held back, and a source starts only on a running context. A context that stops running under a track reads the same way and rejoins the window when it runs again. A track that cannot be loaded reads "Audio cue unavailable", disabled with its reason, and is asked for again the next time the question's window opens — a network that dropped for a moment does not silence the rest of the deck.

**Known limits and follow-up, from the pre-merge review (2026-10-25).** None blocks this record; each is recorded so it is not rediscovered.

- **Part of the cue's timing has no automated test.** `createBufferCuePlayer()` takes its context and its file read as arguments, so `bun test` holds its flows with a fake context: the loop and the starting position, the stop, the mute, a held-back context, a failed track and its second request, and the release. These behave as specified in a browser, but nothing in `bun test` holds them: the stop when the window runs out on its own (the effect in `useQuizAudioCue` that re-arms its timer from `cueWindow.closesAt`), everything in `createElementCuePlayer()` (the release of the track, `load()` when `error` is set, an older `play()` whose outcome arrives after a newer one) and everything in `useQuizAudioPreview()`. Follow-up: DOM tests for these timer and media effects.

## Updates

- 2026-10-21 — Quiz audio cue shipped. A quiz slide carries quizAudioUrl (default ""), an authored address held to the slide media URL rule: capped at 2048 on create/PATCH and resolved through quizAudioCueFor() (browserSafeAssetUrl, refused rather than repaired). withAudienceSlides() empties it for every caller who cannot edit the deck, so the join payload, public list, slide.changed broadcast and anonymous deck fetch never carry it. The editor's Scoring & timing group authors it (Audio cue row, warning for an unplayable address or an audience-paced deck, Remove). The presenter page alone plays it (src/components/QuizAudioCue.tsx): from the question opening until the countdown reaches zero, the presenter closes submissions, navigates away or ends the deck; looping, restarted by Restart timer, with a per-question mute beside the countdown and on the blanked screen, and the browser's autoplay refusal surfaced as Play audio cue. Two new check guards keep raw reads of the field and any sound outside that module and the presenter page out. Tests: server/quiz-audio.schemas.test.ts, server/quiz-audio.integration.test.ts (incl. 401/403 refusals and a genuinely key-less pre-REQ058 row), src/components/QuizAudioCue.test.ts; verified end to end in a browser against a local track.
- 2026-10-21 — Hardened after an independent review. The cue now keeps the window's time: whenever it starts (question opening, reopened submissions, paging back, a reload mid-question) it plays from (elapsed since the window opened) mod the track's length, via the pure quizAudioCueOffsetSeconds(), so Restart timer still starts it from the top and returning no longer depends on which slides were passed through. A track that failed to load is reloaded the next time its window opens instead of staying unavailable until a page reload, and the unavailable label says so. An unreadable opening stamp is silent for untimed questions too. Correction to the entry above: the second guard does not keep out "any sound" - it keeps audio elements and audio contexts (new Audio, window.Audio, <audio>, createElement("audio"), (webkit)AudioContext) out of every module but the cue's own and the presenter page; a video slide's player is outside it. The first guard now also catches bracket access, one-line destructuring and quizAudioCueFor() calls outside the cue module and the editor.
