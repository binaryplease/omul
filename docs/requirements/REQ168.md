## Description

The built-in `signal` deck theme — the one a deck that never chose a theme is drawn in — carries the same neutral-base blue-accent values the application chrome took in REQ166, in both colour schemes, in place of the tangerine accent and the warm-slate and slate neutrals it holds today. Its standing rule is unchanged and now points at the moved values: this theme's palette is `src/index.css`'s, to the digit, role for role — Ground / Card / Raised / Hairline / Text / Muted / Dim / Accent per scheme, as the table in REQ166 fixes them — so elevation inside a light-scheme slide runs *toward white* the way the chrome's now does, the wash painted behind a slide follows the new accent rather than the retired one, and the swatch and the one-line description the editor's theme picker shows describe the palette the theme actually has. What does not move: it stays named `Signal`, stays set in Sora, stays the theme an absent or unknown theme id resolves to, and the tangerine is retired rather than re-offered under another name. Done when: a deck that never chose a theme renders with no surface resolving to `#ff6b35` or the warm-slate neutrals in either scheme, accent-coloured text inside a deck scope measures at least 4.5:1 against the surface behind it in both schemes, and the repo's gate and test task (both named in `AGENTS.md`) stay green.

## Notes

Current behaviour: `src/components/DeckTheme.tsx:177-223` is the whole of it. The `signal` entry of `DECK_THEME_APPEARANCE` holds `--color-accent: #ff6b35` with its `-hover`, `-glow` and `-dim` companions and `--color-poll-1: #ff6b35` in both schemes, the warm-slate dark ramp `#0a0a0b` / `#111114` / `#1a1a1f` under text `#e8e6e3`, the slate light ramp `#ffffff` / `#f1f5f9` / `#e2e8f0` whose elevation runs *darker* as it rises, an accent-tinted radial wash per scheme, the swatch `{ canvas: "#111114", accent: "#ff6b35" }` and the description "The house look — electric tangerine on warm slate, set in Sora." Those are the values `src/index.css` carried before REQ166 moved it. `DEFAULT_DECK_THEME` is `signal` (`server/schemas.ts:4517`) and `builtInDeckThemeIdFor()` resolves an absent or unknown id to it (`server/schemas.ts:4634-4639`), so this palette is what an unthemed deck wears on the presenter's screen, on the projector, on every participant's phone, and on the join screen before any deck is known (`src/pages/JoinPage.tsx:150-162`). **A custom-but-unauthored id reaches the same accent by a different road, and the difference matters to anything that keys off the catalog entry:** `deckThemeAppearance()` asks `deckBrandFor()` first, which answers a brand for *any* deck whose id is `custom` — including one where every field is empty — so such a deck is never resolved through `builtInDeckThemeIdFor()` at all. It gets the house accent and canvas as `deckBrandAppearance()`'s fallback for an unauthored colour (`src/components/DeckTheme.tsx:674-681`), in a freshly built appearance that is not the catalog object. The deck-settings brand-colour controls hold three of these values a second time, by hand, as the placeholders that both paint the collapsed swatch and seed the native picker: `#ff6b35`, `#111114` and `#e8e6e3` at `src/pages/CreatePage.tsx:1114,1121,1128`.

**The invariant this theme was written under is retired by this requirement.** The comment above the entry states it (`src/components/DeckTheme.tsx:174-176`): *a deck that never chose a theme must look exactly as it looked before themes existed*. Preserving it is what let REQ166 re-skin the chrome around an untouched deck canvas, and it cannot survive this change — after it, decks built before the decision render differently for their audiences. That holds for two populations the stored data does not distinguish: a deck that never named a theme, and a deck that named `signal` deliberately because it wanted the orange. Both carry the same id, and both re-skin. That consequence is the decision, not a side effect of it.

Contrast, and why the done-when names it: `.deck-theme` (`src/index.css:215-228`) re-points `--color-accent-text` and `--color-accent-text-hover` at the deck's own `--color-accent`, so accent-coloured words inside any deck scope are drawn in the raw accent rather than through the per-scheme text seam REQ157 built. That is safe with the tangerine, which measures 6.65:1 as text on this theme's dark surface. It is not safe with the blue: measured WCAG 2.1, the dark accent reads 3.61:1 against Card and 3.31:1 against Raised — clear of the 3:1 a graphic needs, under the 4.5:1 text needs. Light is unaffected at 6.71:1 on Card and 6.11:1 on Raised. So this requirement carries the equivalent of REQ166's measured obligation, over the surfaces that draw the accent as words inside a deck scope: the join code, links in slide text, the quiz timer, result and leaderboard metadata, and the chips. Icons and bars keep the raw accent at the graphics floor, as they do in the chrome.

Not in scope, and why: the other built-in themes. `pulse`, `ember`, `editorial` and the rest of `DECK_THEME_APPEARANCE` are palettes an organizer picks *instead of* the house look, and a theme somebody chose on purpose is not a surface that should change under them — the identity is carried by what a deck gets when it chooses nothing. Authored deck brands (`deckBrandAppearance()`) stay the organizer's colours for the same reason. Also not here: the product's fallback mark on participant surfaces, which is a drawn mark rather than a palette value and would not be caught by this requirement's done-when — it is REQ169.
