## Description

As somebody who arrives at the app through a link whose query carries parameters the deployment's operator listed, I want those parameters to stay in the address bar, unchanged, while I move around the app, so that every request the app makes while they are there — the sign-up request above all — carries them in its same-origin `Referer`.

As an operator, I choose which parameters those are; an instance that chooses none keeps none.

## Notes

**What happened before (defect).** The parameters were lost on the first in-app navigation: `navigate()` in `src/router.ts` pushed `pathForRoute(route)` with no query, and the URL clean-ups in `src/App.tsx` (the `#share=` and `#link=` consumers) replaced the URL with the bare path.

**As built.**

- **The list is the operator's.** `OMUL_KEPT_QUERY_PARAMS` (`server/kept-query-params.ts`) is a comma-separated list of parameter names (`ref`) and name prefixes ending in `*` (`campaign_*`). **Unset is empty, and empty keeps nothing** — the behaviour before this requirement. An entry outside `A–Z a–z 0–9 _ . -` plus one trailing `*`, a bare `*`, or an entry that would keep an auth landing's `mode`, `token` or `error` (`t*` included) is a fatal startup error naming the variable; the boot log prints the list or that it is unset (`[query] …`). No value ships with this repository: which parameters to keep depends on what reads the `Referer` at the deployment's edge.
- **It reaches the client inside the page, not over `/api`.** `server/routes/static.ts` writes it into every copy of `index.html` it serves — the app's pages and `/app/index.html` alike — as `<meta name="omul-kept-query-params" content="…">` at the end of `<head>`; an empty list writes nothing, so the page is served byte for byte as built. A fetch would not do: `navigate()` can run before any response, and a parameter dropped by that first navigation is gone. In dev, a serve-only Vite plugin (`vite.config.ts`) writes the same tag from the shell or `.env`; the build never writes it.
- `src/router.ts` reads the tag (`keptQueryParamsFromPage`) and filters with `keepsQueryParam`, which refuses `mode`/`token`/`error` whatever the list says. `passThroughSearch` (the kept `?name=value` segments of a query string, or `""`) and `urlForRoute` (the route's path, then that query, then the route's hash, so the `#create` / `#join` dialogs keep it too) take the list as a parameter, defaulting to the page's. `navigate()` writes `urlForRoute(route, window.location.search)`.
- Segments are kept raw, in their order, never decoded and re-encoded, so values leave exactly as they came (`%20` stays `%20`, `+` stays `+`).
- The two `replaceState` clean-ups in `src/App.tsx` keep the kept query and still drop the rest of it, as before.
- `clearLandingParamsFromUrl` in `src/auth.tsx` keeps every parameter except `LANDING_QUERY_PARAMS` (`mode`/`token`/`error`, the same constant the startup check refuses), filtering the raw segments instead of round-tripping through `URLSearchParams`, which re-encoded every value it left.
- The full page load after an account is deleted goes to the app's home with the kept query.

**Constraints.** The address bar is the only carrier: no cookie, no `localStorage`/`sessionStorage`, no server-side recording, no new request, no new schema field. Nothing outside the operator's list is carried by this mechanism, and the code names no parameter of its own beyond the auth landing's three it refuses. The app sets no `Referrer-Policy` of its own, so the browser default (`strict-origin-when-cross-origin`) sends the full URL on same-origin requests; this requirement does not set or loosen one.

**Done when.** `src/router.test.ts` asserts that, with a configured list in the page, navigating between routes (including `#create` / `#join`) keeps exactly the listed parameters, that a page without the tag keeps none, and that a URL without them gains no query; `server/kept-query-params.test.ts` asserts the parsing, the refusals and the tag; `server/app-paths.test.ts` asserts that every served copy of the page carries the tag when configured and is unchanged when not.

**Out of scope.** The links into the app from elsewhere, whatever reads the `Referer` at the edge, and the value any one deployment sets.

## Updates

- 2026-10-16 — Shipped: the list is `OMUL_KEPT_QUERY_PARAMS` (server/kept-query-params.ts), empty by default, a malformed entry or one keeping `mode`/`token`/`error` fatal at boot, written into index.html as a `<meta>` tag by server/routes/static.ts (and by a serve-only Vite plugin in dev), read by src/router.ts. navigate(), the App.tsx URL clean-ups and the auth.tsx landing clean-up (through the shared filterQuery helper) keep the listed parameters raw in the query, between path and hash; asserted in src/router.test.ts, server/kept-query-params.test.ts and server/app-paths.test.ts. Verified against a production build in a browser with `ref,campaign_*` set: `/app/?campaign_source=a%20b&mode=x&ref=news+1&other=1` → Use a Template → `/templates?campaign_source=a%20b&ref=news+1`, and Create Presentation → `/app?campaign_source=a%20b&ref=news+1#create`; unset, the same two land on `/templates` and `/app#create` with no query. OUTSIDE THIS REPOSITORY: the live deployment keeps nothing until its operator sets the variable in the deployment configuration.
