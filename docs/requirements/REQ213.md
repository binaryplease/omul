## Description

As an operator of an omul instance, I want reducing a deck's authored markdown to plain words for the PDF export to cost work linear in the length of that text, and the export route to be rate-limited per client like the other expensive routes; and I want a render to hand the thread back while it works and the render work in hand to be bounded across all callers, so that neither one caller nor several together can hold the server's single thread for seconds at a time by exporting decks.

## Notes

Defect, **internal**: raised by a security review of `main` (NST12592, finding 1, severity medium), not by a business need. It affects availability only. Nothing is disclosed, nothing is lost, and the export is correctly authorized.

**What was wrong.** `plainTextFromMarkdown` in `server/deck-pdf.ts` reduces each line of a slide's `question` and `body` through a chain of regular expressions. Two of them did work quadratic in the line: the link expression (`[label](address)`) and the bold expression (`**…**` / `__…__`). Both searched the rest of the line for their closing delimiter from *every* opening one, so a line whose openers never close cost the whole remaining line once per opener. Each field is capped (`SLIDE_TEXT_MAX_LENGTH`, REQ159), but a quadratic cost under a cap is still large, and it is paid once per field across every slide of the deck.

**Why it mattered.** Bun serves every request from one thread, so a slow export does not just make one request slow: it stalls the process. The route asks for owner-or-edit-token, and an anonymous create hands out an edit token, so the route was effectively as open as create. It was also the one expensive route without a rate limit, because REQ145 covered the account-free writes and REQ159 recorded the export throttle as a separate remedy it did not take. Measured on one machine, for a deck at the slide cap with every `question` and `body` at the field cap: the reduction took **3.8 s** of CPU and the whole export **5.2 s**.

**What closes it.**

1. *The two quadratic expressions are replaced by scanners* (`reduceLinks`, `reduceStrong` in `server/deck-pdf.ts`). Each produces exactly what its expression produced. Each is linear because of one observation:
   - **Links:** a `[` that fails passes its verdict on to every `[` before the `]` it reached. All of those reach the same `]` and fail the same way. A missing `]` or `)` ends the line's links, since no later opener could find one either.
   - **Bold:** an opener that finds no closer proves that no later opener of the same pair can find one, so each pair is searched to the end of the line at most once.

   The other expressions in the chain were checked and are linear as they stand. Three are anchored at the start of the line, and code and italic stop at their own next delimiter. Same input as above: reduction **3.8 s → 23 ms**, whole export **5.2 s → 1.5 s**, with the document model the same as before.

2. *The route is rate-limited.* `GET /api/presentations/:id/deck.pdf` runs `guardDeckPdf` (`server/rate-limit.ts`) before authorization: `DECK_PDF_RULE`, 60 per 5 minutes, one bucket per client. It is the same mechanism and the same rules as every other guard: the `OMUL_RATE_LIMITS_DISABLED` switch, `OMUL_TRUST_PROXY`, and IPv6 keyed by `/64`. Over the limit it answers `429` with `Retry-After` and `retryAfterSeconds`. The ceiling is sized so ordinary exporting never meets it: a workshop of thirty people on one wifi, each exporting both readings of their own deck inside five minutes, fits.

3. *The render yields, and render work in hand is bounded* (second round, from the security review of the first: NST12661, finding 1). With the reduction linear, a deck at every cap still costs about 1–1.7 s of render work, and in one stretch that is 1–1.7 s in which no other request is answered. Several addresses, each inside its own `DECK_PDF_RULE`, could keep that going. Two changes close it, and neither is a rate limit, so `OMUL_RATE_LIMITS_DISABLED` switches off neither:
   - **Time slices.** `renderDeckDocument` hands the thread back every `RENDER_SLICE_MS` (10 ms) between blocks, list items, table rows and pages. Measured for a deck at both caps: the longest stretch the event loop was held went from **1,339 ms to about 20–40 ms**, with the total render about the same (≈1.5–1.8 s).
   - **A global gate.** `DECK_PDF_RENDER_GATE` (`server/rate-limit.ts`) lets one render run at a time across every caller, with four more waiting first come, first served. Past that the export answers `503` at once, with `Retry-After: 5` and `retryAfterSeconds`. The gate is entered after authorization and after the deck is read, so only a render that will really happen holds a place.
   - `DECK_PDF_RULE` stays at 60 per 5 minutes. What it guards is now the share one address can take of the single render slot, not the thread: at the worst case that is a minute and a half of rendering in five.

**The claim this record once made about slide counts was wrong.** The first round's rationale said decks are "uncapped in slides". They are not: every write caps a deck at `SLIDE_LIMIT` (200) slides (REQ159). The rationale in `server/rate-limit.ts`, `server/deck-pdf.ts` and `docs/api.md` now says so.

**What stays the same.** The output. Every valid markup reduces exactly as before. Before closing, the new reduction was checked against the old one locally (not committed): 3,196,744 inputs (random texts, delimiter-dense texts, and every string of length 1–7 over the delimiter alphabet), with zero divergence.

**How it is held.**
- In `server/deck-pdf.schemas.test.ts`, a ratio test drives `buildDeckDocument` itself, not a copy of the reduction. It compares the same amount of adversarial text cut into short fields against the same amount cut into long ones. Linear work measures about 1×, quadratic work about 8×, and the test asserts under 3×. It fails against the old expressions, link and bold each on their own.
- Pinned cases cover the edge semantics of links and bold.
- `server/rate-limit.integration.test.ts` exhausts the route and expects the `429`.
- `server/deck-pdf.schemas.test.ts` renders a long deck while a 1 ms timer measures the longest stretch the thread was held, and asserts that stretch is under a quarter of the render's own length. The old render held it for nearly all of it.
- `server/deck-pdf-load.integration.test.ts` runs the real route twice. First, health checks are asked again and again while a long deck exports, and the slowest must wait under a quarter of the export. Second, more exports are fired at once than the gate holds; no more than it holds may render, the rest must answer `503` with `Retry-After`, and every refusal must arrive before the first render finishes. Both fail against the first round's code.
- `server/rate-limit.test.ts` covers the gate itself: queueing, first come first served, and that a turn given back twice frees one place.

**What this does not cover.** The XLSX export (`results.xlsx`) is still unthrottled. Its work is linear and has no markdown reduction. A deck at every cap still costs about 1.5–2 s of render work per export. The time slices stop that work from holding the thread, and the gate stops it from piling up, but neither makes it smaller. Running the render in a worker thread would take it off the request thread entirely. It was not done here, because the server ships as one bundled file and a worker needs its own entry point. The client's own link parser (`src/components/SlideText.tsx`) is a separate finding of the same review and is not touched here.
