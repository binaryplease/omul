## Description

As an operator, I want the routes that need no login — creating a presentation, resolving a join code, and the four public participant writes — to be throttled per client and to answer an over-limit call with a `429` and a retry hint, so that a scripted caller can neither fill the store with presentations nor stuff a slide's tally, while a full lecture hall answering the same question at the same moment is still served.

## Notes

Context: joining and answering never require an account — that is what makes a room work from a phone with a six-digit code. It also means there is no session, no quota and no login attached to a participant, so nothing else in the system bounds how often an anonymous caller may write. The limits are that bound.

Goal: refuse the two shapes of abuse the account-free surface actually exposes — a create loop that grows the store without limit, and a submission loop that decides a poll — and refuse them visibly, with a `Retry-After` header and a `retryAfterSeconds` field in the body, so a well-behaved client backs off instead of guessing.

Boundary: this is flood protection, not ballot integrity and not a per-human quota. Conference wifi puts hundreds of legitimate participants behind one NATted address, so every per-client ceiling is sized for a whole room bursting at once; the tighter per-`participantId` ceiling is what bounds a single client. One-vote-per-person is a separate concern and is not what this requirement asks for.

What counts as one client: an IPv4 address, or an IPv6 `/64`. A `/128` is not a client — one subscriber is routed a whole `/64` and may source from any of the 2^64 addresses in it, so keying the full address makes the per-client ceiling unreachable for exactly the scripted caller it exists to refuse, and leaves it unable to serve as the backstop behind a rotated `participantId` that the boundary above claims it is. The `::ffff:a.b.c.d` form a dual-stack socket reports IPv4 peers in is read back as the IPv4 address it is, never truncated.

Scope: six routes — `POST /api/presentations`, `GET /api/join/:code`, and the four public writes (`vote`, `response-vote`, `qa`, `qa/:questionId/upvote`). The presenter's own mutations are already gated by owner-or-edit-token, and the WebSocket carries no create, lookup or vote, so neither is throttled here.

Posture: the limits are on unless an operator explicitly turns them off, and `X-Forwarded-For` is distrusted unless an operator explicitly says how many proxy hops sit in front — a mis-set or mistyped variable must leave the protection standing rather than quietly remove it or hand a caller a fresh bucket per request.

The cost of that distrust default, and what is owed for it: behind a reverse proxy — the topology this project actually deploys under — distrusting the header leaves the limits standing but collapses every visitor on the internet into the proxy's one bucket, and from inside the process that is indistinguishable from the correct configuration for a directly-exposed server. The default stays as it is, because believing the header on a directly-exposed server is the worse of the two failures. What the safe-but-ambiguous default owes in exchange is that the deployment be made to say which case it is in, rather than discover it in a live session: the posture is printed on every boot, and a request arriving with `X-Forwarded-For` while no hop is trusted is warned about once. A notice and not a fatal error, because `0` hops is the correct and required value for a directly-exposed server and refusing to start on it would break the deployment it is right for.
