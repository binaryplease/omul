## Description

As a presenter, I want deleting a presentation to also erase every record the room produced under it — the votes, the response upvotes, the Q&A questions and the Q&A upvotes — so that "delete" means the session is gone rather than only its deck, and nothing a participant wrote survives the presentation they wrote it in.

## Notes

Defect: `deletePresentation` in `server/services/presentations.ts` is `presentations.remove(id)` and nothing else. The `votes`, `responseVotes`, `qaQuestions` and `qaUpvotes` collections are all keyed by `presentationId`, and every row in them outlives the deck it belonged to.

What survives, concretely: the free text a participant typed into a word cloud or an open question (`StoredVote.value`), the questions they asked out loud in the room (`StoredQAQuestion.text`), and the `participantId` on all four record types that ties those rows to one device across a session. None of it is anonymous aggregate — it is what individual people wrote.

Why it cannot be reached again: the deck document that carried the id is gone, so no route, presenter screen, results export or admin action resolves it. `GET /api/admin/actions` offers only `reassign-presentation`; there is no purge surface. The rows are not shown, not exportable and not deletable — they are simply retained, and the store grows by them with every deleted presentation.

The behaviour is already documented as if it worked. The OpenAPI description on `DELETE /api/presentations/:id` reads "Permanently removes the presentation, all its slides, votes and responses." A presenter deleting a session is told the participants' answers went with it. They did not.

The same code already knows how to do this. `resetPresentation` clears exactly these four collections by `presentationId` before it puts the deck back to `draft`, on the reasoning that "the audience in front of you is not the one that asked". Delete is the stronger operation and does less: a re-run erases the room's answers, a deletion keeps them. Whichever way the inconsistency is read, one of the two is wrong, and it is delete.

Scope: erase the four collections keyed by `presentationId` as part of the delete, and correct the endpoint's description if the wording still overstates what it does. The route's authorization is unchanged — owner-or-edit-token already gates who may delete, and this requirement does not touch who may, only what happens when they do.

Out of scope: retention policy, scheduled expiry of untouched presentations, and any participant-facing "erase my answers" request. Those are separate capabilities; this is about one operation keeping the promise it already makes.

## Updates

- 2026-08-07 — deletePresentation now erases the four participant-keyed collections (votes, responseVotes, qaQuestions, qaUpvotes) before removing the deck, via a shared eraseParticipantRecords helper resetPresentation also calls; DELETE /api/presentations/:id description corrected to state what it erases; covered end to end by server/delete-cascade.integration.test.ts, verified failing against the unfixed delete.
