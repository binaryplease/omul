## Description

As someone pointing a coding agent at omul — to script a deck, to wire a session into a pipeline, to let an assistant pull a room's results — I want this repository to carry a skill file the agent's harness can install, so that the agent learns the credential it needs and the commands that do the job from one installed document instead of from reading this codebase.

Done when the standard skill installer run against this repository (`npx skills add binaryplease/omul`) installs a skill whose instructions alone let an agent create a presentation and read its results through the client of REQ180, with the gate AGENTS.md declares still green.

## Notes

**Current behaviour.** Nothing in this tree is addressed to an agent that wants to *use* omul. There is no `SKILL.md` anywhere in the repository and no `skills/`, `.claude/skills/` or `.agents/skills/` directory; `AGENTS.md` is a contributor document about working *on* this codebase, and `CONTRIBUTING.md` likewise. The only agent-facing affordance the product has is the one the API carries itself — the discovery index at `GET /api` (`server/routes/discovery.ts:176`) and the OpenAPI spec at `/api/docs/json` (`server/index.ts:34`) — which an agent has to find and interpret on its own.

**What the installer expects.** Verified against the skills CLI's own documentation on 2026-09-18: a skill is a directory holding a `SKILL.md` with YAML frontmatter, of which `name` (lowercase, hyphens allowed) and `description` are required; the installer walks a repository's root, `skills/`, `.claude/skills/`, `.agents/skills/` and similar container paths, so an ordinary application repository carrying one skill directory is a supported layout and needs no repository of its own. This one is public and clonable already.

**Order.** This record is not pickable before REQ180 lands — the skill's content is the client's verbs and its credential, and a skill written against a client that does not exist is a document nobody can follow.

**Credential wording is load-bearing.** The skill tells an agent which secret to use and where to read it from. It must not instruct an agent to paste a personal API key into a command line, and it must not imply that an edit token can be re-fetched — the server returns it exactly once (`server/routes/presentations.ts:507`).

Out of scope: listing or promoting the skill in a third-party directory, which is a distribution decision for the owner and belongs in the business catalog, not here — the outcome above is the skill being installable from this repository, which is true with or without a listing; and an MCP server, which is a different integration shape and a different record if it is ever wanted.

Catalog note: written with `source: internal`, following REQ179's precedent, because the business half was not in scope and no business-requirement number was available to cite. If one covers the agent-facing surface, this `source` line is the thing to correct.

## Updates

- 2026-09-18 — Shipped the agent skill at skills/omul/SKILL.md — a directory-plus-SKILL.md layout the standard installer walks (npx skills add binaryplease/omul), frontmatter name "omul" matching its directory plus a description written for the moment of need. Its instructions stand alone: how to get the command (nix run, or bun link in a checkout), how to point it at a server, the two credentials and their rules, create from a template or from a deck document, read show/results with --json, and what "withheld" means. Credential wording is the load-bearing part — an agent is told never to put a personal API key on a command line or in a file it writes, and to stop and ask the person to export OMUL_API_KEY or run omul auth login themselves; the edit token is described as returned exactly once, with the local 0600 store named as its only copy and no way to re-fetch it. Verified by walking the document against a locally-run server with no credential configured: create from its own example deck JSON and from --template retrospective, show, results, and the withheld marker a second token store reads on a resultsVisibility private deck. The skill also says what the client cannot do yet — starting, advancing and ending a session are the presenter's, so a draft deck's empty tally is not a bug. README and docs/api.md point at it, and docs/api.md records that the skill restates the client rather than linking to the repo, so both move together. mise run check and mise run test green.
- 2026-09-21 — Review fix: five Low/Info wording findings on skills/omul/SKILL.md, each checked against cli/ first and all five confirmed. The edit-token path is now given as $XDG_DATA_HOME/omul/edit-tokens.json with ~/.local/share as the fallback (cli/edit-tokens.ts). The plaintext opt-out now tells the agent to stop and ask the person, the same rule as the API key. The skill now warns that a throwaway container destroys the only copy of the edit token. The server-URL order now includes the config file between OMUL_SERVER_URL and the default (cli/config.ts resolveSettings). The human output of results is now described as two lines per slide (question, then tally) and show as one row per slide. No cli/ or server/ change.
