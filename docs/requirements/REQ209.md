## Description

As a participant in a live session, I want my screen to follow the presenter's deck on its own, whenever and however I joined and whatever happened to my connection, so that I am never left on "Waiting for presenter" while the session is running.

## Notes

**The defect, as reported by a tester.** A participant was shown "Waiting for presenter" (`t.waitingPresenter`) while the presenter was live. The participant page draws that screen for a presenter-paced deck when its copy of the deck says `draft`, or when it holds no slide at `activeSlideIndex` (`src/pages/ParticipantPage.tsx`, the waiting branch).

**Root cause: the socket's only source of truth was the frames it happened to be in the room for.** A client learns the deck's state from a read it made before its socket joined: the join lookup (`GET /api/join/:code`) on first load, or whatever it held when the frames stopped arriving. The server's `join` handler only seated the socket in the room and answered nothing. Every frame broadcast in between reached a room the client was not in, so a lost `presentation.started` left the phone on the waiting screen for the whole session. Four paths reach that.

1. **Joining around the start.** The join lookup reads the deck as a draft. The presenter starts. Only then does the socket connect and join, which takes a render and a WebSocket handshake. The start frame went out in between.
2. **A dropped socket, or a server restart.** The client reconnects after 1 s and joins again, but nothing re-read the deck. A start (or any other frame) broadcast while it was down was gone. A restart drops every socket at once.
3. **A socket that died without closing.** A phone that slept, or moved from Wi-Fi to cellular, can hold a socket the browser still reports open while nothing reaches it. No close event fires, so the reconnect in path 2 never runs.
4. **A live slide this copy does not have.** The server lets a live deck be saved (REQ207 records that the rule is undecided). A slide added after a phone read the deck, then navigated to, arrives as an index only: `slide.changed` moves `activeSlideIndex` and the client keeps its old slide list, so there is no slide to draw.

**Decided.**

- **Every join is answered with where the deck stands** (`room.joined`, `joinLiveRoom` in `server/services/presentations.ts`). The frame carries the deck's runtime fields, `LiveRoomSnapshotSchema` in `server/schemas.ts`: status, active slide, session clock, question stamps, reveal set, closed slides, blanking and countdowns. Every one of these is already on the deck every participant receives. Seating the socket, reading the deck and sending the frame run in one synchronous step (`findOneNow`, `server/db.ts`), so no other request's write and broadcast can land in between. Anything that changes after the read reaches the client as its own frame, behind this one. The client applies the frame with `applyJoined` (`src/store/session.ts`) and drops a frame for another deck or one that does not parse. This closes paths 1 and 2: the first join and every re-join after a reconnect both converge.
- **The client keeps a heartbeat** (`SOCKET_PULSE_MS`, `pulseWs` in `src/api.ts`). Every 15 s the client sends `ping` and the server answers `pong`. A beat that finds nothing heard since the last one, whether an unanswered ping or a handshake still hanging, opens a fresh socket. A page coming back to the foreground after longer than a beat opens one at once, and so does the browser's `online` event. Each fresh socket joins again and is answered by `room.joined`. This closes path 3. Reconnects are bound to the socket that closed, so a socket already replaced never starts a second chain, and frames from a replaced socket are not delivered.
- **The participant page re-reads the deck's slides when the presenter is live on a slide its copy does not have** (`liveSlideMissing`, `src/pages/ParticipantPage.tsx`, through the existing `refreshDeckSlides`). It asks once per active index and deck length, so a deck that really has no slide there costs one lookup, not a loop. This closes path 4 whichever way REQ207 is decided.

**Not covered here.**

- A slide inserted *before* the active one moves a held copy onto a different slide rather than onto the waiting screen. That belongs to REQ207.
- A reset missed while disconnected now reaches the phone as `draft` from `room.joined`. It does not bump `sessionResetRevision`, so a stated name (REQ076) is not forgotten on that path. A Q&A or chat change missed the same way is re-read on the next one. Neither leaves a participant on the waiting screen.
- **Reverse proxy.** The deployment's proxy must pass the WebSocket upgrade through. The heartbeat puts a frame on the wire every 15 s each way, so a proxy idle timeout above that never closes a healthy socket. One below it closes the socket, and the client reconnects and catches up through `room.joined`.

**Done when.** A regression test for each path fails without the fix:

- Paths 1 and 2 on the server: a join after a start and slide change is answered live on that slide, and a re-join after a drop hears the start it missed (`server/ws.integration.test.ts`).
- Paths 1 and 2 in the reducer: a draft or ended copy follows `room.joined` (`src/store/session.test.ts`).
- Path 3 in `src/api.test.ts`: an unanswered ping replaces the socket and the new one joins again, and a page back from sleep reopens at once.
- Path 4 in `src/pages/ParticipantPage.test.ts`: `liveSlideMissing`, and the page's re-read wired to it.

## Updates

- 2026-10-23 — Fixed: every socket join is answered with room.joined, the deck's live state read in the same synchronous step that seats the socket, and the client applies it, so a start broadcast before the join or during a dropped socket or server restart is no longer lost. The client sends a ping every 15 s and replaces a socket that heard nothing for a whole beat, reopens at once when the page returns from sleep or the network comes back, and binds each reconnect to its own socket. The participant page re-reads the slides when the presenter is live on a slide its copy lacks. Regression tests in server/ws.integration.test.ts, src/store/session.test.ts, src/api.test.ts and src/pages/ParticipantPage.test.ts fail without the fix.
- 2026-10-23 — Review fix: a failed re-read of a missing live slide no longer waits for the presenter. refreshDeckSlides now resolves whether its answer landed, and the participant page re-reads through rereadUntilAnswered, which retries a failed read with backoff (1 s doubling, held at SOCKET_PULSE_MS) for as long as liveSlideMissing holds and stops at the first answer or when the index, deck length or missing state moves. This closes the sequence the review traced: slide added and navigated to, the phone's re-read lost on a weak link, the reconnect's room.joined repeating the same index. src/pages/ParticipantPage.test.ts drives the retry loop with a hand-stepped timer, including through the store with a first fetch that fails.
