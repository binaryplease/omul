## Description

As an operator of any omul instance, I want the set of administrator accounts to be supplied by the deployment rather than compiled into the source, so that the identity of one deployment's administrators is not a fact every other deployment ships, and so that changing who is an administrator does not require editing, rebuilding and redeploying the application.

## Notes

Raised by a publication readiness check, **internal**. Two defects in one line of code, one of which blocks publication.

**What is there now.** `server/admins.ts` holds `ADMIN_EMAILS` as a hardcoded `readonly string[]` containing two real named individuals at the operator's own mail domain. The same two addresses are repeated across `server/admin-events.test.ts` (eight occurrences) and `server/ownership.integration.test.ts`, the latter beside a test password literal.

**Why it blocks publication.** These are personal work addresses of identifiable people, sitting in the source of a repository that is headed for a public URL. Publication is one-way: within minutes of the flip they are cloned, mirrored, indexed and scraped, and setting the repository private again does not reach the copies. Address harvesting for phishing is the ordinary outcome, and the addresses are not merely present — they are *labelled as the administrators of a live system*, which is a targeting hint on top of a contact detail.

**Why it is also a design defect, independent of publication.** The docblock says plainly that there is no role column and no self-service grant. That is a defensible security posture and it does not require the list to be a compile-time constant. As written, a self-hoster who deploys this image gets someone else's administrators in their binary and has no supported way to name their own: the only route is to fork, edit a source file, and rebuild. An operator changing an administrator should be changing configuration, not source.

**The shape of the fix.** An environment variable read at startup — a comma-separated list of addresses — parsed once, trimmed and lower-cased into the same `Set` the module already builds, with the same case-insensitive comparison and the same null/blank/unknown → `false` contract. The exported surface (`isAdminEmail`, `adminEmails`) stays as it is, so the route layer and the tests do not move. The empty default is the safe one: no variable set means no administrators, which fails closed — the admin surface simply has no one on it — rather than falling back to a shipped list. Whatever the deployment currently relies on is then supplied the same way the auth signing secret already is, by the deployment's own secret delivery, and named in the environment-variable table in `docs/deployment.md`.

**The tests come with it.** The test files should build their own allowlist from the same injection point with addresses in a reserved example domain, not from the production one. `scripts/` and the rest of the suite already use `example.com` and `example.test` throughout; these two files are the exception.

**Related, and deliberately not folded in.** `server/accounts.ts` falls back to a placeholder auth signing secret when `BETTER_AUTH_SECRET` is unset, and `docs/deployment.md` states in two places that this placeholder ships in the open-source repository and that every session cookie is forgeable without the variable set. That is a documented, deliberate developer-experience default rather than a leaked credential, and it is correctly flagged where an operator will read it — but a placeholder secret whose value is public in a repository anyone can clone deserves its own decision (fail closed at startup outside development, as this requirement does for the allowlist) rather than inheriting this one.

**Done when.** No personal address appears in `server/` or in any test; the allowlist is read from the environment with an empty, fail-closed default; the variable is documented in `docs/deployment.md`; and `bun test` passes with the tests supplying their own list.
