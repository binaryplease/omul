## Description

Decks and folders can be edited by several accounts, with concurrent edits resolved rather than silently overwriting each other.

## Notes

### Slices

- [x] **REQ126/1-stale-write-refused** — a deck write states which revision of the deck it was based on, and the server refuses it `409` without applying it when the deck has moved since. The editor sends its copy's revision on every Save, reports a refused save as a conflict and keeps the unsaved edits on screen. Server, editor, tests, `docs/api.md`.
- [x] **REQ126/2-conflict-merge** — on a refused save the editor resolves the conflict instead of only reporting it. Changes that do not overlap (different slides, different settings) are carried onto the current deck and saved, and overlapping ones are shown so the person chooses which to keep. Builds on slice 1.
- [x] **REQ126/3-deck-folders** — an account can group its decks into folders, and the home screen lists them by folder. Built by task NST12126-deck-folders-slice.
- [ ] **REQ126/4-folder-sharing** — a folder can be shared with accounts at the REQ075 access levels, and a grant on a folder reaches every deck in it. Closes REQ126.

### The deck revision (slice 1)

- **Where it lives:** `revision` on `StoredPresentationSchema` (integer, `.default(0)`, so a deck stored before it reads as `0`) and on `PresentationSchema`, so every deck read carries it. It is server-owned: `writeAuthoredContent` in `server/services/presentations.ts` is the only writer and adds one per successful write. `UpdatePresentationSchema` does not declare it, so a PATCH cannot set it.
- **What advances it:** `PATCH /api/presentations/:id` (`updatePresentation`), and the three routes that rewrite what the editor also saves: `…/results-visibility` (rewrites the slides' overrides), `…/qa/settings` and `…/channels`. Run-state routes (start, end, slide, reveal, timer, countdown, participation, blank) do not move it.
- **How a write states it:** the PATCH body field `baseRevision` (validated, never stored). Absent means unconditional, which is what the CLI and API-key clients send. The editor (`src/pages/CreatePage.tsx`) keeps the revision it loaded and sends it on Save; `staleDeckWriteOf` in `src/api.ts` recognises the refusal — only a `409` with `refused: "stale-revision"`, no other `409` — and hands back the deck and revision it carries (`ApiError.body`).
- **What the `409` carries:** `{ error, refused: "stale-revision", revision, presentation }`. `presentation` is the current deck through `sanitize(…, { canEdit: true })`, the editor's projection, so `creatorId` and `creatorTokenHash` never travel. That is the base slice 2 has to merge onto. Nothing is written or broadcast on a refusal.
- **Ordering:** the read, the comparison and the write run in one per-deck turn of `deckRevisionLock` (`createKeyedLock`), so two writes on one revision cannot both land. Like every lock here it is per process. The HTTP race rarely reaches the gap between read and write, so the discriminating test calls `updatePresentation` concurrently in one tick (`server/deck-revision.integration.test.ts`).
- **Open for slice 2:** a refused editor is stuck until it merges or reloads, and a reload discards its edits. Settings toggled from the presenter screen (Q&A, channels) also refuse an open editor's next Save. That is deliberate, because the Save would otherwise revert them, but it makes merging settings as important as merging slides.

### The merge (slice 2)

- **Where it lives:** `src/store/deckMerge.ts`, pure apart from the `write` its save loop is handed. `mergeDeckEdits` is the merge, `saveDeckEdits` the loop; `src/components/DeckMergeDialog.tsx` asks for the overlaps; `CreatePage` adapts the API to `write` and holds the outcome.
- **Three sides:** the deck as this editor loaded it (`base`, kept beside `baseRevision`), the person's edits as Save would send them (`mine`), and the `409`'s `presentation` (`theirs`). Both decks off the wire go through `editorDocumentFor` in `src/store/editor.ts` — the reader `loadEditor` uses — so a default filled in on one side never reads as an edit.
- **Units:** each deck-level field the editor saves (`DECK_FIELD_LABELS`, a `Record` over the editor document's keys, so a new field does not compile until it is listed) and each slide by `id`. Nothing is merged inside a slide. Equality is structural, ignoring key order and keys holding `undefined`.
- **Rules:** a unit changed on one side takes that side's value; changed on both to the same value it is not a conflict; changed on both differently it is an **overlap**. A slide missing from a side is "absent" there, so an add is kept, a delete against an untouched slide deletes it, and a delete against an edit is an overlap.
- **Order:** the side that reordered the slides all three hold leads, and the other side's slides are placed after their own predecessor (first, when none was placed). Both reordering differently is one more overlap, `order`. The order is built from the set of kept slides, each placed once.
- **Saving:** a merge with no overlaps is saved at once on the `409`'s `revision`, and that deck becomes the new base. A refusal of that save merges again, up to `DECK_MERGE_ROUNDS` (3) per Save, then stops with a banner and the merged edits on screen. Overlaps open the dialog: one choice per overlap (mine or the current one), Save inert with its reason until all are made; Cancel saves nothing and leaves the edits and the old base, so the next Save is refused and merged again.
- **For slices 3 and 4:** a deck's folder, if it becomes an authored field the editor saves, is one more deck-level unit — add it to the editor document and `DECK_FIELD_LABELS` and the merge covers it. Folder writes outside the editor need no merge unless they advance the deck revision.

### The folders (slice 3)

- **Where they live:** `server/services/folders.ts`, which owns two collections and imports nothing from the presentation service. `folders` holds one row per folder (`ownerId`, `name`). `folderEntries` holds one row per filed deck (`folderId`, `presentationId`, `ownerId`) and is unique on `presentationId`, so a deck is in at most one folder at the storage layer. The schemas are `StoredFolderSchema`, `StoredFolderEntrySchema` and `FolderSchema` in `server/schemas.ts`. Routes are in `server/routes/folders.ts`, documented in `docs/api.md` under **Deck folders**.
- **Not on the deck:** membership is deliberately not a deck field. No folder id reaches any deck read, so it never reaches a participant, and filing is not an authored write. The deck `revision` does not move and the slice 2 merge is untouched. The editor does not save a folder.
- **Who:** every folder route answers to the caller's own account (`401` without one). Another account's folder answers `404`, the same as a missing one. Filing (`PUT /api/presentations/:id/folder`) requires `creatorId` to be the caller, so a shared deck, a workspace deck and a deck held only by an edit token all get `403`.
- **Lifecycle:** deleting a folder deletes its entries and never a deck. `deletePresentation`, `setPresentationWorkspace` and `assignOwner` (on a change of owner) call `unfileDeck`, so a filing never outlives the ownership it was made under. Filing a deck that already has an entry replaces it.
- **Home screen:** `HomePage` reads `GET /api/folders` beside `/presentations/mine`. `groupDecksByFolder` makes one group per folder, then the unfiled decks; with no folders the list looks as it did before. A New folder button sits on the list. Each folder heading has rename and delete buttons, and each deck card has an owner-only "Move this deck into a folder" button that opens a picker.
- **For slice 4:** a grant on a folder will need its own collection keyed by `folderId`, at the REQ075 levels. To find a deck's folder, read `folderEntries` by `presentationId`, a unique, indexed lookup. The folder grant then joins the strongest-standing resolution in `resolveDeckAccess`. Two things slice 4 must settle. First, the routes here are the owner's alone, so a grantee's view of a shared folder (listing it, and its decks under "Shared with You") is new surface. Second, an entry is only cleared on delete, workspace move and owner reassignment, so access resolution should still require the deck's current `creatorId` to equal the folder's `ownerId`, and not trust the entry alone. `claimOwnership` needs no unfiling, because it only claims an unowned deck, and such a deck cannot have been filed.
