## Description

As a maintainer of this repository, I want the SQLite document store to be an ordinary registry dependency at a pinned version, so that updating it is a version bump with a changelog to read rather than a tree-diff against an upstream nobody can see from here.

## Notes

The store was vendored at `vendor/binp-docstore/` as `file:./vendor/binp-docstore` — a snapshot taken before the upstream had any version at all, sitting at `0.0.0`. Two costs followed from that and both are the reason this exists. **Updating it was a manual tree sync**, so "which storage layer is this?" could only be answered by diffing; and **its license had to be argued for** rather than stated, because the snapshot predated the upstream `LICENSE` file (REQ161, `NOTICE.md` §2). The upstream is now published as `@binaryplease/zodstore` under the MIT License, which settles both at once.

**It is a version jump, not only a specifier change.** The vendored snapshot predates the upstream's `0.1.0`; the published version is `0.4.2`. Three of the intervening changes reach this codebase and each is decided in `server/db.ts` with the reasoning beside it:

- **`enforceDefaults` (new in 0.1.0, defaults to `true`) is turned off here.** The library refuses a non-identity field with no `.default(...)` — this project's declared-defaults rule, enforced rather than documented — and recognises an identity field by the schema object its `ref()` helper returns. `ref(prefix)` is a `z.string().startsWith("prefix_")`, and this catalog's foreign keys are plain `z.string()` over `crypto.randomUUID()` values that carry no prefix, so the walk reads all eighteen of them — eight distinct names (`presentationId`, `slideId`, `workspaceId`, `userId`, `authorId`, `participantId`, `questionId`, `responseId`) spread over nine of the eleven collections — as ordinary fields that forgot a default. The rule is not dropped: `server/stored-defaults.test.ts` enforces it over every collection with each one's identity fields written down, so a *new* field that forgets a default still fails, and an exemption for a field that no longer exists fails too.
- **`maxRows` (new in 0.1.0, defaults to `10_000`) is disabled here.** An unbounded `find()` throws rather than truncating, which is the right shape — a silently truncated result is a wrong answer. It is still wrong for this application: every read is already narrowed by a presentation id, and one large event crosses ten thousand rows legitimately (1 000 participants over ten slides is 10 000 rows of `votes` for one deck, which `votes.find({ presentationId })` is what the results view and the spreadsheet export are built on). Capping it would turn that event into a 500. **This is the one place the swap leaves an open question rather than closing one** — the honest fix is a paged read at those two call sites, at which point the ceiling can come back on.
- **Two `undefined` readings changed (0.2.0) and both are strictly safer.** A `where` condition whose value is `undefined` now matches no row instead of being skipped, so `deleteMany({ ownerId })` with an unset id can no longer empty a collection; and an `update()` patch key holding `undefined` is now a no-op instead of resetting the field to its declared default. Nothing here relied on either, and the suite is unchanged by both.

The pragmas are left at the library's own defaults (`journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=5000`); `applyDefaultPragmas`, which the vendored copy had and this codebase never passed, is gone.

**Done when.** No `vendor/` directory and no `file:` dependency in `package.json`; the store imported from `@binaryplease/zodstore`; `NOTICE.md` states the MIT position and carries the notice the bundled server has to travel with; and the repo's gate and test task stay green.
