## Description

As the owner of a repository headed for publication, I want every reference to private infrastructure, private sibling repositories and internal tooling removed from the tree — designed out, injected as deployment-supplied configuration, or restated without the fact — so that the repository is self-sufficient for a stranger holding this repository and nothing else, which is the only thing a stranger will hold.

## Notes

Raised by a publication readiness check, **internal**. This requirement names *classes* of disclosure and the file locations that carry them; it deliberately does not restate the values, because this file ships in the published tree too and a finding that quotes its target has carried the target across.

**A full-history secret scan found no credential.** `gitleaks` over all refs reported no leaks on every run up to 2026-08-27, and none since has found a credential either — the single finding the 2026-08-28 run returns is a high-entropy test fixture, filed as REQ173. Nothing here needs rotating. What follows is confidentiality, not credentials — which makes it no less blocking, because it is equally unrecallable once public.

**The classes found, by location.**

1. *Private infrastructure topology.* `docs/deployment.md` and the update log of REQ145 describe the production deployment as it actually stands: the reverse-proxy vhost, the published loopback port, the redeploy-webhook listener port, the secret-delivery paths on the host, and the private infrastructure repository that owns the compose file. A second internal host that never existed is named in the same log while being corrected. `task/0005-slide-type-settings.md` links an internal collaboration pad by its unguessable share slug — a capability URL, so it is closer to a credential than to a hostname and should be treated as one.

2. *Private sibling repositories and internal tooling.* `AGENTS.md` names the private documentation sidecar, the archived predecessor repository, and the agent collection that stages this repo's `check` tooling. `vite.config.ts`, `Dockerfile`, `tools/inspector/README.md` and `package.json` named the internal UI project that was the vendored inspector's canonical home; all four references left with the inspector itself on 2026-08-28 (see the update log). Beyond `AGENTS.md`, a sibling internal project was named in six further places — `docs/api.md` twice and four server docblocks under `server/` — and the internal collection that stages the `index` CLI was named in `docs/README.md`, `docs/frontend.md`, `docs/deployment.md` and the vendored store's own README. `server/admins.ts` carried the sibling project's name in its docblock until REQ164 rewrote that module; the claim that it still does is stale and was carried forward in error. Some of these are load-bearing for a contributor and some are not; each needs the move that fits — design it out, inject it, or restate the constraint without the fact.

   The private infrastructure repository that owns the deploy configuration re-entered this class after it had been swept: the requirement documents written on 2026-08-29 for the identifier sweep named it in three out-of-scope clauses, all in body text, all written *after* the sweep of 2026-08-28 had measured the tree clean. Each clause has been restated by role — the deploy configuration lives in a separate private infrastructure repository, which is that repository's to change — and the constraint each carried, that the configuration is out of this repository's reach, survives the restatement intact.

3. *Internal task identifiers, in commit messages and in file bodies.* **Retired as a disclosure class by the owner on 2026-08-31. Nothing here is swept, gated or owed, and the class is kept in this list by number only so classes 4 and 5 still mean what every other document says they mean.** What was found: every commit carries a trailer naming the internal work queue and the task within it, requirement documents and one test docblock cite those identifiers inline, and together they disclose the existence, shape and volume of an internal work queue. The standing answer — that REQ165's extraction starts the published history at one commit carrying none of them — was true of the trailers and never of the file bodies, which the export copies verbatim; that gap is what reopened the class on 2026-08-31 and what the retirement closes.

   **Why it is retired rather than swept.** The session runner stamps every commit with such an identifier, so the published repository goes on collecting them for as long as development continues, and each sweep had been leaving the next one's residue — a chase that cannot terminate. Against that, one commit's identifier discloses little: a bare ticket number a reader cannot resolve, with no name, no content and no route into anything. The owner weighed the two and closed the class. A work-queue identifier may therefore sit anywhere in this tree — a requirement body, a commit trailer, ordinary prose — and the guard does not refuse one. The occurrences already inside append-only `## Updates` logs stay exactly as written, which they would have anyway.

4. *Internal decision-record identifiers.* Twenty-nine distinct decision-record references — the letters `ADR`, a hyphen and a four-digit number — appeared across the tree, 996 occurrences over 240 files, pointing at records held in a private repository. To a stranger they were dangling citations; to a reader who could correlate them they enumerated an internal decision corpus. **Swept for the editable tree on 2026-09-03.** Every reference that carried a real constraint on this codebase now states that constraint in words a reader holding only this repository can act on — the defaults rule, the disable-don't-hide rule, one descriptor per cross-surface affordance, no third-party runtime asset host, and the rest — and the ones that carried nothing the surrounding sentence did not already say are simply gone. Two closed task logs were renamed, because their filenames encoded identifiers. What remains is the append-only residue: 76 occurrences inside `## Updates` logs across 49 files, left exactly as class 3's residue was left, for the same reason — those sections are append-only, and the one exception ever taken to that is not a precedent a session may extend on its own judgement.

5. *Product-team and competitive framing.* the design document positions the product against another vendor and against an internal ecosystem, and `task/0006-docker-deploy-migration.md` names sibling internal web apps. `AGENTS.md` is explicit that competitive research and business-side material do not belong in this repository. No competitor name or help-centre URL survives anywhere in this tree or its history — that residue was left behind with the predecessor repository and the check confirms it — so this is framing to remove, not a leak to contain.

**What keeps a swept class swept.** Class 2 was removed by hand twice and came back within a day of its own sweep both times. Nothing in this repository failed when the vocabulary returned, so only the next manual sweep noticed, and a sweep is a measurement rather than a control. `scripts/guard-publication-residue.ts` is the control, and `mise run check` runs it. **Its coverage is exactly one term** — the private infrastructure repository that owns the deploy configuration — refused in any file and any section of a file, with no allowance anywhere and no exemption but the publication record itself. Everything else in this requirement is convention held by review: a green `check` says that one slug is absent from the tree and says nothing whatever about the other classes, so do not read it as a swept tree. It scans untracked files as well as tracked ones, because the session runner's hook is what commits and a new file is untracked right up to that moment.

The guard holds its term as a SHA-256 digest rather than as a literal, and redacts the identifier out of its own failure report. That is not concealment — a short slug is brute-forceable and the digest is not a secret — it is the same constraint REQ174 and REQ175 met when they deleted three negative-assertion tests: a guard that names the string it refuses is an occurrence of that string, in the one file whose subject is its absence. What it buys is that a stranger grepping the published tree for that term finds nothing, the guard included.

Every other class is held by argument rather than by the guard. Class 1's deployment topology is closed by removal and by `D8`'s extraction step, and class 5's framing by removal. Class 3 is retired, so there is nothing to hold. Class 4 is closed by removal in the editable tree and is held by review from here on, which is the weakest of the five holds: a citation costs one parenthesis to write back, nothing in this repository fails when one does, and only the next manual sweep would notice — the shape this note opens by describing. A guard for it is mechanically easy in a way class 2's was not, because the thing to refuse is a *shape* and not a string, so no digest is needed and the guard would state no identifier. What makes it an owner's call rather than a session's is the residue: every one of the 76 remaining occurrences sits inside an append-only `## Updates` log, so a guard has to carry either section detection or a per-file allowance table — and both were deliberately deleted from `scripts/guard-publication-residue.ts` when class 3 was retired. Re-adding one reverses that simplification, so it is recorded here as a question rather than taken.

**Not in scope here.** The hardcoded administrator allowlist is a design finding with its own remedy and is filed as REQ164. The object-store residue that decides the publication artifact is REQ165. The scanner finding on a test fixture is REQ173 — it is scan hygiene, not a disclosure.

**Done when.** A sweep of the tree over the estate's own vocabulary — internal repository names, internal hostnames, ADR identifiers, internal project names, and not work-queue identifiers, which this requirement no longer claims — returns only occurrences that a stranger can act on, and the build and the tests still pass with every removed fact either designed out or supplied by deployment configuration.
