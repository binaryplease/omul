## Description

The create path accepts a template identifier and returns a deck whose slides are copies of the template's, fully editable and detached from their source.

## Updates

- 2026-08-10 — POST /api/presentations now accepts templateId and answers with a deck whose slides are copies of that entry's. Copying is withFreshSlideIds() in server/schemas.ts — one definition of what a copy is, re-minting the slide id and every nested identity down to a form field's own options, now shared by the create-from-template path and the client's duplicate and import paths (which had a partial version of it). Nothing records the origin: no templateId on the stored deck, so editing it cannot reach the catalog and two decks from one entry share no id. A template create may omit title (inherited from the entry) and slides; every create that names no template still requires a non-empty title and at least one slide, enforced by a refinement on CreatePresentationSchema rather than by min(1). An unknown id is a 400 that writes nothing, and the create spends the ordinary create rate-limit budget (REQ145). Deck settings — pace, reveal mode, Q&A, the participant channels, theme — stay the request's, never the template's, so a gallery pick cannot open a room's chat; a slide's own resultsVisibility does travel, since it lives on the slide. Covered by server/templates.schemas.test.ts and server/templates.integration.test.ts (41 tests), which walk every built-in entry and assert the copy is detached both ways.
