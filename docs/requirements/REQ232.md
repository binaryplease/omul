## Description

As a participant answering a quiz question, I want an answer the server turns away to leave me on the question with the reason beside it, so that a late or second tap does not throw me out of the presentation onto an empty code entry.

The vote route refuses a well-formed answer for four stated reasons, each with a machine-readable `refused` code (REQ054, REQ057, REQ111, REQ226): `quiz-not-started`, `quiz-window-closed`, `quiz-already-answered` and `participation-closed`. Each is news about one answer, not about the session. This repairs REQ054/REQ057 (quiz answers), REQ111 (closed slides) and REQ226 (questions waiting for their timer) on the participant page, and puts the reason where REQ221 announces it.

- **A stated refusal stays on the slide.** The page does not switch to its error screen. The reason appears under the answer control, in the answer status line that REQ221 made a polite live region, so a screen reader reads it out. It is not also raised as a toast there, which would read it twice. On a slide with no such line, it is a toast, as before.
- **Worded from the deck's language, keyed on the code** (REQ084, REQ225): the same dictionary entries the phone's own lock reasons use, chosen by the `refused` code and never by the English `error` text the route sends beside it.
- **A refusal re-reads the participant's scorecard**: after `quiz-already-answered`, the answer on record (from another tab, say) shows as the locked choice.
- **Once the question is over** the refusal line is dropped, so the participant sees the result and the solution exactly as somebody who did not answer in time.
- **Failures without a stated refusal keep the page's error path**: the deck no longer live, the slide gone, a value the boundary rejects.
- **Unchanged:** the server's refusals, scoring and window rules; the preview's participant pane, which reports non-refusal failures as a toast.

## Notes

Defect, **internal**: found in three successive re-tests of the quiz feature. Every refused quiz answer replaced the participant page with an error screen whose "Try again" led to an empty code entry.

As shipped (2026-10-31):

- **Client:** `routeSubmissionFailure` in `src/components/ParticipantSlideView.tsx` sends a failure carrying a `refused` code to the slide's own report and everything else to the surface's `onError`. The wording per code is one `Record<VoteRefusalCode, …>`, so a new code without wording does not compile. The slide view holds the refusal per slide and shows it in `AnswerStatus` behind the lock reason. The local closed-slide guard reports through the same path. `ParticipantPage` still passes the store's `setError` as `onError`.
- **Server, `cli/`:** not touched.
- **Tests:** `src/components/ParticipantSlideView.test.ts`, "a refused quiz answer keeps the participant on the slide (REQ232)". For every refusal code, with a select answer and a typed answer, the live transport is answered with the route's `400` body. The failure is routed with the store's `setError` as the page's error path. The tests check that the store's `error` stays empty, which is what the page draws its error screen from, and that the reason arrives in German. An uncoded `400` still sets the page error. A source guard pins `onError` to one call site. The tests fail on the tree before this change, which has no router and three direct `onError` calls.

Left open: the English "Try again" on the error screen that remains, and the brief "time is over" live-region flash at the deadline.
