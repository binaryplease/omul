## Description

As a presenter who ends a live deck and then presses Restart, I want every screen in the room (each participant's phone and any other presenter tab) to go live again on the same slide I see, so that the room and I are never on different slides.

## Notes

**The defect, as reported by a tester.** After a restart the presenter stood on slide 1 while the participants stayed on the slide shown last (for example slide 3).

**The restart path.** On an ended deck the presenter bar offers Restart (`src/pages/PresenterPage.tsx:1590`), which calls `POST /presentations/:id/start`, the same action as the first Start. `startPresentation` (`server/services/presentations.ts:1423`) sets `status: "live"` and moves `activeSlideIndex` to `0`. Ending a deck leaves `activeSlideIndex` wherever the session stopped.

**Root cause.** The clicking presenter takes slide 0 from its own call (`startPresentation` in `src/store/session.ts:501`). Every other screen learns of the start only from the `presentation.started` frame. That frame carried the session clock and nothing about the slide, and `applyStarted` (`src/store/session.ts:653`) only set the status. So each participant, and any second presenter tab, went live again on the index it still held from the last session. A Start on a deck that is already live moves the deck back to slide 0 in the same way and diverged the same way.

**Decided.** The `presentation.started` frame names the slide the start landed on (`slideIndex`), and `applyStarted` applies it. The move travels in the same frame as the status, so no screen briefly shows the old slide as live while a second frame is still on its way. A frame without `slideIndex` leaves the index the screen holds.

**Done when.** A regression test drives start, next slide, end and start over a real socket and asserts that the restart frame names the slide the server landed on (`server/ws.integration.test.ts`). A reducer test asserts that a participant parked on a later slide follows that frame (`src/store/session.test.ts`). Both fail without the fix.

**Out of scope.** The "Waiting for presenter" screen and any new restart behaviour. Whether a restart should resume where the last session stopped, rather than at the first slide, is a separate decision. This record only makes every screen agree with what the server already does.

## Updates

- 2026-10-23 — Fixed: the presentation.started frame now carries slideIndex (the first slide a start lands on) and applyStarted applies it, so a Restart after End moves every participant and every other presenter tab to the slide the presenter stands on. Regression tests in server/ws.integration.test.ts and src/store/session.test.ts fail without the fix.
- 2026-10-26 — Follow-up: a restart after deleting the slide the deck stopped on put every phone on the deleted slide, and a vote there was refused. Cause: the phone addresses the live slide by index into the copy it read before the edit, and REQ209's re-read fired only when that index fell outside the copy, so index 0 resolved to the deleted slide. The presentation.started frame now carries slideId and room.joined carries activeSlideId; the session slice keeps it as liveSlideId (slide.changed sets it from its slide), and liveSlideMissing also counts a held slide with another id at that index as missing, so the page draws nothing and re-reads its copy. Regression test in server/ws.integration.test.ts (three slides, live, stop on the first, delete it, restart, phone state, vote) fails without the fix.
