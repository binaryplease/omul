## Description

As a presenter preparing a deck on the presenter screen (`/present/<id>`) before starting it, I want the per-slide participation control to say what closing a slide does at that point, namely that the slide goes live closed and opens on my cue, so that a pre-closed slide is a choice I make knowingly rather than a room that cannot answer and does not know why.

## Notes

**What happens today.** Closing a slide before the start is real and lasts. The presenter screen draws the REQ111 control on every interactive slide whatever the deck's status (`src/components/PresenterSlideView.tsx:346-354`, wired at `src/pages/PresenterPage.tsx:1395`). `POST /presentations/:id/participation` checks only edit access, not `status` (`server/routes/presentations.ts:965-980`). `startPresentation` leaves `closedSlideIds` as it is (`server/services/presentations.ts:1231-1237`); only Reset clears it (`:1302`). So a slide closed on a draft deck goes live refusing every answer with `participation-closed` until the presenter reopens it. The wording assumes a room is already there. The label reads "Close submissions" (`src/components/LiveRoom.tsx:121`), the tooltip says "the room stops being able to answer it, and every answer already given is kept" (`:86`), and the confirmation toast says "the answers already given are kept" (`src/pages/PresenterPage.tsx:404`). On a draft deck this sits directly above "Start the presentation to collect responses" (`src/components/PresenterSlideView.tsx:420`). Nothing at Start mentions that some slides begin closed. The code's own premise contradicts the behaviour: the docblock at `src/components/LiveRoom.tsx:93-97` says the control "only ever means anything with a room in front of you".

**Decided: the behaviour stays.** Pre-closing a slide is kept on purpose as "open on cue": the question can be shown and explained before the room may answer, and in an audience-paced deck (REQ082) it stops participants from answering ahead. What is wrong is only that the surface does not say so.

**Desired outcome.** A presenter who closes a slide before the deck is live is told, both on the control and when going live, that the slide goes live closed.

**Done when.** On a draft or ended deck, the participation control's visible label, `title`/`aria-label` and confirmation toast describe the slide as going live closed and say nothing about answers already given. On a live deck they read as they do today. Starting a deck that has at least one closed slide tells the presenter which slides start closed. `mise run check` and `mise run test`, as `AGENTS.md` declares them, apply unchanged.

**Out of scope.** Whether a slide can be closed before the start, and what a closed slide does to a submission (REQ111), do not change. A per-slide "opens closed" setting authored in the editor is a separate feature and is not this record.

**Note.** On a slide whose placement is `center` or `right`, the control is still drawn left-aligned. Its wrapper at `src/components/PresenterSlideView.tsx:347` is a row `flex` with `placement.items`, which aligns only vertically, unlike the quiz block's `flex-col` at `:317`. A later record would have to take that up. Ending a deck also keeps `closedSlideIds`, so End then Start reuses the last session's closed slides, and the start notice above covers that case too.

**Known limits and follow-up, from the pre-merge review (2026-10-25).** None blocks this record; each is recorded so it is not rediscovered.

- **"Go live closed" can read like a start button.** It sits right beside "Start Presentation". The behaviour is as specified; the wording is a follow-up.
