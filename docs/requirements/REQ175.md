## Description

As someone using this application — an organizer whose browser holds edit tokens for the decks they created, a recipient holding a results link, a participant the room knows by name, or anyone saving a deck to a file — I want every name the product writes into my browser, onto the wire and into a file to be the product's own, so that nothing I can inspect names something else.

## Notes

Three surfaces name the product where a user's own state depends on it: six `localStorage` keys (`omul-tokens`, `omul-results-tokens`, `omul-participant-id`, `omul-participant-names`, `omul-theme`, `omul:pending-email-change`), two dedicated request headers (`X-Omul-Edit-Token`, `X-Omul-Results-Token`), and the deck export's `kind` marker plus its `.omul.json` suffix.

**Nothing is migrated, because nothing was ever written under another name.** The project is greenfield: no browser holds any of these keys, no page is loaded from an earlier bundle, no integration is written against an earlier header, and no exported file exists on anyone's disk. A migration would be code that can only ever run against a state no browser is in.

The first implementation of this requirement shipped one anyway — a retired spelling beside every key, a shape-aware reconciliation between the two copies, a dual read on both headers, and a dual read in the pre-bundle theme bootstrap — against a brief that stated the product was live. That premise was wrong, and the layer was withdrawn in full rather than left bypassed.

**Why `src/storage.ts` still owns the keys.** Not for the rename: a deck's edit token is returned exactly once, on creation, and the server keeps only its SHA-256 hash, so the copy under `omul-tokens` is the only one that exists anywhere. A key spelled at its read site is one refactor away from being spelled differently at two of them, and the failure that produces is every anonymous organizer locked out of every deck they made, with no error to read and no path back. So the keys are declared once and `src/api.ts`, `src/components/ui/Theme.tsx` and `src/auth.tsx` import theirs. One reader cannot: the inline script in `src/index.html` paints the colour scheme before the bundle loads, so a reload does not flash the wrong one, and it therefore spells `omul-theme` itself — the one place in the client where a key is written outside that module.

**The headers are two capabilities and stay two.** `editTokenFromHeaders` reads `X-Omul-Edit-Token` and falls back to the `Authorization: Bearer` slot the web UI has always used; `resultsTokenFromHeaders` reads `X-Omul-Results-Token` and never the `Authorization` slot, because a server that read one capability out of the other's slot would be deciding which it held by trying both. Both compose one rule for reading a header — a present-but-blank value is no claim, and no claim must not shadow the fallback behind it, or a proxy that always sets the header would silently demote a caller that did state its token. What the token proves is decided by the deck's stored hash and never by which slot it arrived in.

**The export marker is a label, not a format version.** `kind` is written on export and never read on import: the gate is `title` plus a `slides` array. A file carrying no marker at all therefore imports, which is asserted in `src/api.test.ts` rather than left as an inference, because the file picker accepts any JSON. The `.omul.json` suffix is a suggested download name only.

Out of scope: the environment variables and the database file, which are REQ174's, and the prose sweep, which is REQ176's.

**Done when.** No storage key, request header, export marker or file suffix is named for a retired spelling; every client read site imports its key from `src/storage.ts` bar the pre-bundle theme bootstrap; both headers are read on one blank-is-no-claim rule and neither widens who may mutate or read a deck; and the repo's gate and test task (both named in `AGENTS.md`) stay green.
