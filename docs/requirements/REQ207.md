## Description

As an organizer running a deck, I want one clear rule for editing it while it is live, applied the same way on every surface, so that I know whether I can fix a slide mid-session and what the room will see if I do.

Raised by a tester, verbatim: "Generell: Ist es wirklich richtig so, dass man nur Bearbeiten kann, wenn die präsentation gestoppt ist? Das sollten wir ggf. als issue aufnehmen und mal challengen lassen ob wir das so wollen."

**The owner chose B, bounded by one rule, on 2026-10-26.** The options, the recommendation and the decision are in the Notes.

## Notes

**Current behaviour: a hidden menu entry, not a rule.** Read from the code as it stood on 2026-10-23.

- **The only restriction is on the presenter screen.** Its Deck menu shows "Edit presentation" only when `isOwner && (pres.status === "draft" || pres.status === "ended")` (`src/pages/PresenterPage.tsx:1213-1216`, row at `:1237-1250`). While the deck is live the entry is simply missing, and nothing says why. The rule dates from the first commit of this repository (the old top bar's Edit button). REQ190 and REQ199 carried it over unchanged as presenter-screen layout ("for the same viewers and states as today's Edit button"). No requirement states it as a product rule.
- **The server enforces nothing.** `PATCH /presentations/:id` (`server/routes/presentations.ts:834-845`) checks only edit rights (`requireEdit`, `:374-405`). `updatePresentation` (`server/services/presentations.ts:1032-1137`) saves a live deck like any other, and its own comments already assume mid-session edits (`:1058-1060`, `:1079-1080`). The only status gate on a mutation is `acceptsSubmissions` (`:1802-1806`), which refuses audience submissions to a deck that is not collecting: a live-mode deck that is not live, or a survey deck that has ended. `startPresentation` and `endPresentation` also branch on `status === "live"` (`:1473-1476`, `:1515-1518`), but only to keep or stop the session clock (REQ108). No deck edit is refused because the deck is live.
- **The editor is reachable while live through three other paths.** Preview's Edit button checks only `isOwner` (`src/pages/PreviewPage.tsx:418-419`). The copied edit link opens `/edit/<id>` at any status (`src/pages/PresenterPage.tsx:734`). The router accepts `/edit/<id>` directly (`src/router.ts:82-83`). The editor never checks status (`src/pages/CreatePage.tsx:326-350`), and it always shows a "draft" badge, even on a live deck (`:908`).
- **A live edit reaches the room unannounced, at the next re-read of the deck.** No WebSocket event announces a changed deck (`server/ws.ts:1-30`). `updatePresentation` broadcasts only settings: Q&A, channels, results visibility, participant name, repeat passes, the join bar, and recounted standings. A participant loads the deck once, at join (`loadByCode`, `src/store/session.ts:437-464`), and takes only the new index from `slide.changed` (`:632-633`). But the participant page re-reads the deck through `refreshDeckSlides` (`src/store/session.ts:490-512`) whenever the revealed-slide set or the deck's reveal mode changes (`src/pages/ParticipantPage.tsx:409-419`), and when the presenter is live on an index its copy has no slide at (REQ209, `:429-439`). That re-read replaces `slides` and keeps `activeSlideIndex`. So an edit saved mid-session reaches phones at the next reveal toggle (REQ102) or reveal-mode save, with nothing telling the participant that the deck changed. After a delete or reorder, the unchanged index can then point a phone at a different slide.
- **Answers survive an edit but can silently stop counting.** Answers are stored per `slideId`, holding an option id or encoded item ids. A choice or quiz tally counts only options that still exist (`server/services/presentations.ts:4475-4491`). Ranking answers that no longer decode are skipped (`:4744-4747`), and so are grid answers (`:5076-5078`). Quiz scoring drops answers to a deleted option (`:3785-3790`). A quiz participant whose answer no longer stands may answer again (`:2405-2414`). The exports leave those answers empty (`server/results-export.ts:178-186`). No edit deletes an answer.
- **The live position is an index.** `activeSlideIndex` (`setActiveSlide`, `server/services/presentations.ts:1275-1320`) is not adjusted by `updatePresentation`. Deleting or reordering slides before the active one therefore moves the room onto a different slide, or past the end of the deck.

So the tester's reading ("you can only edit while stopped") is what the presenter screen suggests. It is not what the product does.

**Options.**

- **A — Keep the rule, and make it real.** Editing a live deck is refused everywhere: on the server, in the editor, from Preview and from the edit link. The edit stays possible after End, or after Reset back to draft.
  - *Live state:* untouched, because nothing changes mid-session.
  - *Answers:* can never be orphaned during a session.
  - *What people see:* participants never see a deck change under them. The presenter gets a clear "stop to edit" instead of a missing menu entry. A typo spotted mid-session can't be fixed without ending the session, and ending stops submissions for a live-mode deck (`acceptsSubmissions`).
- **B — Allow some edits while live.** Edits that leave existing answers and the live position meaning what they meant are allowed while live: wording of a question, an option, an item or a body; presenter notes; settings that already broadcast; slides added after the active one. Edits that would orphan answers or move the room are refused while live, or need the deck stopped: deleting or reordering options or items, changing a slide's type or answer mode, deleting or reordering slides at or before the active one.
  - *Live state:* the active slide stays the same slide.
  - *Answers:* option and item ids are unchanged, so every tally and score stays as it was.
  - *What people see:* participants need to see the corrected text when it is saved. Today it reaches them only at the next reveal toggle or reveal-mode save, because nothing announces an edit. The presenter gets a clear reason for the edits that are refused.
- **C — Allow all edits while live.** Any edit at any status, as the server already accepts.
  - *Live state:* the active index has to follow the slide it pointed at, or the room jumps.
  - *Answers:* answers to deleted or re-typed options silently drop out of tallies, scores and exports (references above). The participant who gave one sees their vote vanish from a result they already saw. A quiz participant may answer again.
  - *What people see:* participants need the changed deck broadcast to them when it is saved, not picked up at the next reveal with an index that may now name a different slide. The presenter needs to be told which edits invalidate answers already given.

**Recommendation: B.** The thing an organizer needs mid-session is to fix wording on the slide in front of the room. The data model already makes that safe: answers hold option and item ids, not text. The edits that are unsafe are exactly the ones that make the tally code throw answers away (`server/services/presentations.ts:4475-4491`, `:3785-3790`) or shift `activeSlideIndex`. B allows the first and holds back the second, so a running session never loses an answer it already counted. A is the cheaper fallback if the propagation B needs is judged too much for now. C makes silent answer loss a normal live action. Whichever option is chosen, today's state has to go: hidden in one menu, open through three others, enforced nowhere, never announced to the room.

**Decision: B, bounded by one rule.** While a deck is live, *text is always free, whatever has answers keeps its structure, and whatever the room is on stays where it is.* "Has answers" means at least one stored answer on that slide, option or item, checked by the server at save time. This replaces the position-based bound in option B above: the live position follows the active slide by id, so where a slide sits relative to the active one no longer decides anything.

- **Allowed while live.** Wording of a question, option, item, statement or slide body, and swapping its media, on any slide including the active one. Presenter notes, slide style, layout, chart type and value display. The settings that already broadcast. Inserting, duplicating and moving slides anywhere, the active one and answered ones included. Appending an option or item, and reordering options or items (answers hold ids, not positions). Removing an option or item that has no answers. Any change to a slide that has no answers and is not the active one, deleting it included. Marking or changing the correct option, after a confirmation that names how many participants are re-scored (standings are already recounted, REQ059).
- **Refused while live.** Removing an option or item that has answers. Changing the type, answer mode or answer rules (scale range, a lower selection limit, a quiz time window) of a slide that has answers. Deleting a slide that has answers. Deleting the active slide. Adding or removing options on a quiz question that has opened (its first answer is final and its time counts, so the question has to stay the one the room started answering). Every refused edit is possible again after End, where the answers stay, or after Reset.
- **The server holds the rule.** For a live deck, `PATCH /presentations/:id` compares the stored slides with the incoming ones and refuses the forbidden changes with a machine-readable reason per change; the editor mirrors the rule only to explain it. `updatePresentation` re-derives `activeSlideIndex` from the id of the slide that was active, so no edit moves the room. A phone on an audience-paced deck likewise keeps its slide by id after a re-read.
- **The room gets the edit when it is saved.** A deck-changed frame goes to every client of the deck, phones and presenter screens alike, which re-read the deck through the existing `refreshDeckSlides` path. Nothing is announced: no banner and no toast on phones or on the stage. Selections, focus and drafts in progress survive the re-read. When the slide a phone is showing changed, a polite status message ("Question updated") is exposed to assistive technology without moving focus. When someone other than the viewer saved, the presenter's slide rail marks the changed slide with that person's name for a few seconds; the stage area shows nothing.
- **The editor explains every refusal where it happens.** On a live deck the editor's badge reads "Live" instead of "draft", and a persistent strip above the stage says that saved edits reach the room at once and that slides with answers can be reworded but not restructured. The slide list marks the active slide and shows each slide's answer count. A refused control stays visible, disabled, with its reason spelled out next to it (not only as a tooltip), and offers the way out: duplicate the slide to restructure it; switch to another slide before deleting this one; End or Reset for the rest. A wording change on an option or question that has answers saves, with a note that those answers now stand for the new text. A save the server refuses lists each refused change with its reason and offers to save without them or to go back; nothing typed is lost.
- **The ways in.** While live, the presenter's Deck menu shows "Edit (live)" instead of hiding the row. It, Preview's Edit and the edit link open the editor in a new tab, so the screen the room sees never shows presenter notes or a quiz's answer key, and saving in a live editor does not navigate to the presenter screen.

**Fallback.** If this is too much for one step, enforce A (refused on the server, explained on every way in) rather than keep today's state. The server rule and the deck-changed frame are the first pieces of B to build.

**Done when.** For a live deck, the presenter's Deck menu, Preview's Edit, the edit link, `/edit/<id>` and `PATCH /presentations/:id` behave as this decision says, a saved edit reaches phones and every open presenter screen without a reload, no edit changes which slide the room is on, no live edit removes an answer from a tally, score or export, and the gates `AGENTS.md` names are green.

**Out of scope.**

- Edit rights (owner or edit token, `requireEdit`) are not changed. This record is about deck status, not about who may edit.
- A survey-mode deck, which collects answers while still a draft (`acceptsSubmissions`), faces the same answer-orphaning question while it is a draft. This record covers the live status only.

**Note.** The editor's fixed "draft" badge (`src/pages/CreatePage.tsx:908`) misstates a live or ended deck under every option. It is a small fix that does not wait on this decision.
