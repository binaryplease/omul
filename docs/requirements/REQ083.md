## Description

An audience-paced deck can allow one device to complete it more than once; each pass is stored as its own set of answers rather than replacing the previous one.

## Notes

Defaults this requirement left open, as built:

- **A per-deck switch, off by default.** `allowRepeatPasses` is authored with the deck (create, PATCH, the editor's Pace section) and defaults to `false` on every schema that carries it, so a deck stored before it existed — and every deck that never turns it on — keeps exactly the one set of answers per device it had, a resubmission replacing it. It is in effect only on an audience-paced deck (`deckAllowsRepeatPasses()` in `server/schemas.ts`): on a presenter-paced deck it is stored but opens no pass, and the editor draws the switch only while Audience pace is selected. Switching to Presenter pace hides the switch and leaves the stored value as it was, so switching back shows it unchanged. Switching it off and pacing the deck back to the presenter both stop *new* passes only — a pass already opened stays open, since on a kiosk it belongs to the next person. It is public on the deck document, and a PATCH that moves it broadcasts `presentation.repeat-passes` so every phone redraws at once.
- **Hiding the switch under Presenter pace deviates from ADR-0025 on purpose.** ADR-0025 rule 1 (disable, don't hide) and rule 4 (no layout shift) would keep the switch drawn disabled with a reason. The owner decided that it appears only under Audience pace, with no disabled control and no reason line in its place. The Audience pace card's description names the option, so an author on Presenter pace can still find it. The deviation covers this switch only.
- **A pass is stored on every answer.** `votes` and `responseVotes` rows carry `pass`, a whole number from 1; a row written before the field existed has no such key and reads as `1`, a single first pass, with no migration. Because the store's where-clause reads the raw document — where such a row has no `pass` at all — a pass is never filtered on in a query; rows are narrowed to a pass after they are read back.
- **Starting a pass, and how many.** A device that has reached the deck's last slide is offered "Answer again" on the participant screen — reaching the end is what having finished means on a deck that is free to navigate and free to leave questions unanswered — and the control is drawn disabled with its reason on every earlier slide. The number of passes is unbounded.
- **A pass is opened by the server, and recorded, before anything is answered in it.** `POST /api/presentations/:id/passes` opens the pass after the latest one opened for the device and stores it in `participantPasses` (one row per deck and device; none for a device that never started another, since the first pass is always open). A kiosk waiting at the first slide for its next person therefore holds a pass of its own, and whoever answers there answers in it — never over the person before. It is always the next number, even when the latest pass holds nothing yet, because the last answer of one person and the next person's tap can cross in flight; a pass started and never answered in leaves no rows, so a device's passes in an export can skip a number.
- **Which pass an answer lands in** is one rule, `submissionPassFor()`, composed by the vote, the upvote and the scorecard: the first pass always, with no lookup at all; a pass the server opened for the device, whatever the switch says now; and any number that was never opened (a client that missed a reset, a hand-built request) the latest pass that was. An answer never opens a pass, so a drifted number lands in the same place however many answers follow it and one person is never split across two passes.
- **Each pass is its own set of answers.** Everything that was per device is per pass: a resubmission replaces only that pass's answer, a quiz answer is final only within its pass (the next pass answers again, on a blank scorecard), a word cloud's cap counts one pass's responses, a multi-select deselect and an upvote toggle reach only their own pass, and the duplicate fold treats an earlier pass's identical words as somebody else's.
- **Every pass counts as its own respondent** — one device's one pass, `respondentIdOf()` — on the results surface (`respondentCount`, a quiz's scoring), on the leaderboard (a row of its own), in segmented results (joined per pass), and in both exports: the workbook's Participants sheet has a row per pass and a `Pass` column, the Responses sheet a `Pass` column, the Summary counts respondents beside a `Repeat passes` row (the setting as of the export, like every setting on that sheet); the PDF's cover counts respondents and its roster lists each pass, a later one marked `(pass n)`. A first pass is named by the participant id itself, so a deck without repeat passes counts exactly what it always counted.
- **The breakdown's privacy floor counts people, not passes.** Segmented results hold back a group of fewer than five from a caller who cannot edit the deck; that floor counts distinct devices, so one person going through five times is five respondents and still one person, and never makes a group publishable. Counting devices undercounts people on a kiosk, which only ever holds back more — the fail-safe direction.
- **Turning it off part-way** stops new passes at once (the start route answers `400` with `refused: "repeat-passes-off"`, and the phone takes the control away) without stranding a device in a pass it was already handed, answered in or not yet.
- **Cascades take every pass.** A reset (REQ101) and a deck deletion (REQ146) erase by deck — every pass's answers and upvotes, and the record of which passes were opened; taking an answer down (REQ027) takes its upvotes from every pass. No account deletion reaches answers in this codebase — an answer belongs to a deck and a device, never to an account — so the deck-level cascades are the ones that apply. A participant surface remembers its pass per deck, so a reload lands back in it, and forgets it on a reset.
- **What stays per device.** A name stated on joining (REQ076) belongs to the device: every pass carries it and the roster lists the device once. On a shared kiosk on a deck that requires names, every pass therefore carries the first name stated; telling a kiosk's users apart by name is not what this switch does. The Q&A layer, the chat and reactions are deck-wide channels, not answers, and have no passes.
- **Out of scope**, as briefed: a cap on passes, per-pass comparison views, and presenter-driven decks.

**Known limits and follow-up, from the pre-merge review (2026-10-25).** None blocks this record; each is recorded so it is not rediscovered.

- **Repeat passes rank as separate rows.** An author who turns repeats on for a deck with a leaderboard accepts that one device can place more than once. The switch is off by default and only in effect on an audience-paced deck, and the kiosk case — each pass a different person — is what it is for, so a rule that refused this would refuse that case, not only somebody playing the board. Follow-up: on a deck that has a leaderboard slide, show the switch disabled with its reason (ADR-0025) rather than forbid the combination.
- **On an audience-paced deck the quiz time runs per deck, stamped by the presenter.** A quiz slide's `startedAt` is stamped per deck the first time the presenter's screen arrives on it (`withSlideOpenedOnce`, through `setSlide` and `startPresentation`, as on main), so the presenter paging onto a quiz slide that participants have already answered can re-score those earlier answers against the new start. Repeat passes make this easier to see, because every pass shares the one per-deck clock. Follow-up: quiz time per participant and pass.

## Updates

- 2026-10-21 — Repeat passes shipped. allowRepeatPasses (default false; in effect only on an audience-paced deck, via deckAllowsRepeatPasses()) is authored on create, PATCH and the editor's Pace section, public on the deck, and broadcast as presentation.repeat-passes. Every vote and response upvote stores pass (default 1, so answers stored before it read as a single first pass; narrowed after the read, never in the where-clause). Reset and delete erase every pass and the pass records; REQ027 deletion takes a response's upvotes from every pass. Participant screen: Answer again at the last slide (disabled with its reason before), a transport and a blank slide view per pass, the pass remembered per deck and forgotten on reset, and a repeat-passes-off refusal removing the control.
