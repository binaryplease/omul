## Description

As an operator of any instance of this application, I want the server to refuse to start outside development when the auth signing secret is unset, rather than silently signing sessions with a literal that ships in the published source, so that a deployment cannot reach production with every session cookie forgeable by anyone who has read the repository.

## Notes

Raised by a publication readiness check, **internal**. REQ164 recorded this in its "Related, and deliberately not folded in" paragraph and said plainly that it deserves its own decision; this is that decision written down as a requirement rather than left in another requirement's margin.

**What is there now.** `server/accounts.ts:134` resolves the Better Auth secret as `process.env.BETTER_AUTH_SECRET || DEV_INSECURE_SECRET`. The fallback is a constant in the tree. `docs/deployment.md` states the consequence in two places — that the placeholder ships in the open-source repository and that without the variable set every session cookie is forgeable — so the behaviour is documented, deliberate and correctly flagged where an operator reads it.

**Why documentation is not the remedy once the repository is public.** Today the fallback is a default that only someone with repository access can exploit, and the deployment supplies the real value through its own secret delivery, so the live instance is not affected. Publication changes the population: the literal becomes readable by everyone, and every self-hoster who misses one environment variable runs an instance whose administrator sessions can be minted by a stranger from a value they can read in the same repository they cloned. A warning in a deployment document is read by the operators who already read documents; the ones this protects are the ones who did not.

**The shape of the remedy, and why it matches its neighbour.** REQ164 resolves the compiled-in administrator allowlist by making it deployment-supplied and failing closed when it is absent outside development. The same posture applies here and for the same reason: an insecure value that is convenient in development must be unreachable in production by construction, not by discipline. Development keeps a working default so `mise run dev` and `bun test` need no setup; a non-development start with the variable unset is a fatal startup error naming the variable and how to generate a value, on the same pattern `OMUL_BASE_HOST` already uses for a malformed value.

**Ordering.** This belongs in the tree that crosses into the new repository (REQ165), not in a follow-up after the flip — the fallback literal is published the moment the tree is, and a later fix does not reach the clones. It does not block REQ161's license instrument and can land in parallel with REQ163 and REQ164.

**Done when.** Starting the server outside development with `BETTER_AUTH_SECRET` unset is a fatal error that names the variable; the development default remains and is reachable only in development; no placeholder secret value is used to sign anything in a non-development process; and the repo's gate and test task (both named in `AGENTS.md`) stay green.
