## Description

A theme — colors, fonts, logo — can be defined, stored and applied to decks exactly as a built-in one is.

## Updates

- 2026-08-10 — A theme can now be defined on the deck and applied exactly as a built-in one is: same 'theme' field (a sixth value, 'custom'), same boundary, same PATCH, same <DeckThemeScope> wrapper, same surfaces — no second theming endpoint and no second code path. DeckBrandSchema in server/schemas.ts stores it (name + accent/canvas/text as strict #rgb/#rrggbb + font id, every field defaulted per ADR-0029), deckBrandFor() is the single read site and refuses anything outside the grammar to the house theme's own value, the way deckLogoFor() refuses a URL. The superseded invariant that a theme's appearance never rides the wire was corrected in server/schemas.ts and docs/api.md: a built-in theme still ships only its id, an authored one is the deck's own content and is validated as narrowly as a colour can be. Three authored colours become the whole sixteen-token palette in both colour schemes — deckBrandAppearance() derives the rest along the canvas → text axis and derives the scheme the organizer did not author from the canvas's hue, so the reader's light/dark preference stays theirs. Authored in the editor's Presentation settings beside the picker, with the brand kept while a built-in theme is tried on. A guard in scripts/guard-frontend-conventions.ts fails the build on a surface reading themeBrand raw. Tests: server/theme.schemas.test.ts, server/theme.integration.test.ts, src/components/DeckTheme.test.ts.
