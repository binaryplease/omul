## Description

As a presenter on the presenter screen (`/present/<id>`), I want the way I give the room its join code, link and QR code to follow how I actually invite people to join and vote — before the start, at the start, between slides and while live — so that the code is on screen when the room needs it, out of the way when it does not, and the QR code is there when I reach for it, without a switch whose purpose I have to guess.

## Notes

**Why this record exists.** REQ190 rebuilt the presenter top bar into three zones and is done. The owner questions two parts of it. First, the join-bar show/hide switch: it is unclear when and why a presenter would press it — either the screen has room and the join code should be shown, or it has none and the code should collapse into something like a context menu. Second, the QR code now takes two taps. Both are to be challenged by a UI/UX concept stage against the presenter's whole flow of getting the audience to join and vote, decisions derived from that, and the presenter screen rebuilt to them. REQ190 and REQ073 stay done; this record is the re-decision.

**What the join-bar switch is today.** A per-deck `showJoinBar` boolean, default `true` on every schema that stores or returns it (`server/schemas.ts:5570`, `:6480`), writable only through `UpdatePresentationSchema` (`server/schemas.ts:5401`) on `PATCH /api/presentations/:id` under owner-or-edit-token authorization. The PATCH broadcasts `presentation.join-bar` (`server/services/presentations.ts:1020`), which `src/store/useSessionSocket.ts:81` hands to `applyJoinBarSetting` (`src/store/session.ts:678`); the presenter writes it through `setJoinBarShown` (`src/store/session.ts:546-551`). Every presenter screen of the deck therefore draws the same header. On the presenter screen (`src/pages/PresenterPage.tsx`, header `:1002-1290`) the switch is the first item of the Screen group (`:1060-1074`, `PanelTop`/`PanelTopDashed`, `aria-pressed={!joinBarShown}`), labelled by `joinBarButtonLabel` (`:698-709`): "Hide the join bar — the join code stays valid and the room can still join" / "Show the join bar — put the join code and share controls back on this screen", disabled with its reason for a viewer who cannot edit. Its only effect is whether the Door group is drawn (`:1046-1048`): the join-code copy button and the Share menu (`src/components/ShareCluster.tsx:151-202`). Hiding it therefore also removes the presenter screen's only route to the join link, the QR code, the embed code and the edit link. The join code, `/join/<code>`, status and submissions never read the field (REQ073's log). `docs/api.md:2784-2798` describes the bar.

**Where else the room sees the code.** The presenter screen is both the presenter's console and the view the room is shown — there is no separate projector route among the routes (`src/router.ts:16-54`) — so the Door in the header is on the projector whenever the presenter screen is. The one other place is the **instruction slide** (REQ065, REQ118): `PresenterSlideView` passes `joinCode`/`joinUrl` to `ContentSlideView` (`src/components/PresenterSlideView.tsx:186-188`), which draws a QR code at 200px, the code at `text-5xl` and the URL (`src/components/ContentSlideView.tsx:249-321`). It is an authored slide: the bundled templates open with one (`server/templates.ts:68`, `:111`, `:193`, `:238`), and a deck has one only if its author adds it. It is drawn whatever `showJoinBar` says. While the screen is blanked (REQ109) the whole page, header included, is replaced by the curtain (`src/pages/PresenterPage.tsx:844`), which shows no join code. No other slide, overlay or panel shows the code or a join instruction.

**What the QR code takes today.** One tap on the Share caret in the Door group opens the Share menu; a second tap on its "Show QR code" row (`src/components/ShareCluster.tsx:96-100`) closes the menu (`:195`) and toggles `showQr` (`src/pages/PresenterPage.tsx:893`). The overlay (`:1292-1327`) is a "Scan to Join" panel with a 220px QR code, `<host>/join/<code>` and a Close button; a click on the backdrop closes it. The overlay cannot be reached while the join bar is hidden.

**How a participant gets in today.** Three ways: scanning a QR code, which opens `/join/<code>` directly; opening that link, which the router sends straight to the participant screen (`src/router.ts:80-81`); or typing the code at the join page (`#join`, `src/pages/JoinPage.tsx`, reached from the home page's "Join with Code", `src/pages/HomePage.tsx:246`), which prompts "Enter the 6-digit code shown on screen" (`:170`) and can scan a QR code with the camera where `BarcodeDetector` exists (`:61-102`). A participant may join a draft deck: they wait on "waiting for the presenter" until it starts (`src/pages/ParticipantPage.tsx:561-572`), and in survey mode they answer regardless of status (`:560`). So the room can be let in before the start, at it, and at any point while live; the bar draws the Door the same way in draft, live and ended (REQ190's design: the layout never moves), and nothing on the presenter screen changes with the moment in the flow except the instruction slide when one is the active slide.

**Desired outcome.** The presenter screen offers the room's way in — join code, link and QR code — through one design the UI/UX concept stage derives from the presenter's whole flow of inviting the audience to join and vote and records in these Notes, and the screen is built to it.

**Done when.** The concept stage's decisions are recorded in these Notes (including what becomes of `showJoinBar`), and in a browser at 360px, 768px, 1280px and 1536px wide, for a deck in each of the draft, live and ended states, as its editor and as a viewer without edit access, the presenter screen follows them while still meeting every constraint below; `mise run check` and `mise run test`, as `AGENTS.md` declares them, apply unchanged.

**Defaults, stated flat.**

- The design is left open here. The concept stage decides it, including how many taps the QR code takes and whether the per-deck `showJoinBar` setting stays, changes meaning, or is retired. If it changes meaning or is retired, REQ073 (`source: BR073`) gets an update-log entry recording that, not a rewrite, and `docs/api.md`'s join-bar section and the `presentation.join-bar` row follow the decision.
- Every other REQ190 constraint stays: the Back link, the deck title and the lifecycle button (or the View only marker) visible and uncovered at every width from 360px; no horizontal scrolling in the bar or the page; every capability the bar offers today still reachable; each control's disabled-with-reason state for a viewer without edit access and its `aria-label`/`title` kept, unless the decision changes that control itself.
- What the join code, the join link and `/join/<code>` admit stays as it is: whatever is decided about showing the code changes nothing about who may join.

**Out of scope.** The editor (`src/pages/CreatePage.tsx`), the participant screen and the join page beyond reading them, and the slide rail (`src/pages/PresenterPage.tsx:1333-1347`). The instruction slide's own layout is not reworked here, though the design may rely on it.

**Note.** `docs/api.md:2786-2788` still describes the bar as "inline on wide screens and on its own row below the header otherwise", the REQ189-era layout; REQ190 made that false and did not touch the doc, so whoever touches the join-bar section takes that sentence up too.

**Decisions (UI/UX concept stage, 2026-10-11) — build exactly this.** These were drawn as an interactive concept at 360, 768, 1280 and 1536px, for draft, live and ended decks, as editor and as view-only, and measured there with no overflow in any of the 24 combinations. Nothing below is an option. A line written `:NNN` is in `src/pages/PresenterPage.tsx` as it stands today. Everything REQ190's Design says still holds unless a decision here changes it.

*The idea.* The presenter screen is also the projector, so the Door is the room's standing invitation and not a setting. It is drawn whenever the deck is on screen. The join-bar switch is retired. The QR code is one tap, beside the code, and it opens at a size the back row can scan.

*The flow these decisions serve.*

- **Doors open (draft).** The deck's welcome slide (REQ065), if it has one, carries the QR. If it doesn't, the presenter taps QR, and the overlay shows the code, the address and a head-count that rises as people join.
- **Start.** Esc or one clicker press closes the QR, then the presenter presses Start. Nothing in the bar moves.
- **Asking the room to vote (live).** Phones follow the slide on their own. Anyone not yet in reads the Door: "Join at `<host>` · code" from 1536px, the code alone below that.
- **Latecomers.** One tap on QR, then one clicker press takes it down without changing the slide.
- **End.** The bar is unchanged (REQ190's layout never moves). The Door stays, because a Restart lets the same code in again.

*Decision 1 — the join-bar switch is retired.*

- **Why.** Nobody has a moment in this flow where hiding the code is the right move:
  - Hiding it admits nobody fewer. Its own label says the code stays valid, and the code is on every phone and every forwarded link already.
  - It also removed the presenter's only route to the link, the QR, the embed code and the edit link.
  - The owner's "no room" branch never occurs on this screen. Below `xl` the console has a line of its own, and at 360px the Door, Screen and Panels use about 291 of 328px, the same as today.
  - When the room should see nothing, the tool is Blank (REQ109), which already takes the whole page, Door included, off the projector.
  - So the code is never folded into a menu, at any width.
- **Presenter screen.**
  - Delete `joinBarShown` and `joinBarButtonLabel` (`:698-709`), `handleSetJoinBarShown` and its docblock (`:460-474`), the `setJoinBarShown` selector and the `PanelTop`/`PanelTopDashed` imports.
  - Delete the switch's `<button>` in the Screen group (`:1061-1074`). The Screen group keeps `role="group" aria-label="Shared screen"` and holds Blank alone, unchanged.
  - Draw the Door unconditionally: `<ShareCluster variant="menu" controls={shareControls} />`, without `joinBarShown &&` (`:1046-1048`).
  - Rewrite the comments at `:1043-1059` so they say the Door is always drawn and the Screen group is Blank only.
- **Client.**
  - `src/store/session.ts`: remove `setJoinBarShown` and `applyJoinBarSetting`, both their types (`:158`, `:195`) and their bodies (`:546-551`, `:678`).
  - `src/store/useSessionSocket.ts`: remove the `presentation.join-bar` subscription (`:78-81`) and its import (`:35`).
  - `src/api.ts`: remove `showJoinBar` from the `updatePresentation` input type (`:521-522`).
  - The client then neither reads nor writes the field.
- **Server: unchanged in this slice.** `showJoinBar` stays accepted by the PATCH, stored, returned, and broadcast on `presentation.join-bar`, with nothing reading any of it. `server/join-bar.integration.test.ts` keeps passing as it is. Removing the field is the first follow-up below.

    - the presenter screen always draws the join code and its share controls, and no setting hides them;
    - the field and the frame are still accepted, stored, returned and sent, but no client reads them, and their removal is pending.
  - That also retires the stale REQ189 sentence the Note above names.

*Decision 2 — the QR code is a direct control in the Door, one tap.*

- **The Door group.** `ShareCluster` (`src/components/ShareCluster.tsx`) draws the group in this order:
  1. the join-code button;
  2. the `w-px h-5 bg-border` divider;
  3. **the QR button**;
  4. the Share caret.
- **The QR button.**
  - It is the descriptor's `qr` action, drawn as a `BAR_GROUP_ITEM` with `<QrCode size={16} aria-hidden />`, `aria-haspopup="dialog"`, and `aria-label`/`title` set to the action's `title` ("Show QR code").
  - It is enabled for every viewer, as the menu row was.
  - Pull it out with `actions.find((action) => action.key === "qr")`. `buildShareControls()` keeps the action, so the descriptor stays the single source of the set.
- **The Share menu.**
  - Its rows are every action except `qr`: Copy join link, Copy embed code, then the divider and the edit link for an editor.
  - Drop `qr` from the rows' close-first rule.
  - `shareMenuLabel()` becomes `Share — copy the join link${editLink ? ", the embed code or the edit link" : " or the embed code"}`.
  - The heading stays "Share · join <code>".
- **The host in the bar, from `2xl`.**
  - `ShareJoin` gains `host: string`, and `buildShareControls()` gains a `host` parameter. PresenterPage passes `window.location.host`.
  - The join-code button's label span stays `max-sm:sr-only text-xs text-text-muted` and holds `<span className="2xl:hidden">Join:</span><span className="hidden 2xl:inline">Join at <span className="inline-block max-w-56 truncate align-bottom font-mono text-text">{join.host}</span></span>`.
  - The code, the `Copy`/`Check` icon and `title="Copy join code"` are unchanged. The guard in `scripts/guard-frontend-conventions.ts` needs no change.
  - Measured in the concept: identity keeps 366px at 1280px in the widest case (the same as REQ190), and 486px at 1536px with the host shown.
- **The overlay (`:1292-1327`), room-sized.** It is replaced by:
  - **Backdrop**: `fixed inset-0 z-50 flex items-center justify-center bg-void/90 backdrop-blur-sm p-4`. A click on it closes the overlay.
  - **Panel**: `role="dialog" aria-modal="true" aria-labelledby` pointing at the heading, with `slide-in flex w-full max-w-2xl lg:max-w-5xl max-h-full flex-col lg:flex-row items-center gap-4 sm:gap-5 lg:gap-10 overflow-y-auto rounded-2xl border border-border bg-surface-raised p-6 sm:p-10 text-center lg:text-left shadow-lg`. Content clicks stop propagation, as today.
  - **QR**: `<div className="flex-none rounded-xl bg-white p-3 sm:p-4 *:size-[min(44vh,calc(100vw-6rem),28rem)] lg:*:size-[min(60vh,28rem)]"><QRCodeDisplay url={`${window.location.origin}/join/${pres.code}`} size={448} /></div>`.
  - **Text column**: `flex flex-col items-center lg:items-start gap-4 sm:gap-5`, holding:
    - `<h3 className="text-2xl sm:text-4xl font-semibold">Scan to join</h3>`;
    - the address line, `flex flex-wrap items-baseline justify-center lg:justify-start gap-x-2 text-sm sm:text-lg text-text-muted`, holding "or go to" and then `<span className="font-mono text-accent-text [overflow-wrap:anywhere]">{host}<wbr /><span className="whitespace-nowrap">/join/{pres.code}</span></span>`, so the address can only break before `/join`;
    - the code: `<p className="text-xs uppercase tracking-wider text-text-muted">Join code</p>` over `<p className="font-mono font-bold text-4xl sm:text-6xl tracking-widest text-text">{pres.code}</p>`;
    - a footer row, `flex flex-wrap items-center justify-center gap-4`, holding the head-count `<span className="inline-flex items-center gap-1.5 font-mono tabular-nums text-sm text-text-muted"><Users size={16} aria-hidden />{participantCount} in the room</span>` and the Close button (`btn-secondary text-sm`).
  - The old "Point your phone camera" line goes.
  - **Sizes measured in the concept**:

    | Viewport | QR (px) | Panel height (px) |
    |---|---|---|
    | 360 × 740 | 264 | 586 |
    | 768 × 1024 | 448 | 857 |
    | 1280 × 720 | 432 | 546 |
    | 1536 × 864 | 448 | 562 |

    No case scrolls, and the address stays on one line.
- **Opening and closing.**
  - On open, focus goes to Close (`autoFocus`).
  - `onShowQr` keeps the opener in a `useRef` (`document.activeElement`), declared with the other hooks above the early returns. One `closeQr()` sets `showQr` false and focuses that element. The backdrop, Close and the keys below all call it.
  - In `handleKeyDown` (`:613-630`), before the owner/live guard: `if (showQr) { if (["Escape", "ArrowRight", "ArrowDown", "ArrowLeft", "ArrowUp", " "].includes(e.key)) { e.preventDefault(); closeQr(); } return; }`. Add `showQr` to the dependency list.
  - So a clicker press takes the QR down and never pages the deck behind it.
- **Viewer without edit access.** Same Door and same QR. Their Share menu lacks the edit link, as the descriptor already decides.
- **Blanked screen.** Unchanged: the curtain's early return draws neither the Door nor the overlay.

*Decision 3 — the presenter screen invites the room through the Door and the QR, and does nothing louder.*

- **More.**
  - The Door is always there.
  - It names the host from `2xl`, the width a 1920px projector runs at, so a latecomer can type the code in rather than having to scan.
  - The QR is one tap, room-sized, and shows a live head-count, so the presenter can see the room fill.
- **Less.** One switch fewer.
- **Unchanged.** Nothing else on the presenter screen changes with the moment in the flow. Draft, live and ended still change only what REQ190 lists.

*Roads not taken.*

- **Keep the switch, moved into the Share or Deck menu.** Quieter, but it still hides nothing that matters.
- **Fold the code into a menu on narrow widths.** No width from 360px lacks the room.
- **Hide the Door on an ended deck.** The layout stays fixed, and Restart reuses the code.
- **Show the QR automatically in draft or on Start.** It would cover a slide the author chose.
- **A `Q` hotkey for the QR.** The screen has no shortcut set beyond paging, and a clicker can't send one.
- **Retire `showJoinBar` on the server in this slice.** It would roughly double the change, mostly the 331-line integration test, for no visible effect.

*Recommended follow-ups (not in this slice).*

1. **Retire `showJoinBar` server-side** (`source: internal`): `server/schemas.ts:5401`, `:5570`, `:6480`; the broadcast at `server/services/presentations.ts:1012-1024`; `server/join-bar.integration.test.ts`; and the frame's row in `docs/api.md`. Object schemas strip unknown keys, so stored decks read cleanly without the field.
2. **Editor.** A new deck, or a deck whose first slide is not an instruction slide, could be offered a welcome slide, because that is where doors-open is meant to be carried.
3. **Participant screen.** The draft wait screen could show the live head-count, so an early joiner sees the room fill too.
4. **Slide types.** An instruction slide's QR could be a room-sized variant (today it is 200px). A poll or quiz slide could carry an optional "join at" footer that an author places on the slide itself.

**Known limits and follow-up, from the pre-merge review (2026-10-25).** None blocks this record; each is recorded so it is not rediscovered.

- **The QR dialog does not hold Tab.** Tab from "Close" leaves the dialog. Any key closes it and returns focus (the clicker rule), so Tab never lands behind a dialog that stays up; the dialog keyboard contract is REQ211.
