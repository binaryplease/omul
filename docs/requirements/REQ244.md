## Description

As a deck author, I want to choose a ready-made background for a slide or for the whole deck from a set that ships with omul, so that a slide can look designed without my having to find, host and paste a picture.

The background controls (the "Style" group, and the canvas controls of REQ243 once they exist) offer a gallery of built-in backgrounds: gradients and a small set of pictures. Picking one applies it to the slide; a second action applies it to every slide of the deck. A built-in background is stored on the slide by a stable identifier, not as a copied URL, so a later build can improve the asset without breaking decks. Text over any built-in background keeps the legibility REQ071 already guarantees for a pasted picture.

**Done when.** A slide and a whole deck can each be given a built-in background in one click, and the choice survives reload, presenting, the participant view, shared results and every export that renders the slide. Each built-in background passes the existing contrast checks with the house theme and every other built-in theme, in both colour schemes. Every bundled asset is served from omul itself, and its licence permits redistribution in this repository, recorded next to the asset. A deck stored before this change renders unchanged. `mise run check` and `mise run test`, as `AGENTS.md` declares them, apply unchanged.

## Notes

Today a slide's background is a colour (REQ070) or a picture URL the author pastes (REQ071, `backgroundImage` in `server/schemas.ts`, rendered by `src/components/SlideBackground.tsx` under a scrim). omul uploads and stores no media by design, so a picture has to live at a public address before it can be used. The built-in themes (REQ079) carry a palette and a soft radial wash, not a backdrop.

Out of scope: uploading one's own picture. That would make omul store media for the first time and is an architecture decision of its own. Assets are vendored into the build and never fetched from a third-party host (`AGENTS.md`, the one-external-dependency rule).

The new stored field needs a `.default(...)` like every other non-identity `Stored*` field (`AGENTS.md`, Schemas).
