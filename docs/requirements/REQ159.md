## Description

As an operator of an omul instance, I want the cost of rendering any deck a caller is allowed to author to be bounded and roughly proportional to its size, so that one request for a PDF export cannot stall every other request the server is serving.

## Notes

Defect, **internal** — raised by a security review of the branch that shipped the PDF export (REQ096), not by a business need. Availability only: nothing is disclosed, nothing is lost, and the export itself is correctly authorized.

**What was wrong, in two halves.**

*The renderer's cost was quadratic in one unbroken run.* `wrapLine` in `server/deck-pdf.ts` breaks a word too wide for its column by repeatedly asking `fittingPrefix` for the longest prefix that fits and slicing it off the front. `fittingPrefix` binary-searches, but it was handed the *whole* remaining run each time, and `widthOfTextAtSize` measures every character of the string it is given. So each of the ~n/300 lines emitted cost O(n·log n) measurement, and the whole break cost Θ(n²·log n).

The docblock there records an earlier round of the same defect — a walk down from the end, O(n³), where 4,000 characters took 2.8s. Replacing that walk with a binary search removed one factor of n and left the dominant one, and the test guarding it used a budget loose enough to pass anyway.

*The fields feeding it were uncapped.* `SlideSchema.question`, `.body` and `.mediaUrl` were plain `z.string()`, and neither `CreatePresentationSchema.slides` nor `UpdatePresentationSchema.slides` bounded the array. So the input to the quadratic path was unbounded as well as the path being quadratic.

**Reachable with no account.** `POST /api/presentations` returns a self-issued `creatorToken`; `PATCH /api/presentations/:id` writes the oversized slides and carries no rate-limit guard; `GET /api/presentations/:id/deck.pdf` renders. Bun serves on one thread, so this was not a slow request but a stalled process — every other caller queued behind it.

Measured on the branch before the fix: one slide with a 200,000-character unbroken run took **33.1s**, ten such slides **285.3s**. The same 200,000 characters spaced into ordinary words took 417ms, which is the control that names the unbroken-token path as the cost.

**What closes it.**

1. *Bound what any one measurement looks at.* `wrapLine` hands `fittingPrefix` a window of `WRAP_PROBE_CHARACTERS` rather than the whole tail, and widens that window only while the whole of it still fits — which is the only case where a wider window could give a different answer. The break therefore lands exactly where an unbounded search would have put it, at any window size, and the cost becomes linear. Verified as identity, not as an argument: 4,320 differential comparisons of the old and new wrappers across every font, size and column width the renderer uses, and across alphabets chosen for the narrowest and widest WinAnsi glyphs — zero divergence.

2. *Bound what may be written.* Every authored string a slide carries, and every list of them, held at the write boundary by `SlideInputSchema` and composed by both doors slides arrive through:

   - `SLIDE_TEXT_MAX_LENGTH` (5,000) — the prose fields: `question`, `body`, `notes`.
   - `SLIDE_MEDIA_URL_MAX_LENGTH` (2,048) — the address fields: `mediaUrl`, `backgroundImage`.
   - `SLIDE_ITEM_TEXT_MAX_LENGTH` (500) — every authored *row*: an option's text, a ranking or points or grid item's, a scale statement's, an accepted quiz answer's, a form field's label and each of its choices, a scale's or grid axis's end labels, and `mediaAlt`.
   - `SLIDE_LIMIT` (200) on the slide array, `SLIDE_OPTION_LIMIT` (50) on `options` and `SCALE_LABEL_LIMIT` (20) on `scaleLabels` — the two row lists that carried no ceiling at all. Every other row list was already count-capped by its own feature's constant, which `SlideInputSchema` re-composes rather than restates.

The caps live on a `SlideInputSchema` rather than on `SlideSchema` itself, because that schema is also what every *stored* deck is re-parsed through on the way out of the document store. Tightening the stored shape would not shorten one oversized field already on disk — it would make the deck holding it unreadable, which is answering a denial-of-service defect by denying service. This is the split the file already used for a deck's `title`: capped on the create and the patch, plain `z.string()` on `StoredPresentationSchema`.

**What this requirement does not cover.** The export routes are still unthrottled and the rendered document still has no page ceiling, so the remaining worst case is a *legal* deck at every cap — measured at 5.8s of single-threaded CPU for 200 slides carrying every field at its ceiling. That is a bounded linear cost rather than an unbounded quadratic one, and it is a separate finding of the same review with a different remedy (a guard on the export routes, and a `413` past a page ceiling). It is not folded in here.

A slide's `id` is the one authored string left plain. It is an identity rather than something drawn, so capping it would buy no rendering bound while risking a hand-built deck's ids being refused on save.

**Correction — the first cut of this did not meet the criterion above.** It capped the three fields the original review named (`question`, `body`, `mediaUrl`) and bounded the slide array, and recorded that the remaining nested authored text — an option's `text`, a ranking or grid or points item's `text` — was "no longer an amplification vector" because rendering it had become linear. That was wrong, and the follow-up review — logged below — was right to refuse it: a linear cost over an *unbounded* input is still an unbounded cost. `options` in particular had neither a length cap on its rows nor a count cap on the array, and the published attack worked verbatim with one word changed — `options[0].text` for `question` — buying ~60s of wedged event loop from a single request. The bound is only a bound if it covers every string the renderer draws.

## Updates

- 2026-08-14 — Filed and closed together. `wrapLine` now measures a bounded, self-widening window instead of the whole remaining run (`WRAP_PROBE_CHARACTERS` in `server/deck-pdf.ts`), and the first-word-on-a-line case no longer measures a candidate whose width it discards. `SLIDE_TEXT_MAX_LENGTH`, `SLIDE_MEDIA_URL_MAX_LENGTH`, `SLIDE_LIMIT` and `SlideInputSchema` bound `CreatePresentationSchema.slides` and `UpdatePresentationSchema.slides` in `server/schemas.ts`; the stored shape is deliberately left permissive so decks written before the ceiling still read back. Measured, same machine and same harness as the report: 200,000-character unbroken run 33.1s → **298ms**, ten such slides 285.3s → **2.8s**, both output files byte-for-byte the same size as before; an ordinary 20-slide deck 23ms → 29ms. Over HTTP the attack `PATCH` is now refused `422` at the body, and a deck at every cap exports in 1.75s. Tests: the linear-time guard is now a scaling assertion (quadruple the input, assert well under quadruple the ratio) that the pre-fix renderer misses by an order of magnitude, plus a seam test that reads the drawn text back off the page and asserts every character survives the break in order, plus the cap and stored-still-readable cases in `server/schemas.test.ts`.
- 2026-08-14 — Follow-up review (NST9039) found the exploit survived in a field the audit had not named: options[].text had no length cap and options no count cap, so the published payload still bought ~60s of wedged event loop with one word changed. Closed properly this time — SLIDE_ITEM_TEXT_MAX_LENGTH (500), SLIDE_OPTION_LIMIT (50) and SCALE_LABEL_LIMIT (20) added, and SlideInputSchema now bounds every authored string the export draws (options, ranking/points/grid items, scale statements and end labels, quiz answers, form field labels and choices, grid axis titles, mediaAlt, backgroundImage, notes) plus the two arrays that carried no ceiling at all. Same input-side split as before: SlideSchema is untouched, so a deck already stored above a row ceiling still reads back, and there is a test for it. Verified: every payload the review published is refused at the write boundary, an ordinary 50-option poll is still accepted, and the worst deck the caps now permit renders in 5.8s (an 8.75 MB request body) instead of without limit. Also corrected the linear-time test's comment, which credited the absolute wall-clock bar with a catch only the ratio assertion makes.
- 2026-08-14 — Review fix: the caps now have a client half. The editor enforces them at the input (maxLength on every authored prose/row/URL field, add-option and add-slide held at SLIDE_OPTION_LIMIT/SLIDE_LIMIT with the canvas add tool disabled with its reason), and the save path runs slideWriteRefusalFor (server/schemas.ts, same SlideInputSchema the boundary parses with) before the PATCH — a refusal now names the slide and the field and selects the slide, instead of surfacing as a generic banner. That named refusal is also the way back for a deck stored before a cap existed: it still reads (stored shape stays uncapped, unchanged), and its author is now told exactly what to trim instead of finding every save of it refused with no reason.
