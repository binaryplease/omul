## Description

As a presenter who made presentations without an account, I want the home page to tell me they live only in this browser and to offer me an account, so that clearing the browser's data does not lose them for good.

## Notes

**What happens today.** A presentation created without an account is held by one thing: its edit token, in this browser's `localStorage` under `TOKEN_KEY` (`src/storage.ts`). The server stores only the token's hash, so a browser whose data is cleared loses every such deck with no way back. The way out already exists — email sign-up and sign-in through Better Auth (`src/auth.tsx`), after which `claimLocalPresentations()` in `src/api.ts`, called from `src/pages/HomePage.tsx`, attaches every locally held deck to the account — but nothing on the home page says so.

**Desired outcome.** On the home page, a browser that is not signed in and holds at least one presentation sees a notice saying the presentations are stored only in this browser, with a control that opens the existing sign-in dialog. Which offer it makes depends on whether this client has observed a session in this browser — on the home page or on any page with the header's account controls: a browser that never had an account is offered to create one (the dialog opens on "Create account"), and one that has had an account is asked to sign in to keep these presentations (the dialog opens on "Sign in"), since "Create account" would refuse the address it already registered. Signing in either way adopts the decks (below) and removes the notice. After a sign-out the adopted decks are no longer listed, so a signed-out browser lists only what is held by it alone — a deck made after signing out is exactly what the notice is for, and it is offered again with the sign-in wording. The notice is an offer, never a gate: it can be closed, the close is remembered in this browser, and nothing on the page is blocked while it is shown.

**Adoption.** A deck the account now owns after the claim on sign-in (`claimLocalPresentations()`, the claim answered 200 — newly claimed or already the account's) is adopted: this browser forgets its edit token. After a sign-out it is no longer listed on the home page and cannot be edited or deleted from this browser; signed in again it is listed and fully usable through the account. Only a success drops the token: a deck another account or a workspace owns (409) is collaboration reached through an edit link and keeps its token, and a refused or failed claim proves nothing and keeps it too. The token stays valid server-side, so an edit link already handed out keeps working for its recipients — retiring it on claim is a server change and out of scope. A consequence: the presenter screen's edit-link control asks the token map, so from this browser it is not offered for an adopted deck (the share cluster shows the join code, Link, QR and Embed, but no Edit Link), as it already is not for an owner on a second device; sharing with another account (REQ075) is the account's way. A signed-out browser whose decks were all adopted holds no local deck, so it is not shown the notice either.

**Done when.**

- A signed-out browser that holds one or more presentations and has not closed the notice sees it above "Your Presentations"; one with none, a signed-in one, or one that closed it, does not, and it is not drawn while the session or the list is still loading.
- In a browser in which no session has been observed, the notice offers to create an account and its action opens the sign-in dialog on "Create account"; in one in which a session was observed before (on any page with the header, such as `/workspaces`), it asks to sign in and its action opens the dialog on "Sign in". After signing up or signing in, the notice is gone and the decks are owned by the account; after signing out, those decks are not listed and no notice is shown for them.
- After signing out, a deck the account adopted is not listed on the home page and its editor does not open for this browser; signed in again, it is listed and its editor opens. A deck the claim answered 409, 4xx or a network error for keeps its local token.
- Closing the notice keeps it closed across reloads of this browser.
- The notice's words come from `src/i18n.ts` and exist in every language the dictionary carries; the home page draws them in English, like the rest of its chrome.
- The notice composes the shared primitives in `docs/frontend.md` (lucide icons, `ICON_BUTTON_HOVER`), and its close control carries an accessible name.

**Known limits.** The record that picks the sign-in wording is written in the browser when this client observes a session, so it covers sign-ins from the release that added it on. A browser that was signed in before that release and signed out before any page with the header saw the session carries no record, and is offered "Create account"; its "Create account" refuses the address already registered, and the dialog's Sign in tab is one click away. Decks claimed before the adoption change kept their local tokens, so such a browser still lists them while signed out and is offered the notice for them; the next sign-in that reaches the home page re-claims them, which drops the tokens. Neither can be closed on the client: a signed-out browser is never told whether a deck it holds a token for has been claimed, because `creatorId` must never reach clients. Likewise a deck reached through an edit link to another account's deck (its claim answered 409, so it keeps its token) counts as a listed local deck; telling those apart is not part of this requirement.

**Out of scope.** A passwordless recovery-email mechanism or any new server endpoint; reminders anywhere but the home page; a redesign of the sign-in dialog.
