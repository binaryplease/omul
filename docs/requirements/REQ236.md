## Description

As a participant whose answer was still on its way when the presenter ended the deck or deleted the slide, I want to see what the rest of the room sees, so that I am not shown an English error page and a "Try again" button that leads to an empty code entry.

The vote route answered both cases with a `400` and only its English `error` text ("Cannot vote – presentation not live or slide not found"). That body had no `refused` code, so the participant page treated it as an unexpected failure. It replaced the room's screen with that text and an English "Try again" that led to `/app#join`, even after the `ended` frame had arrived.

- **Deck ended (or otherwise not accepting answers):** the vote route answers `400` with `refused: "presentation-not-live"`. The participant sees the ended screen every other participant sees, plus a notice in the deck's language that the answer was not accepted.
- **Slide gone:** the vote route answers `400` with `refused: "slide-not-found"`. The participant stays in the deck on its current state and gets the same kind of notice. No full-page error is shown.
- **The error screen that remains** for unexpected failures shows its text and button in the deck's language whenever the deck is known. The button reloads the deck in place. Without a deck, when the join lookup itself failed, the screen keeps the lookup's own message and its way back to the join form, in English like that form.
- **Unchanged:** the four stated refusals (REQ054, REQ057, REQ111, REQ226) and how they are shown (REQ232, REQ234). A value the slide does not take and a deck that does not exist still answer `400` with the `error` text alone.

## Notes

Defect, **internal**: Re-Test D, D1. The setup was a German deck in Chrome at 390 × 844, with the vote delayed 6 s while the presenter clicked "End" inside the delay. The slide-deleted path was not exercised there and is covered by tests. REQ232 had listed the English "Try again" as left open.

- **Wire:** `DECK_MOVED_ON_CODES` in `server/schemas.ts` holds `presentation-not-live` and `slide-not-found`. They ride in the same `refused` field as `VOTE_REFUSAL_CODES` but are kept as a separate vocabulary: they mean the screen is behind the room, not that a rule refused the answer, and the client answers them differently. `presentation-not-live` is the name the timer route already uses for the same fact (REQ227). `submitVote` returns them where it used to return `null`. `cli/protocol.ts` restates no refusal vocabulary and the CLI does not vote, so `cli/` is unchanged.
- **Client:** `ApiError.movedOn` carries the code. `routeSubmissionFailure` has a third report, `movedOn`, with wording keyed on the code (`answerNotAcceptedDeckEnded`, `answerNotAcceptedSlideGone`) and never on the English `error`. The slide view toasts it and calls `onDeckMovedOn`. The live page wires that to the store's `catchUpWithRoom`, which re-reads the deck through the join lookup and patches the status, the slides and the active slide, without raising `loading`. Each is patched only if no frame moved it while the read was in flight. `participantErrorScreen` in `src/pages/ParticipantPage.tsx` decides the remaining error screen's text, button and destination.
- **Tests:** `server/vote-moved-on.integration.test.ts` pins both codes over HTTP (ended live deck, draft deck, ended survey, slide deleted by a save) and pins that a bad value and an unknown deck stay uncoded. `src/components/ParticipantSlideView.test.ts`, "an answer the deck moved on under keeps the participant in the deck (REQ236)", answers a German deck's live transport with each code. It routes the failure as the page does and checks three things: no page error, the deck's status or slides caught up, and the notice in German. That covers D1 with the `ended` frame received and with it missed. `src/store/session.test.ts` pins the in-flight guards of `catchUpWithRoom`. `src/pages/ParticipantPage.test.ts` pins the localized error screen. All of them fail on the tree before the change.
