## Description

As the operator of an omul instance, I want administrator access to require that the account has proven control of its allowlisted address, so that whoever first signs up with an address on `OMUL_ADMIN_EMAILS` does not become an administrator without owning that inbox.

## Notes

Raised for production hardening, **internal**. This is an authorization defect: admin rights are granted on an address nobody has proven.

**Current behaviour.** `/api/admin/*` admits a signed-in account when `isAdminEmail(account.email)` holds (`server/routes/admin.ts:78`, `server/admins.ts:54`), which compares the address alone and never reads `emailVerified`. Because verification is soft (`server/accounts.ts:174`, see REQ188), anyone can create an account under an allowlisted address that has no account yet — or no longer has one after a self-service deletion — and is signed in and admitted to the admin surface at once, reading feedback answers and admin events.

**Desired outcome.** An account is treated as an administrator only when its email address is both on the allowlist and verified.

**Done when.** A test shows an account on the allowlist with an unverified address answered `403` by `/api/admin/*` and the same account admitted once verified, with the gates in `AGENTS.md` (`mise run test`, `mise run check`) green.

**Out of scope.**
- Requiring verification for sign-in in general — that is the operator-enforced switch in REQ188.

**Note.** An operator whose own allowlisted account is still unverified loses the admin surface the moment this ships, until they follow a verification link — which needs a deployment that actually sends mail. The client may still show admin affordances to such an account; whether it does was not checked here.
