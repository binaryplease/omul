## Description

As a client of this API — a script, an integration, or an AI agent finding the surface with no prior knowledge of the route layout — I want every link the `/api` discovery index hands me to be one I can follow as written, on the deployed public host as much as on a plain local server, so that the one route whose entire job is to be believed can be.

## Notes

`server/index.ts` built the discovery response's `links` from `new URL(request.url).origin`. In a production deployment a reverse proxy terminates TLS at the public host and forwards over plain HTTP to loopback, so the origin the process observes is `http://<public host>` — the right host with the wrong scheme — and every link went out as `http://`, the WebSocket one as `ws://` (derived by `base.replace(/^http/, "ws")`). Nothing in the repo read `X-Forwarded-Proto`.

A browser survives that on the proxy's `http` → `https` redirect. A client that follows the links literally does not, and a `ws://` connection to a host that serves only 443 fails rather than redirecting — so the failure lands on exactly the caller the route exists for.

**The constraint that shapes the fix.** This repo already has a stated position on forwarded headers: `OMUL_TRUST_PROXY` defaults to `0` and the abuse limiter ignores `X-Forwarded-For` unless the operator says a proxy exists, because the header is caller-supplied and a directly-exposed server that believes it hands every caller a fresh bucket per request (REQ145). The discovery index has the same exposure in a different currency — believing a caller there lets it choose the links this server hands the *next* client — so it must tell the same story, not a more relaxed one. It reads the same variable, the same way, from a module both now share.

**What it resolves, most trustworthy first** (`server/routes/discovery.ts`):

1. `OMUL_BASE_HOST` — the public host, as configuration rather than as a header. Read as `https://<host>`, the same variable and the same reading `server/accounts.ts` already resolves Better Auth's canonical origin from. A value that is not a bare host is a fatal startup error, not a fallback: the variable exists precisely because the observed origin is wrong here, so quietly ignoring a malformed one would serve the broken links it was set to prevent.
2. `X-Forwarded-Proto` / `X-Forwarded-Host`, and only as far as `OMUL_TRUST_PROXY` says a proxy exists — the entry that many hops in from the right, the same rule the limiter's client address uses, so a caller cannot prepend its own.
3. The origin the request actually arrived on. Unchanged for `mise run dev`, for the tests, and for a directly-exposed self-hoster, which keeps reporting its own real origin.

The WebSocket link is derived from the resolved origin rather than assembled separately, so it cannot disagree with the links beside it about the scheme.

**Naming what stays invisible.** A proxied deployment that sets neither variable looks, from inside the process, exactly like a healthy direct one — the same shape of blindness REQ145's startup report exists for. So the boot log states which of the three sources is in force, and that is also where a malformed `OMUL_BASE_HOST` becomes fatal, rather than first failing on a link days later.

Out of scope: the limiter's own client-address logic (REQ145, done); Better Auth's base-URL resolution, which already resolves a canonical origin and was not the defect; and the deployment's own configuration, which lives outside this repository and already sets both `OMUL_TRUST_PROXY` and `OMUL_BASE_HOST` correctly.

## Triage note

Discovery links now carry the origin a client can reach: OMUL_BASE_HOST, else a trusted X-Forwarded-Proto/Host, else the observed origin; ws scheme derived from it.
