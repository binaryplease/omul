## Description

A slide carries an optional background image, rendered so foreground text keeps a legible contrast against it.

## Updates

- 2026-08-11 — Completed the pre-existing backgroundImage field rather than rebuilding it. Two gaps closed: the URL now goes through browserSafeAssetUrl() (the same scheme allowlist the deck logo uses), so a javascript:/data:/protocol-relative address draws no picture instead of reaching a background-image; and the legible-contrast guarantee is now computed rather than hard-coded — slideScrimFor() picks the scrim's tone against the words that sit on it and checks WCAG AA, honouring an authored text colour only while it passes. The values reach CSS as --slide-scrim / --slide-overlay-text / --slide-overlay-shadow, with index.css keeping the previous per-scheme values as the fallback, so a slide that authored nothing renders exactly as before. Verified end to end on the presenter, participant and preview surfaces in both colour schemes.
- 2026-08-11 — Review fix (NST8763, finding 6): the scrim's legibility check compared the authored text against pure black/white, but the scrim is 0.7-0.82 alpha over an arbitrary picture, so the computed contrast was a best case rather than a floor. It now checks against the worst backdrop each tone can produce — its weakest alpha over the most hostile image — which both fallback pairings still clear (8.45 and 6.98), so the AA claim in the docs is now a guarantee rather than an approximation. Also correcting the entry above: 'verified end to end ... in both colour schemes' was a manual browser pass during the build session and is not something the branch reproduces; the automated coverage is the resolver, the HTTP round-trip and now the worst-case scrim floor.
