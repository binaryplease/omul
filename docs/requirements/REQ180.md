## Description

As someone driving omul from a terminal, a CI job or a coding agent rather than from a browser, I want one installed command that creates a presentation and reads its state and results over the same HTTP API the web client uses, authenticated by the personal API key I already hold, so that an automated caller does not hand-write requests against `/api` to do what a presenter does by clicking.

Done when a person who has installed this repository's command-line client can create a presentation and read that presentation's results with that client alone — an API key, no browser step — against a running server, with the gate AGENTS.md declares still green.

## Notes

**Current behaviour.** The HTTP surface is already programmatically reachable and already documents itself. Personal API keys are issued by the Better Auth `apiKey` plugin and accepted in the `x-api-key` header (`server/accounts.ts:263`, `server/accounts.ts:344`); a create authenticated by an API key is owner-editable through the key and is deliberately minted no redundant edit token (`server/routes/presentations.ts:507`); `GET /api` is a discovery index written to be followed by a client or an agent that knows nothing about the route layout (`server/routes/discovery.ts:176`), and the OpenAPI spec sits at `/api/docs/json` behind a Scalar UI at `/api/docs` (`server/index.ts:34`). What does not exist is any client for that surface outside the browser. `src/api.ts` is the frontend fetch client and is browser-bound — it keeps edit tokens in `localStorage` (`src/api.ts:84`); `package.json` declares no `bin`; `flake.nix` exposes `devShells` and nothing else (`flake.nix:21`, `flake.nix:56`), so there is no package or app output for `nix run` to reach. A terminal caller today writes `curl` by hand.

**This is credential-handling code.** The client holds two long-lived secrets — a personal API key, and the per-presentation edit token that is returned exactly once — so where it reads each from, and whether either can end up in a shell history, a log line or a process argument list, is part of this requirement rather than a detail of it.

**Delivery shape is already decided by the owner.** The executable is Bun-run and reachable through this repository's flake as a runnable output, plus a `bin` entry. The two sibling viewers in this estate already ship exactly that shape — a flake `packages.default` whose install phase wraps the built CLI bundle, an `apps.default` beside it, and a `bin` name in `package.json` — and they are separate repositories, so that precedent is not resolvable from this tree. The command word follows the convention those siblings state, package name = repository name: `omul`.

Out of scope: the agent skill that teaches an agent to use this client (its own requirement, filed alongside this one); any new HTTP route — the client wraps what `/api` already exposes and adds no server surface; and full coverage of every API verb — each further verb group is its own record, and a client that cannot yet do everything the browser does is still the outcome above.

Catalog note: written with `source: internal`, following REQ179's precedent, because the business half was not in scope and no business-requirement number was available to cite. If one covers a programmatic client surface, this `source` line is the thing to correct.
