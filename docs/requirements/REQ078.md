## Description

A deck can carry a chat channel participants post to during the session, separate from the Q&A queue and from slide answers.

## Updates

- 2026-08-10 — Live chat shipped as a channel separate from the Q&A queue and from slide answers at every level: its own chatMessages collection (no slideId in the stored shape), its own GET/POST /api/presentations/:id/chat, its own chat.updated broadcast, and no aggregation that reads it. chatEnabled is deck state defaulting closed (ADR-0029), moved by POST /api/presentations/:id/channels (owner or edit token) and by the deck PATCH the editor saves through, both broadcasting channels.settings. One projection for everybody — a chat is the room's, not a moderated list — except own, which marks the reader's lines; the writing participantId never leaves the server. Ordered oldest-first on a strictly-increasing stored instant so same-millisecond messages keep the order they were written in, capped at the newest 200 as a read cap. Closing the channel stops posting, not reading. Cleared by reset (REQ101) and by delete (REQ146) — delete-cascade now covers five collections. Client: a shared ChatPanel module (feed reader, useChatFeed on chatRevision, list, composer, heading, switch), participant section, presenter audience panel, and editor deck settings; chat strings added to all seven dictionaries (REQ084). Tests: chat.schemas.test.ts, chat.integration.test.ts (a message is in the chat and in neither the Q&A list nor any tally, and vice versa), ChatPanel.test.ts, session-slice reducers. docs/api.md updated.
