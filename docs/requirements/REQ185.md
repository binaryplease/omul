## Description

As a presenter, an editor or a participant, I want to send feedback about omul from the app menu on any screen, without leaving the app, so that the people who run this instance hear what I think of the tool. The feedback must not pass through a presenter or an event organizer. When I am signed in, I want to be able to say "you can contact me about this", so that the operator can write back to me.

## Notes

**Two feedback channels and one store.** This requirement owns the feedback database and the menu channel ("user feedback"). REQ186 adds the participant channel: the prompt after a session, which reuses this store, the form and the operator view. A third channel already exists and is not touched: a presenter who wants feedback on their own event adds ordinary slides (the open-ended question, REQ023; the `feedback` template category in `server/schemas.ts`).

**The feedback database.** It is a dedicated `bun:sqlite` file, built the way `server/admin-events.ts` builds `admin.sqlite`:

- Module: `server/feedback-store.ts`, a factory function. A process-wide default store is opened at import.
- Path: `OMUL_FEEDBACK_DB`. The default is a `feedback.sqlite` sibling of the docstore file, through `server/store-path.ts`. `:memory:` gives tests an isolated store.
- Two tables, one per channel: `user_feedback` (this requirement) and `participant_feedback` (REQ186). Their columns are the same apart from `surface` and `contactAccountId`, which only `user_feedback` has:

| Column      | Type                | Meaning                                                                                                 |
|-------------|---------------------|---------------------------------------------------------------------------------------------------------|
| `id`        | text, primary key   | random UUID                                                                                             |
| `rating`    | integer 1–5, null   | optional star rating                                                                                    |
| `comment`   | text, null          | optional, at most 2,000 characters, trimmed                                                             |
| `surface`   | text                | `user_feedback` only: `presenter`, `participant` or `other` — the kind of screen the menu was opened on |
| `contactAccountId` | text, null   | `user_feedback` only: the sender's account id, set only when the contact box was ticked                  |
| `language`  | text                | UI language of the screen it was sent from                                                              |
| `createdOn` | text, `YYYY-MM-DD`  | UTC date only                                                                                           |

Keeping this out of the zodstore domain data is deliberate. Feedback is the operator's data about the product, not data in any deck, workspace or account, so no presentation, workspace or deletion path ever touches it. Backing it up, purging it or excluding it is one file. The request bodies are still validated by Zod schemas in `server/schemas.ts`, which stays the single place where boundary shapes are defined.

**Never stored:** an email address, a participant id, a name, a presentation id or code, a workspace, an IP address, a user agent, or a time finer than the day. An account id is stored only as `contactAccountId`, and only when the sender ticked the contact box. Without the tick, an answer is as anonymous as a participant's. On a quiet instance a timestamp to the minute sitting next to a known session would identify the sender. The write route must not log the request body.

**Contact is stored as the account id, not the email address.** The operator view looks up the email at read time with `findUserById` (`server/accounts.ts:391`). This has two consequences, and both are intended:
- If the user changes their address, the operator writes to the current one.
- If the account is deleted (`POST /api/auth/delete-user`), the lookup returns nothing. The entry then reads "account deleted, no contact", with no cascade hook and no copy of the address left in `feedback.sqlite`.

**The pre-ticked box is not consent, and nothing may treat it as consent.** GDPR Recital 32 says that "silence, pre-ticked boxes or inactivity" do not constitute consent, and the CJEU (Court of Justice of the European Union) held the same for a pre-ticked box in Planet49 (C-673/17). The box is a choice the sender can see and undo before sending, and it is used only to reply to that one piece of feedback. So:
- The code and the docs do not call it consent.
- The stored id is used for nothing but the operator's view of that entry: no newsletter, no export, no other route.
- Which legal basis a deployment relies on, and what its privacy policy says about it, is the operator's call, settled with their legal advisor and not in this repository. The same goes for whether the box should start unticked. The default is a one-line change in `FeedbackForm`.

**Rating or comment — at least one, either alone is enough.** A submission is valid when it has a `rating` (an integer 1–5), a non-blank `comment`, or both. A comment alone is complete without stars, and stars alone are complete without a comment. If neither is present the server answers `400`, and the client keeps the send button disabled.

**The form.** One shared component, e.g. `src/components/FeedbackForm.tsx`:
- five stars, optional, and tapping the selected star again clears it;
- a comment box;
- **signed in only:** a checkbox, ticked by default, labelled "You can contact me about this". Under it, a line in smaller type names the address: "We'd write to maria.keller@example.org (your account email)", with the signed-in account's email filled in from `useSession()` (`src/auth-client`). Signed out, the checkbox and the line are not drawn. The REQ186 prompt never draws them;
- a send button, enabled once a rating or a non-blank comment is present;
- a confirmation after sending.

The form's heading names the recipient: "Feedback about omul — goes to the people who run omul here, not to the presenter or organizer". REQ186 renders the same component in the deck's language. The menu's copy is English, like the rest of `AppMenu`.

**The menu channel.**
- `AppMenu` (`src/components/ui/AppMenu.tsx`) gains a "Send feedback" item between Appearance and Legal.
- The item opens the form in a dialog: a disclosure that keeps the menu's existing focus rules (Escape closes it and focus returns to the trigger).
- It appears on every screen that mounts `AppMenu`. `src/components/LegalLinks.test.ts` already requires every routed page to mount the menu.
- No URL and no external target: nothing leaves the deployment.

**Write path.** A public `POST /api/feedback` taking `{ rating?, comment?, surface, language, contactMe? }`.
- It works without an account, because participants and anonymous deck creators have none.
- **The account comes from the session, never from the body.** With `contactMe: true`, the server stores the id returned by `resolveUserId` (`server/accounts.ts`). Without a session, `contactMe` is ignored and the answer is stored anonymously. A client cannot name somebody else's account.
- It is rate-limited by client address under REQ145. Add a new rule to `server/rate-limit.ts` and a row to the abuse-limits tables in `docs/deployment.md` and `docs/api.md`.
- It answers `404` while the channel is off, for every request — the body is not read or validated first, so a malformed or empty one cannot get a different answer.
- It takes `application/json` only and refuses any other content type with `415` before validation and before the rate limit. A form-encoded, multipart or plain-text post is what a page on another site can make a visitor's browser send, and the real client sends JSON.

**Configuration.** Off on a fresh install. With the switch unset, the menu, the endpoints and the boot line behave as they did before this requirement.

| Variable                | Default       | Meaning                                                  |
|-------------------------|---------------|----------------------------------------------------------|
| `OMUL_FEEDBACK_ENABLED` | unset (= off) | exactly `"true"` turns the menu item and its endpoint on |
| `OMUL_FEEDBACK_DB`      | `feedback.sqlite` beside the docstore | where both channels' answers are stored |

- The boot line reports which posture is in force (`[feedback] …`).
- If the channel is on but `OMUL_ADMIN_EMAILS` is empty, the boot line also warns that nobody can read the answers.
- The client learns the state from a public `GET /api/feedback/config`, which returns `{ enabled: boolean, … }`. REQ186 adds its own fields to the same payload. The client reads it once per page load, the way `useLegalLinks` loads `GET /api/legal`.

**Operator view.** Reading feedback is operator-only.

- **API:** `GET /api/admin/feedback?channel=user|participant` sits behind `requireAdmin` in `server/routes/admin.ts` (REQ164: cookie session plus `OMUL_ADMIN_EMAILS`). It returns:
  - the total;
  - the count per rating, plus the number of entries with no rating;
  - the entries newest first, with a cursor for paging.
  - For `user` entries only, it also returns the contact address resolved at read time: an email, `null` when the box was not ticked, or a "deleted" marker when the account no longer exists. The page renders the email as a `mailto:` link, so a reply goes out from the operator's own mail client and omul sends nothing itself.
  - The gate answers before anything else, the query's validity included. While the channel is off an administrator gets `404`, the answer `POST /api/feedback` gives, and no database is opened. Any other `channel` is `422`; a `cursor` that names no entry of the channel is `400`.
- **Page:** a minimal page at a new route, `/admin/feedback`, with one tab per channel. It is the first admin page in `src/router.ts`. A non-admin sees the `403` as an error screen that mounts `AppMenu`.

Presenters, workspace roles and deck owners never see either channel. No presentation, workspace, results or export path reads the feedback database.

**Done when.**
- With `OMUL_FEEDBACK_ENABLED` unset:
  - the menu is unchanged;
  - `POST /api/feedback` answers `404`;
  - `GET /api/feedback/config` reports `enabled: false`;
  - no `feedback.sqlite` is created.
- With it set:
  - the menu item appears on every screen that mounts `AppMenu`;
  - a comment-only, a rating-only and a combined submission are each stored;
  - an empty submission is refused with `400` and is impossible to send from the UI;
  - a stored row holds only the columns above (store test).
  - Signed in, the form shows the ticked checkbox and the account's email. Sending with the box ticked stores `contactAccountId`; unticking it first stores `null`. Signed out, there is no checkbox, and a body carrying `contactMe: true` still stores `null`.
  - After the account is deleted, its entries read "account deleted" in the operator view, and no email address exists in `feedback.sqlite`.
- `GET /api/admin/feedback` answers `401` signed-out and `403` for a non-admin, and returns both channels to an admin.
- `docs/deployment.md`, `docs/api.md` and `.env.example` carry the variables and endpoints.
- `mise run check` and `mise run test` stay green.
