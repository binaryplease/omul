## Description

As a second editor whose presenter screen missed the deck ending, I want a "Start timer" or "Restart timer" click that the server refuses to bring my screen to the deck's real state, so that I am not left on an error page that is also wrong about what happened.

The server refuses the timer on a presenter-paced deck that is not live with `409` and `refused: "presentation-not-live"` (REQ227). That answer is correct and stays. The presenter page handed it to the store's page error, which replaced the whole presenter view with "Start the presentation first — question timers run only while the deck is live". That wording names a draft, so it was wrong for an ended deck too, and only a reload brought the screen back.

- **The view stays.** That refusal never replaces the presenter view.
- **The screen catches up.** It re-reads the deck on its own credentials. When the deck ended, or was reset to a draft, it applies the lifecycle change it missed as the `ended` or `reset` frame would have. A frame that lands while the read is in flight wins.
- **The notice names the real state.** A toast beside the view says "The presentation has ended — question timers run only while the deck is live" for an ended deck, and the existing "Start the presentation first …" only for a draft. The disabled timer control carries the same reason as its tooltip and description, and so does the route's `error` text on an ended deck.
- **Unchanged:** the route's status and `refused` code, survey decks, and every other timer failure, which keeps the page's error path.

## Notes

Defect, **internal**: Re-Test D, section 4, the `/timer` 409. The deck was live with a running quiz timer. The second editor dropped `presentation.ended` with a WebSocket init script, the presenter clicked "End", and the second editor clicked "Restart timer".

- **Wording:** `QUIZ_TIMER_DECK_ENDED_REASON` in `server/schemas.ts`, returned by `quizTimerUnavailableReason` for an ended deck. The route, the disabled control and the notice all read that one function, so they cannot disagree. Changing the route's `error` prose on an ended deck is the only server-visible change: the route itself is untouched.
- **Client:** `routeTimerFailure` in `src/components/PresenterSlideView.tsx` sends an `ApiError` whose `movedOn` is `presentation-not-live` to a catch-up and a notice, and everything else to the page error. The notice is phrased from the deck the screen holds after the catch-up, never from the refusal's prose. `catchUpPresenterDeck` in `src/store/session.ts` re-reads through `getPresentation` without raising `loading`, and replays `applyEnded` or `applyReset` only when the status is still the one it asked from. `PresenterPage.handleRestartTimer` wires both.
- **Tests:** `src/components/PresenterSlideView.test.ts`, "a timer refused on a screen behind the deck (REQ237)", answers the timer call with the 409 and the deck read with the real deck. It checks three things: no page error, the deck caught up (ended with its end stamp, or reset), and the notice and the control's tooltip naming the real state. It also pins that other failures keep the error path and that a frame landing during the read wins. `server/quiz.integration.test.ts`, "the timer is refused on an ended deck", pins the ended wording on the route. They fail on the tree before the change.
