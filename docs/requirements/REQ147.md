## Description

As a participant, I want my answer to a quiz question to be the one answer I hold however many submissions leave my device at the same moment, and as a presenter I want every number the room's tally reports to count the same way, so that "one final answer" (REQ054) is a rule the deck actually keeps rather than one a double-tap can get around, and so that one payload can never report one respondent beside two answers.

## Notes

Defect, found in review of the quiz slice on `workbatch/edc87853`, confirmed by reproduction rather than by reading.

**What was wrong.** The one-answer rule in `submitVote` is a read-modify-write: it looks up the participant's rows on this slide, refuses if any of them still stands, and otherwise inserts. `votes.find` is `await`ed, so the next submission's handler runs in that gap and reads the state that predated the first one's insert. Both then write. Against a fresh in-memory deck, two concurrent submissions from one participant both persisted and the editor's payload read:

```
respondentCount:       1
scoring.answeredCount: 2
scoring.correctShare:  50
option counts:         a=1 b=1
```

One person in two bars of the chart the room is looking at, and a correct share taken over rows rather than over people.

**Why a quiz and not the rest.** Ranking, 100 Points, Guess the Number and Pin on Image are all one row per participant too, and all reach the same gap — but each of them *replaces* on the participant's next submission and collapses whatever the race left behind. A quiz is the one slide type that permanently refuses that next submission, precisely because speed is part of the score (REQ054). So the two rows stand for the rest of the session, and neither the participant nor the presenter has any way to get back to one.

**Why the numbers disagreed on top of it.** The read path counted two different units in one payload. `respondentCount` counted distinct participants; `scoring.answeredCount`, `correctShare`, `totalVotes`, the per-option counts and the typed-answer groups (REQ055) all counted rows. Meanwhile the leaderboard (REQ059) and the participant scorecard each silently took the *first* of the two rows. Three readings of one room, in one response.

**Scope of the fix.**

- `server/keyed-lock.ts` — a keyed queue, so a read-modify-write cannot interleave with another under the same key. In-process, like the abuse counters in `server/rate-limit.ts` and for the same stated reason (omul ships as one container); several replicas would each get their own queue.
- The quiz branch of `submitVote` runs its check-and-insert in that queue, keyed `presentationId:slideId:participantId` — the narrowest key that covers the invariant, so a whole room answering together is not serialized. The loser of a race reads the winner's row and is refused with `quiz-already-answered`, which is the truthful answer and already the modelled one. The broadcast stays outside the queue.
- `finalQuizAnswers` — one judgement about which rows count on a quiz slide (standing, and one per participant, the first), composed by the scoring, the typed tally, the per-option counts, `totalVotes` and `respondentCount`. It is what makes the payload internally consistent for decks that already hold a duplicate, which the write-path fix cannot reach. `rankQuizDeck` lost its own copy of the de-duplication, which was the same rule stated a second time and the copy the room's tally did not have.

Covered by `server/keyed-lock.test.ts` (the queueing itself), `server/quiz.integration.test.ts` (concurrent submissions leave one row; a deck already holding two reads as one, and the scorecard and standings agree with the bars beside them) and `server/quiz-typed.integration.test.ts` (the same for a typed question's answer groups). All three fail against the unfixed service and pass after.

Out of scope: the same race on the Word Cloud / Open Ended response cap, filed as REQ148 — pre-existing, and self-correcting on the participant's next submission in a way a quiz's is not.

## Updates

- 2026-08-07 — Requirement written against a defect found in review of the quiz slice. Fixed by queueing the quiz branch's read-modify-write per participant per question (server/keyed-lock.ts, a factory-shaped keyed lock per ADR-0007) and by routing every count on a quiz slide through one finalQuizAnswers judgement, so a payload reports people consistently rather than rows in some fields and people in others. Regression tests in server/keyed-lock.test.ts, server/quiz.integration.test.ts and server/quiz-typed.integration.test.ts, each verified failing against the unfixed service.
