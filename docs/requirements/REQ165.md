## Description

As the owner of a repository headed for publication, I want the public artifact to be a *new* repository created from the reviewed tree, with this repository parked private, so that no object the current remote still serves by SHA can be reached at the public URL — and so that the estate detail this repository's own commit messages narrate does not travel with the tree.

## Notes

Raised by a publication readiness check, **internal**. This is the finding that decides the *shape* of the publication, so it is recorded even though nothing here is a secret.

**A local scan cannot see this, which is why it is written down.** `gitleaks` over all refs is clean and every local history check passes. That says nothing about the remote's object store, because a clone only ever fetches *reachable* objects. The check has to be run against the remote directly.

**What the check found.** This repository's initial commit was amended after it was pushed. The local reflog shows both the original and the amended commit; the original is unreferenced by any branch or tag, does not appear in `git log`, and is invisible in the GitHub UI. The remote still serves it: a direct object query returns the commit in full, with its author identity, its date, its tree SHA and its complete message. Every blob under that tree is reachable the same way, by anyone who has or can guess the SHA.

The difference between the two commits is two documentation files, and the content is not itself sensitive. That does not change the verdict. A repository that ever had something removed by rewrite, amend or force-push is dirty by construction, and the rule has no threshold: the object is served, the object is dirt, and flipping this repository to public publishes it with nothing in the interface to indicate it is there. A rewrite would not help — a rewrite is what created this — and the platform's sensitive-data removal request is discretionary, applies only to material the platform judges to be a credential, and lands after the objects have already been served.

**There is a second, independent reason.** The initial commit's message narrates the predecessor repository's history, its archived name, and the private infrastructure repository that owns the deployment. Commit messages cannot be corrected without rewriting history, which this project does not do. A fresh repository resolves it by construction: the tree crosses, the commits do not.

**One half of that argument is retired, and the verdict does not move.** This requirement used to count a second thing in the same breath: every commit here carries an internal work-queue task identifier as a trailer, and those trailers cannot travel. On 2026-08-31 the owner retired work-queue identifiers as a disclosure class (REQ163 class 3) — the session runner stamps every commit with one, the published repository will go on collecting them, and one ticket number a reader cannot resolve is not worth an unending chase. So the trailers are ordinary text: whether they travel is no longer a reason for anything. What is left is the sentence above, about what the initial commit's message *says*, which never depended on the trailer and still stands. And the object-store finding decides this requirement on its own in any case — a fresh repository was never carried by the trailer argument.

**What this means concretely.** Publication runs `extract-repo-for-publication` against the reviewed ref, not a visibility flip on this repository. That skill exports the tracked tree, sweeps it as a tree, commits it under an explicit author identity, parks this repository under a private legacy name, and creates the new repository private with its own approval gate before it is made public. Because the *history* here is dirty and not only the object store, the new repository starts at a single commit rather than carrying these 59 across.

**Precedent, and why it is not a repetition.** This repository is already the product of one such extraction — its own initial commit records that the predecessor was archived rather than rewritten, for exactly this reason. That extraction was correct and it worked: no competitor name or help-centre URL survives anywhere in this tree or its history. What it did not survive was an amend afterwards. The lesson to carry into the next one is the ordering: the extracted repository is created private and stays private until its gate, and nothing is amended after a push.

**Ordering.** REQ163 and REQ164 clean the tree *first*. Extraction does not launder a tree that still discloses — it copies whatever it is given. REQ161's license instrument should also be in the tree that crosses, so the new repository's first commit is licensed.

**Done when.** The public artifact is a new repository whose history begins at one commit over a tree that passes REQ161–REQ164; this repository is private under a legacy name; and a direct object query against the *new* remote for any pre-publication SHA returns nothing.
